# SMS 에이전트만 쓰는 고객사 테스트베드 설계

저장소 위치: testbed-services `docs/spec-testbed-sms-only.md`. 작업 기록 위치: `~/dev/testbed-ops/v4/agent-out/ST1-design.md`. 작성 2026-11-16 KST(ST1 설계 에이전트). 관문 GT0-S(사용자 직접 승인)는 2026-11-16 12:4x KST 에 통과했다(추천 6개 모두 확정). 아래 결정 6개는 확정이고 ST2~ST5 는 이 확정을 따른다.

자매 문서: [SMS, NMS 전용 전통 3계층 테스트베드 설계](spec-testbed-vm-3tier.md)(이하 "T 문서", GT0 확정 2026-11-10). 이 문서는 T 문서의 구성과 절차를 기본값으로 쓰고, 다른 점만 새로 정한다. 따로 적지 않은 것은 T 문서를 따른다.

근거로 쓴 조회: 66, 119, 66 위 tb-w1 과 tb-runner 를 읽기 전용으로 조회했다(2026-11-16 11:35~11:50 KST). 119 ClickHouse 질의는 파드 안 `clickhouse-client --readonly=1 --max_threads=2 --max_execution_time=60` 에 시간 범위 조건을 걸었고, PostgreSQL 은 `default_transaction_read_only=on` 으로 SELECT 만 했다. 제품 코드는 lucida-next `origin/develop-ai` 를 읽었다(119 설치판은 `develop-ai-2026.11.09-01`).

## GT0-S 결정 (2026-11-16 사용자 확정)

| # | 정한 것 | 선택지 | 확정 | 근거 한 줄 |
|---|---|---|---|---|
| 1 | 119 가 S 서버에 닿는 길(ICMP 를 넣을지) | (가) T 의 WireGuard 터널을 같이 쓰고 119 쪽 허용 대역에 S 업무망 /24 하나를 더한다. ICMP 켬, 에이전트도 터널 주소로 보낸다 (나) 터널 없이 66 NAT 로 보내기만 한다. S 서버 4대의 수집 정책에서 ICMP 상태와 RTT 를 끈다 (다) 사내망 VLAN 213 주소 4개를 받아 기존 작업 노드처럼 직통 | (가) | 보내기만은 터널 없이 된다(실측). 그러나 ICMP 는 SMS 등록에 딸려 오는 제품 기본 동작이고, 가용성 판정(DOWN 과 UNKNOWN)을 가르는 근거다. 닿지 않는 주소로 등록하면 기존 작업 노드 3대처럼 ICMP 0 이 7일 내내 남는다(§3-1, §3-4). (다)는 사내망 주소 요청이라 T0 사용자 결정("IP 요청 없이")과 어긋난다 |
| 2 | syslog 를 119 로 보낼지 | (가) 보내지 않는다. SMS 에이전트 로그 감시가 `/var/log/syslog`, `auth.log` 파일을 본다 (나) T 처럼 rsyslog 로 119 UDP 514 에 보낸다 | (가) | 제품에서 syslog 수신기는 `network` 형 대상(`syslog-udp-514`)으로 등록되는 NMS 쪽 수집이다(조회). SMS 만 쓰는 고객 모양에 맞고, 로그 원천이 하나라 쌍 비교에서 무엇이 빠졌는지 분명하다 |
| 3 | 계층 사이 가상 라우터 | (가) 두지 않는다. 업무망 하나에 서버 4대, 66 호스트가 게이트웨이 (나) T 와 같은 라우터 VM 을 두되 119 에 등록하지 않는다 | (가) | 라우터가 원인인 장애는 S 에서 정답 대상(등록 대상 번호)이 없어 쓸 수 없다(원칙 6). 서버 쪽 원인의 쌍 비교에서 라우터 한 홉은 결과를 바꾸지 않는다고 본다(추정, ST4 쌍 시험 1건으로 확인). VM 하나와 라우터 설정, 보호 표 유지 비용이 든다 |
| 4 | 원칙 2 서비스 균형과 쌍 녹화의 셈 | (가) T 와 S 는 같은 앱이므로 서비스 균형에서 한 몫으로 센다. 같은 원인의 T, S 쌍 녹화는 분류 장부에 1건으로 센다 (나) S 를 다섯째 도메인으로 따로 세어 1:1:1:1:1, 쌍은 2건 (다) 쌍을 만들지 않고 S 는 독립 시나리오만 | (가) | (나)는 한 앱이 새 생성분의 2/5 를 가져가고, 같은 장애가 장부에 두 번 들어가 묶음 20% 상한에 두 배로 빨리 닿는다. (다)는 "관제 범위만 다른 쌍"이라는 S 의 목적을 버린다. 쌍의 id 규칙과 정답지 두 장의 꼴은 생성 스킬(T5, ST5)에서 정한다 |
| 5 | 서비스 구성 코드 | (가) T 의 코드를 그대로 쓴다(같은 앱 디렉터리, 인벤토리 파일만 둘). T2 가 주소, 이름, 라우터와 syslog 와 DPM 부분을 변수와 선택 단계로 짓게 요구한다 (나) S 전용 사본 | (가) | T2 는 아직 시작 전이라 지금 요구하면 비용이 거의 없다. 사본은 시간이 지나면 갈라져 쌍 비교가 깨진다(§2-3, §2-4). (11-16 덧붙임) T 도 DPM 을 쓰지 않게 되어(T 문서 11-16 결정) DPM 부분은 만들 것이 없다. 추천과 승인은 그대로다 |
| 6 | 119 ClickHouse 메모리 판정 기준 | (가) T 문서의 3.6GiB 를 예산으로 그대로 둔다 (나) 지금 상한(파드 8Gi, `max_server_memory_usage` 7.2GiB)에 맞춰 올린다 | (가) | 파드 상한은 11-10 에 8Gi 로 바뀌었지만(조회) 119 노드는 메모리 23.5GiB 에 스왑이 없고 지금 여유가 10GiB 안팎이다. 10-31 정지 선례도 있다. T 와 S 를 함께 더한 예상 최댓값 3.34GiB(최악 3.46GiB)는 3.6GiB 안에 든다(§5). (11-16 덧붙임) T 의 DPM 을 빼고 다시 세어 약 3.32~3.33GiB(최악 약 3.45~3.46GiB)다. 추천과 승인은 그대로다 |

결정 1 에서 (가)를 고르면 S 는 T0(터널 성립)를 기다린다. T0 가 막혀 T 가 T 문서 결정 8 (다)(제품 원격 수집 워커)로 가면 S 는 (나)로 내려간다. 이 내려감은 다시 묻지 않고 이 문서의 규칙으로 정한다.

### 0-2. 이 문서가 하지 않는 것

- 시나리오 후보, 예시, 원인 분류 축을 정하지 않는다. §8 은 S 데이터로 원칙 3~7 이 서는 범위와 경계만 적는다.
- 주입 강도, 판정 임계값을 시나리오별로 정하지 않는다(시험 실행에서 정한다, 원칙 9).
- T 문서의 확정 결정을 바꾸지 않는다. T 에 대한 새 사실은 §14 확인 필요에 적고 지휘 세션에 넘긴다.
- lucida-next 제품 수정을 정하지 않는다.

## 1. 목적과 요구

목적: (c') 형식, 즉 SMS 에이전트만 쓰는 고객이 가진 데이터(SMS 서버 지표, 프로세스 표본, 연결 표본, 로그 감시 줄, SMS 등록에 딸린 ICMP 상태와 RTT, 가용성)만으로 원인이 서는 장애를 녹화한다. 같은 앱과 같은 장애를 T 에서도 녹화하면 관제 범위만 다른 쌍이 생겨, 관제 AI 가 데이터가 줄 때 어디까지 맞히는지를 같은 장애로 비교할 수 있다.

| ID | 요구 | 수치 |
|---|---|---|
| Q1 | 원인 근거가 SMS 데이터에만 선다 | 이 도메인 녹화 구간에 S 대상의 `otel_traces_local` 행 0, `apm.*`, `dpm.*`, `nms.*`, `kcm.*` 계열 0, `syslog_local` 에서 S 대역(192.168.131.0/24, 132, 133) 출발 행 0 |
| Q2 | 기존 3개 도메인, T 와 격리 | S 주입 중 기존 노드 4대(tb-cp, tb-w1~3)와 T VM 의 CPU, 메모리가 평시 같은 시각 대비 ±5%p 안. S 대역과 192.168.122.0/24, T 대역(192.168.123.0/24~127.0/24) 사이 연결 0(66 FORWARD 거절) |
| Q3 | 평시 안정 | T 문서 Q3 와 같다: 24시간 동안 부하기 5xx와 시간 초과 합이 전체 0.1% 이하, 5분 창의 99% 이상에서 0.5% 이하 |
| Q4 | 터널 끊김이 가짜 장애가 되지 않는다 | T 문서 Q4 와 같다(같은 터널). 녹화 구간 안 터널 공백 0 |
| Q5 | 주입이 터널, 관리망, 관제 흐름을 못 건드린다 | (a) 실행기 인터페이스 허용 목록에 관리 NIC, 66 의 wg0, vmbr0, vmbr1 이 없고 요청하면 거절하는 시험. (b) `vmhost.firewall` 이 보호 대상(§3-6 규칙 3)을 건드리는 규칙을 거절하는 시험이 보호 대상마다 1건 이상 |
| Q6 | 노드 쪽 자가 복구 | 서버 VM 에 거는 모든 주입이 U8 가드를 건다. 기한은 `max_injection_duration` + 600초 |
| Q7 | 주입 배관 흔적 | T 문서 Q7 과 같은 판정. 단 S 는 syslog 를 보내지 않으므로 Q7a 는 `lucida_logs_local`(`event_source=log_monitor`)만 본다. 공통 낱말 0건 규칙에 S 의 Proxmox 접두 낱말 `s5` 를 더한다 |
| Q8 | 119 부담 | **T 와 S 를 합친 119 자원 예산 하나로 판정한다(T 문서 Q8 과 같은 기준, 11-17 검토 세션 답, 계열 수 상한은 두지 않는다).** CH 파드 메모리 최댓값(`MemoryResident` 하루 최댓값 기준) 3.6GiB 미만(결정 6), VictoriaMetrics 파드 메모리 하루 최댓값이 한도의 80% 미만, 119 디스크 80% 미만, 119 steal 하루 평균 증가 3%p 이하, 119 CPU(steal 제외) 하루 평균 70% 이하(다섯째, 11-17 검토 세션 덧붙임 답). ST3 실측(T 가 등록돼 있으면 합)으로 재고, 넘으면 그때 검토 세션에 묻는다. S 가 더하는 활성 계열, 하루 고유 계열, 원천 표(`process_snapshot`, `host_connections`, `lucida_logs_local`) 삽입 행은 참고 측정이다 |
| Q9 | 쌍 비교 성립 | §2-4 조건 전부. ST2 끝과 녹화마다 preflight 가 체크섬으로 확인한다 |

## 2. 구성

### 2-1. 전체 그림

```
                         사내망 192.168.200.0/24, 192.168.230.0/24
   119 (wg0 10.250.0.1) ===== WireGuard UDP (T 와 같은 터널) ===== 66 호스트 (wg0 10.250.0.2)
                                                                     │
               ┌─────────────────────────────────────────────────────┼──────────────────────┐
     S 사용자망 192.168.132.0/24 (66 .1)                    S 업무망 192.168.131.0/24 (66 .1)
       loadgen .10                                            websvr01 .11
                                                              wassvr01 .21, wassvr02 .22
                                                              dbsvr01 .31

   S 관리망 192.168.133.0/24 (66 .1): 모든 VM 의 둘째 NIC. 다른 망과 포워딩하지 않는다. 119 로 안 감.
   tb-ops(192.168.122.20, 러너) → 66 호스트(출발지를 .133.1 로 바꿈) → 관리망 으로만 VM 에 닿는다
```

T 와 다른 점: 계층 사이 라우터 VM 이 없다(결정 3). 66 호스트가 S 업무망과 사용자망을 잇는다. 부하기를 업무망 밖 사용자망에 두는 이유는 T 와 같다(요청이 바깥 사용자처럼 게이트웨이를 지나 들어오고, 서버의 연결 표본에 바깥 주소로 남는다).

브리지 이름과 번호는 ST2 에서 `ip -br link` 로 정한다(T 가 쓰는 번호와 겹치지 않게). S 업무망과 사용자망 브리지에는 66 호스트 주소(.1)를 둔다. T 문서가 업무망 브리지에 호스트 주소를 두지 않은 이유(라우터 우회 길)는 라우터가 없는 S 에는 해당하지 않는다. 대신 66 INPUT 규칙으로 S 대역에서 66 관리면(22, 8006)에 닿는 것을 막는다(§3-5).

### 2-4. 쌍 비교가 성립하는 조건 (Q9)

같은 원인의 T 녹화와 S 녹화를 "관제 범위만 다른 쌍"으로 부르려면 아래가 모두 맞아야 한다. 하나라도 어긋나면 두 녹화는 각각 쓸 수 있지만 쌍이라고 적지 않는다.

1. **같은 소프트웨어**: WAR, 스키마, 부하 스크립트가 같은 저장소 커밋에서 나왔고 체크섬이 같다. httpd, Tomcat, PostgreSQL, JVM 설정 파일은 주소와 이름 자리를 자리표시로 바꾼 뒤의 체크섬(정규화 체크섬)이 같다. preflight 의 버전 표류 검사가 이것을 본다.
2. **같은 기반**: 같은 템플릿, 같은 커널 판, 같은 패키지 판(설치 때 고정 목록), 같은 VM 크기.
3. **같은 부하 모양**: 같은 `PEAK_RPS`, `TROUGH_RPS`, `LOADGEN_SEED`. 주입 시작 시각을 같은 KST 시간대(코사인 부하의 같은 단계)에 둔다.
4. **같은 주입**: 같은 실행기, 같은 승인 강도. 강도 시험 실행은 한 번 하고 두 테스트베드 모두에서 피해 판정(원칙 7)이 나야 한다. 한쪽에서만 피해가 나면 쌍이 아니다.
5. **같은 관제 서버 상태**: 두 녹화 사이에 119 패치가 없다. 두 테스트베드 모두 등록 뒤 24시간이 지나 탐지 밴드가 있다. 두 녹화 모두 녹화 시작 차단(마지막 변경 + 2시간 30분)을 지켰다.
6. **원인 위치**: 근본 원인과 계기가 서버(호스트와 그 하위 리소스, 서비스 프로세스, 서버 위 설정과 파일)에 있다. 근거가 라우터(라우터의 NMS 장비 지표, trap, syslog)에만 있는 원인과 계층 사이 망 경로에 기대는 원인은 쌍이 아니다(결정 3 에서 S 에 라우터가 없다). T 에는 DPM 이 없다(11-16). 서버의 syslog 줄이 근거인 원인은 S 에서도 로그 감시 줄(`/var/log/syslog`, `auth.log`)로 남을 수 있으므로 여기서 빼지 않고 조건 7(S 정답지의 원칙 5 판정)에 맡긴다. 서버 ICMP 상태와 RTT 는 T 와 S 모두 켬이라(T 문서 §4-1, 11-17 검토 세션 답) 그 근거에 기대는 원인도 위 조건을 지키면 쌍이 된다.
7. **정답지**: 두 장. 근본, 계기 칸이 가리키는 물리 위치는 같고 대상 번호만 다르다. S 쪽 정답지가 원칙 5 를 만족하지 못하면(SMS 데이터로 원인을 낼 수 없으면) 그 장애는 T 에만 두고 쌍으로 만들지 않는다.

조건 6 과 7 때문에 쌍은 "T 의 모든 녹화"가 아니라 서버 쪽 원인 장애에만 생긴다. 이 제한은 숨기지 않고 생성 스킬에 알린다(§8).

### 2-5. 평시 운영 요소

T 문서 §2-4 를 따른다. 다른 점:

- syslog: 119 로 보내지 않는다(결정 2). rsyslog 는 로컬 파일 쓰기와 첫 규칙만 둔다. 그래도 첫 규칙은 필요하다. SMS 로그 감시가 `/var/log/syslog`, `/var/log/auth.log` 를 읽기 때문이다.
- 시간 동기화: chrony 로 66 호스트(S 관리망 .1)를 따른다. 허용 오차 50ms.
- 커널 모듈 미리 적재: 서버 4대만. 66 호스트는 S 가 하이퍼바이저 쪽 실행기를 쓰기로 할 때만(§7-1).
- loadgen: 119 로 아무것도 보내지 않는다(T 와 같다).

2. **그러나 SMS 등록은 보내기만으로 끝나지 않는다.** 119 의 collector-sms 는 모든 SMS 호스트의 대상 주소로 ICMP 를 보낸다(§3-4). 대상 주소는 에이전트가 보고한 대표 IP 로 채워진다. 옛 에이전트는 기본 경로 NIC 주소(122.x)를 보고했고 119 는 그 주소에 닿지 못한다. 그래서 기존 작업 노드 3대는 일주일 내내 ICMP 0 이고 RTT 가 없다.

4. 기존 작업 노드가 119 와 직통인 것은 사내망 VLAN 213 주소 덕이다. 이 주소는 66 이전 때(10-19) 따로 받은 사내망 주소다(tb-w1 netplan 주석).

2 와 3 은 기존 테스트베드의 등록 결함이다. S 범위 밖이지만 기존 녹화의 데이터 품질(원칙 3)에 걸리므로 §14 에 적었다.

**확정(GT0-S 결정 1): 넣는다(T 의 터널을 같이 쓴다).**

근거:

1. **ICMP 는 SMS 등록에 딸려 온다.** 제품의 collector-sms 는 매니저 쪽 RTT 프로버로 모든 `polestar_sms` 호스트를 주기적으로 핑해 `sms.server.rtt`(도달하고 RTT 를 읽었을 때만)와 `sms.server.icmp_status`(1 도달, 0 미도달)를 적재한다(`collector-sms/store/rtt_prober.go`, `cmd/collector-sms/main.go` 의 `SM_AVAIL_ICMP`). 이 변수는 기본이 켬이고 119 collector-sms 에는 설정이 없다(조회, 즉 켬). 수집 정책도 기본으로 두 지표를 켠다(119 의 SMS 호스트 6대 모두 `icmp_status` 계열이 있음). 그러니 "SMS 만 쓰는 고객"도 기본 설치에서 ICMP 데이터를 가진다. 넣지 않으려면 정책을 일부러 꺼야 한다.
2. **가용성 판정이 ICMP 에 기댄다.** 에이전트 보고가 끊긴 서버를 스위퍼가 핑해서 실패면 DOWN, 성공이면 UNKNOWN 으로 정한다(`collector-sms/store/availability.go` 머리 주석). 이 스위퍼의 ICMP 는 전역 설정이라 호스트별로 끌 수 없다. 119 가 S 서버에 닿지 못하면 보고가 끊긴 모든 경우가 DOWN 이 되고, "서버가 멈췄다"와 "에이전트만 멈췄다" 또는 "서버 망이 끊겼다"를 데이터로 가를 근거가 사라진다(원칙 3).
3. **닿지 않는 주소로 등록하면 거짓 신호가 상시로 남는다.** 기존 작업 노드 3대가 그 꼴이다(§3-1): ICMP 0 이 7일 내내, RTT 계열 없음. 평시부터 "꺼져 있음"인 신호는 관제 AI 에게 잡음이고, 장애 때 바뀌지도 않는다.
4. **세 주소가 한 주소로 맞는다.** 새 에이전트는 대표 IP 를 "관제 서버로 가는 경로의 출발 주소"로 구한다(`agent/sms/goagent/inventory.go` `primaryIP`). S 서버가 10.250.0.1:18090 으로 보고하면 그 출발 주소는 업무 주소이고, 이것이 대상 주소가 되며, 119 의 ICMP 도 그 주소로 간다. 터널을 쓰면 에이전트 보고 출발지, 대상 주소, ICMP 목적지가 같다.

고객사 현실(추정, 실측 아님): 관제 서버와 업무 서버가 같은 데이터센터 망에 있어 핑이 되는 꼴이 흔하다. 방화벽이 ICMP 를 막는 고객도 있다. 후자는 결정 1 (나)의 모양이고, 그 경우 가용성은 보고가 끊기면 늘 DOWN 이다.

T 의 터널을 같이 쓰는 이유: 같은 66 끝점, 같은 119 wg0 에 허용 대역 하나를 더하는 것뿐이라 119 쪽 변경이 가장 작다. S 전용 터널을 따로 두면 119 에 인터페이스와 포트가 하나 더 생기지만 현실성은 늘지 않는다. 같은 터널을 쓰는 대가는 두 가지다: 터널이 끊기면 T 와 S 가 함께 사라진다(러너는 한 번에 한 도메인만 녹화하므로 Q4 판정은 도메인마다 같다), 그리고 S 가 T0 를 기다린다.

(나)를 고를 때 할 일: 에이전트는 119 실주소(192.168.230.119:18090)로 보내고, 66 의 "119 실주소 거절" 규칙을 S 에서는 두지 않는다. S 서버 4대의 수집 정책(호스트 개별 설정, 제품 화면 경로)에서 `sms.server.icmp_status`, `sms.server.rtt` 를 끈다. 가용성 스위퍼의 DOWN 단정은 그대로 받아들이고 생성 스킬에 "보고가 끊기면 늘 DOWN" 을 알린다. 대표 IP 는 내부 주소라 119 화면의 대상 주소도 닿지 않는 주소로 남는다.

### 3-5. 66 에 더하는 것

T 문서 §3-4 의 66 변경(`t4-net`, wg0)이 먼저 있어야 한다. S 는 새 파일 `/etc/network/interfaces.d/s5-net` 하나에만 쓰고 `tb-nat`, `t4-net` 은 건드리지 않는다. 66 의 FORWARD 기본 정책(ACCEPT, 11-10 조회)은 바꾸지 않고 S 브리지에만 걸리는 명시 규칙으로 격리한다(T 와 같은 이유).

- 브리지 3개(업무, 사용자, 관리), 셋 다 66 주소 .1.
- NAT(패키지 설치용): `-s 192.168.131.0/24`, `-s 192.168.132.0/24` 각각 `-o vmbr0.200 -j MASQUERADE`. 관리망은 NAT 하지 않는다.
- 러너 경로 SNAT: `-s 192.168.122.20 -o <S 관리 브리지> -p tcp --dport 22 -j SNAT --to-source 192.168.133.1`.
- FORWARD(S 전용 체인 하나를 S 브리지에 대해서만 부른다):
  - 사용자망 → 업무망: 192.168.132.10 → 192.168.131.11 tcp 80 과 그 응답만 허용. 나머지 사용자망 ↔ 업무망 거절.
  - wg0 ↔ 업무망(10.250.0.1 ↔ 192.168.131.0/24 만 허용, wg0 ↔ 사용자망, 관리망 거절)은 이 체인이 아니라 터널 도구 `tb-wg` 가 맡는다: `t0-apply.sh add-net 192.168.131.0/24` 가 119 AllowedIPs 와 66 의 mangle 거르기에 이 대역을 더하고, 거르기는 그 밖의 wg0 흐름을 모두 거절한다([터널 적용 runbook](runbook-testbed-tunnel.md) §8). **소유: wg0 의 FORWARD 허용과 거절(wg0 과 상향 사이 거절 포함)과 MSS 는 `tb-wg` 만 다룬다.** `s5-net` 은 `-i wg0`, `-o wg0` 규칙과 MSS 를 두지 않고, 자기 ACCEPT 를 wg0 의 새 흐름에 맞게 쓰지 않는다.
  - 관리 브리지: 192.168.122.20 → 192.168.133.0/24 tcp 22 와 그 응답만 허용, 나머지 거절.
  - S 대역 셋 → 192.168.230.119 거절(결정 1 (가)일 때. 실수로 실주소를 쓰면 실패로 드러낸다).
  - S 대역 셋 ↔ 192.168.122.0/24 거절, ↔ T 대역 123~127 각각 거절(Q2).
  - 업무망, 사용자망 → vmbr0.200 허용(패키지 설치).
- INPUT: S 관리 브리지에서는 chrony(UDP 123)와 이미 맺은 연결 응답만. S 업무, 사용자 브리지에서는 ICMP echo 와 이미 맺은 연결 응답만(게이트웨이 핑은 되고 66 의 ssh, Proxmox 웹에는 못 닿는다).
- 119 쪽: wg0 의 66 상대 `AllowedIPs` 에 192.168.131.0/24 를 더한다(위 `add-net`, T 문서 결정 6 의 119 wg0 권한 범위 안의 더하기. 2시간 30분 규칙의 마지막 변경으로 센다).

### 3-6. 터널과 관리망을 주입에서 지키는 규칙

1. 66 호스트는 S 의 어떤 실행기 대상도 아니다(1차 범위에 하이퍼바이저 실행기가 없다).
2. 실행기 인터페이스 허용 목록은 서버 4대의 업무 NIC 만. 관리 NIC, loadgen 의 NIC, 66 의 모든 인터페이스는 목록에 없고 요청되면 거절한다. 거절 시험을 둔다.
3. **설정 내용 가드(`vmhost.firewall`).** 보호 대상: 10.250.0.1 과 오가는 흐름(에이전트 보고 tcp 18090, 10.250.0.1 출발 ICMP echo 와 응답), 기본 경로(192.168.131.1), 관리 NIC 와 192.168.133.0/24. 실행기는 만든 체인의 첫 줄에 보호 흐름을 받아들이는 고정 줄을 먼저 넣고, 설정 표 항목이 보호 대상을 이름으로 들거나 보호 경로를 바꾸면 실행 전에 거절한다. 적용 직후 66 에서 그 서버 업무 주소 핑과 관리망 ssh 를 확인하고, 119 쪽 도달은 다음 ICMP 표본(30초 안)의 `sms.server.icmp_status` 로 확인한다. 어느 하나라도 실패하면 되돌리고 실패로 끝낸다. 시험은 보호 대상마다 거절 1건 이상과 첫 줄 고정 줄을 지우면 실패하는 돌연변이 시험.
4. 관리망 격리: 서버는 관리 NIC 에 기본 경로를 두지 않고(연결된 /24 하나), `ip_forward=0`, 관리 NIC input 은 192.168.133.1 출발 tcp 22 와 chrony 응답만 허용(T 문서 §3-5 규칙 4 의 서버 쪽과 같다).
5. 모든 주입에 U8 가드.

### 5-3. T 와 S 가 함께 ClickHouse 3.6GiB 안에 드는가

**든다. 예상 최댓값 약 3.32~3.33GiB, 최악 약 3.45~3.46GiB**(11-16 T 에서 DPM 을 빼고 다시 셈, T 문서 Q8 과 같은 값). 다만 최악 여유가 0.14GiB 로 좁아 ST3 등록 뒤 24시간 실측으로 판정한다.

추정 방법: ClickHouse 메모리 최댓값은 쓰기 양에 비례하지 않고, 큰 병합과 큰 질의가 겹칠 때 생긴다. 지난 24시간의 큰 것(조회)은 다음과 같다.

| 큰 메모리 작업(24시간) | 최댓값 | T, S 와의 관계 |
|---|---|---|
| `system.metric_log` 병합 | 1.28GiB | 무관(시스템 로그) |
| 캡처의 `SELECT * FROM lucida_logs_local` 구간 읽기 | 640.78MiB | 거의 무관(T, S 가 더하는 로그 감시 줄은 하루 수천 행, 앱 로그는 하루 184만 행) |
| 캡처의 `SELECT * FROM otel_traces_local` | 576.51MiB | 무관(T, S 는 트레이스 없음) |
| `agg_metric_rollup_1d` 적재 | 480.12MiB | 계열 수에 비례(가정) |
| `agg_metric_rollup_1h` 적재(하루 144번) | 265.10MiB | 계열 수에 비례(가정) |
| `process_snapshot` 병합 | 상위 10 밖(107.65MiB 미만) | 행 수에 비례(가정) |

T 와 S 가 더하는 비율:

- 지표 집계 행: SMS 서버 8대(T 4, S 4)가 지금 SMS 몫(4대, 8.9%)의 두 배인 17.8% 를 더하고, T 의 라우터 NMS 가 많아야 약 2%(활성 계열이 서버 한 대와 비슷하고 프로세스 계열 교체가 없다, 추정)를 더한다. T 에는 DPM 이 없다(11-16, 처음 판은 T 의 DPM 인스턴스 몫 약 2% 를 넣었다). 합계 약 +17.8~19.8%.
- `process_snapshot` 행: 지금 하루 2,551,106행(시간당 약 106,000). T 와 S 가 시간당 약 34,000 씩 더해 +64%.

최악(모든 증가분이 지난 최댓값과 같은 순간에 겹친다고 둠): 3.24GiB + 집계 1d 85~95MiB(480 × 0.178~0.198) + 집계 1h 47~52MiB(265 × 0.178~0.198) + `process_snapshot` 병합 69MiB(107 × 0.64) + 그 밖 10MiB = 약 3.45~3.46GiB.

보통(가장 큰 증가분 하나만 겹침, 집계 1d): 약 3.32~3.33GiB. S 만 더하면 최악 약 3.35GiB, T 만 더하면 최악 약 3.36GiB(T 문서 §3-6).

가정: 집계 적재와 병합의 메모리가 행 수에 비례한다. 이 가정이 틀리면 수치가 바뀌므로 ST3 의 부담 판정은 추정이 아니라 등록 전 24시간과 등록 뒤 24시간의 같은 질의(`system.asynchronous_metric_log` 의 `MemoryResident` 하루 최댓값)로 한다.

지금 실제 상한은 7.2GiB 라 3.6GiB 예산을 넘어도 ClickHouse 가 바로 거절하지는 않는다. 3.6GiB 를 예산으로 남기자는 것이 결정 6 이다. 이유는 119 노드 메모리(가용 약 10GiB, 스왑 없음, PostgreSQL 6.4GiB)와 10-31 정지 선례다.

### 5-4. 디스크와 그 밖

- S 가 더하는 디스크: `process_snapshot` 하루 약 22MB, 지표 집계 하루 약 28MB 등 하루 0.1GB 안팎(지금 두 표의 하루 신규 크기 69MB, 319MB 에서 비례). 보존 기간(프로세스, 연결 7일)을 생각하면 무시할 크기다.
- 그러나 119 디스크는 이미 75% 이고 6일에 9%p 늘었다. ClickHouse 에서 `system` 데이터베이스가 135.45GiB(그중 옛 `text_log_0` 87.95GiB), `lucida` 데이터는 5.04GiB 다. 80% 상한(T 문서 Q8, 이 문서 Q8)에 먼저 닿게 하는 것은 T, S 가 아니라 시스템 로그 증가다. 등록 전에 이 문제가 정리되지 않으면 T3, ST3 가 디스크 조건으로 막힌다(§14-5).
- VictoriaMetrics: 파드 1.68GiB / 4Gi. T 와 S 가 활성 계열을 약 +4,400~6,400(지금 20,706 의 21~31%) 더한다. Q8 의 VictoriaMetrics 기준은 한도의 80%(4Gi 면 3.2GiB) 미만이다.

## 8. 시나리오 범위

- 변경 원인과 변경이 아닌 원인 모두 만들 수 있다. 쏠림은 M1, M2 측정으로만 다룬다.
- 생성 입력은 T 와 같다: 원칙 1~9, 분류 장부 숫자, ST3, ST4 가 만드는 "수단별로 119 에 실제로 남는 흔적" 표. 이 문서와 스킬에 시나리오 예시를 쓰지 않는다.
- **S 에서 성립하는 근거 원천**: SMS 서버 지표(CPU, 메모리, 디스크 용량과 IO, 파일 시스템, NIC), 프로세스 표본(이름, 사용자, pid, 시작 시각, 자원), 프로세스 지표(상위 프로세스, pid 별), 연결 표본, 로그 감시 줄(감시 패턴에 맞는 줄만), ICMP 상태와 RTT, 가용성(UP, DOWN, UNKNOWN), SMS 구성 변경 이벤트(`config`, `inventory`), change-detect 이벤트(§4).
- **S 에서 성립하지 않는 근거**: 트레이스, APM 지표, 앱 로그 전수(로그 감시는 패턴에 맞는 줄만 온다), DPM 세션과 Top SQL, NMS 장비 지표와 trap, syslog, 쿠버네티스 이벤트와 파드 상태.
- **S 에서 원칙 3~7 이 서는 장애 부류**: 원인과 계기가 서버 위에 있고, 그 흔적이 위 원천에 남는 것. 원인 위치로 나누면 서버 자원, 서버 위 서비스 프로세스의 상태 변화, 서버 위 설정과 파일의 운영자 변경, 서버 사이 연결(호스트 방화벽, 연결 고갈), 서버 도달성(ICMP 와 가용성으로 가르는 것)이다. DB 쪽 원인은 DB 서버의 지표, 프로세스, 서버 로그 감시 줄로 원인이 설 때만 쓴다(원칙 5).
- **T 와 겹치는 것**: 위 부류는 모두 T 에서도 만들 수 있다. 서버 ICMP 상태와 RTT 는 T 에서도 켬이다(T 문서 §4-1, 11-17). 쌍은 이 겹침 안에서만 생긴다(§2-4 조건 6, 7).
- **S 에만 맞는 것**: 장애 부류로는 없다(같은 서버, 같은 앱). S 에만 있는 것은 "같은 장애를 더 적은 데이터로"라는 평가 조건이다. T 정답지가 NMS 장비 지표, trap, syslog 근거에 기대는 장애(T 에 DPM 은 없다, 11-16)는 S 쪽 정답지가 원칙 5 를 만족하는지 따로 판정하고, 만족하지 않으면 S 에서 만들지 않는다. 서버 ICMP 상태와 RTT 는 두 테스트베드 모두에 있으므로 그 근거만으로 쌍에서 빠지지는 않는다(§2-4 조건 6).
- U7 의 평시 배포와 미끼 배포를 S 에도 넣는다(`vm.service`). 넣지 않으면 "배포가 보이면 범인" 지름길이 S 에 생긴다.
- 정답 대상은 SMS 서버와 그 하위(NIC, 파일 시스템, 프로세스)의 대상 번호로만 적는다.
- 수단이 배포되지 않은 형식의 후보는 커밋하지 않는다. 실행기는 ST4 시험 실행을 통과한 것부터 생성 스킬에 알리고, 흔적 표는 실측대로 적는다(흔적이 없으면 "흔적 없음").

## 9. 녹화 구조

- T 와 같다(같은 캡처, 폴더 이름 규칙 `-v4-`, 같은 표, 같은 meta 항목, 같은 정답지 형식). 바뀌는 값은 `domain` 하나다.
- 녹화는 시간 구간 기준이라 같은 구간의 다른 도메인(기존 3개, T) 평시 데이터가 함께 담긴다. S 평시도 다른 도메인 녹화에 들어간다. S 등록은 평시 모양을 바꾸는 변경이라 그 뒤 2시간 30분 녹화 시작을 막는다.
- 쌍 녹화는 각각 따로 녹화한다(동시 녹화 안 함). 쌍 표시는 녹화본에 하지 않는다(원칙 8). 쌍 관계는 시나리오 등록 정보(생성 스킬이 정하는 자리)와 러너 실행 기록에만 둔다.
- 골든 상태: T 와 같다. 실행마다 VM 스냅숏으로 되돌리지 않고, ST2 끝에 5대 Proxmox 스냅숏을 하나 떠서 재해 복구용으로만 쓴다.

2. **T 문서 §13-4 의 답.** `sms.server.rtt` 가 .57 하나에서만 나오는 것은 등록 옵션이 아니라 도달성 때문이다(RTT 프로버는 도달하고 RTT 를 읽었을 때만 적재한다). T 터널이 서고 대상 주소가 업무 주소면 T 대상에도 나올 것이다.
3. **T 의 syslog 대상 매칭.** collector-syslog 는 출발지 IP 와 `targets.address` 가 같아야 등록 대상으로 본다. T 는 syslog 를 보내므로 T3 에 "syslog `registered=1`, 출발지 = 대상 주소" 확인을 더해야 한다. 라우터는 NMS 대상 주소(192.168.123.254)로 보내는지도 본다.
4. **ClickHouse 상한 변경.** 파드 상한이 4Gi 에서 8Gi 로 바뀌었다(11-10). T 문서 §3-6 과 Q8 의 3.6GiB 는 옛 상한 기준이었다. (11-16 닫힘) T 문서도 결정 6 과 같은 기준(`MemoryResident` 하루 최댓값 3.6GiB 예산)으로 고쳤다(T1b).
5. **119 디스크 75%.** 6일에 9%p 늘었다. ClickHouse `system` 135.45GiB(옛 `text_log_0` 87.95GiB), 최근 6일 시스템 로그 증가 약 17GiB. 80% 에 닿으면 T3, ST3 가 막힌다. 정리 여부와 방법은 119 운영 결정이다.
6. **T 문서 Q8 "삽입 행 시간당 150,000" 의 정의.** 지표 집계 표의 재삽입을 세면 SMS 서버 4대만으로 시간당 약 200,000 이다. 원천 표만 세는지 정해야 T3 판정이 선다. 이 문서는 원천 표만 센다(Q8). (11-17 닫힘) 두 문서 모두 삽입 행을 판정이 아니라 참고 측정으로 바꿨다(검토 세션 답, 자원 예산 하나로 판정).
7. **에이전트 판.** 대표 IP 를 서버 경로로 구하는 규칙은 develop-ai `agent/sms/goagent/inventory.go` 기준이다. 119 가 배포하는 에이전트 판이 이 규칙을 갖는지 ST3 에서 확인한다(옛 판은 기본 경로 주소를 낸다. S 는 기본 경로도 업무 NIC 라 어느 쪽이든 업무 주소가 나와야 한다).
8. **dbsvr01 프로세스 계열.** PostgreSQL 자동 vacuum 작업자와 배치가 pid 를 바꾸는 정도가 하루 고유 계열을 정한다. ST3 에서 참고 측정으로 잰다. 계열 수 상한은 두지 않으므로(11-17 검토 세션 답) 판정은 Q8 자원 예산이다.
9. **T2 브리프.** §2-3 의 변수화 요구가 T2 브리프에 들어가야 재사용이 선다. 지휘 세션 몫.
10. **66 vCPU 할당 104%.** 실행 중 VM 할당이 24 → 50(48스레드)이 된다. PLAN 의 "할당 26" 은 템플릿 9000 의 2 를 더한 값이다. 실측 사용은 약 16% 라 넘침이 실제 경합이 될지는 ST2 2× 시험으로 본다.
