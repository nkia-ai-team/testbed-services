# 장애 시나리오 설계 원칙과 자동화 점검표

## 0. 목적과 범위

RCA 평가용 시나리오가 100개 넘게 필요하다. 사람이 한 건씩 검토할 수 없으므로,
시나리오 작성 하네스(스킬)와 테스트베드 운영 에이전트가 **이 문서만 보고** 설계하고
스스로 판정할 수 있어야 한다.

- 이 문서는 2026-10-07~08 시나리오 설계 검토에서 나온 결정을 원칙으로 옮긴 것이다.
- [10게이트 품질 헌장](spec-scenario-quality-charter.md)을 대체하지 않는다. 헌장은 "편입 자격"을,
  이 문서는 "설계할 때 무엇을 먼저 확인하고 무엇을 정답으로 삼는가"를 정한다.
  둘이 충돌하면 이 문서가 더 최근의 결정이다.
- 현실 근거 자료: [실제 운영 장애 사례와 원인 분포](ref-real-world-incidents.md).

## 1. 한눈에 보는 원칙

| # | 원칙 | 확인 방법 |
|---|---|---|
| 1 | 정답 원인과 전파 단계마다 흔적이 **lucida-next가 실제로 수집하는 데이터**에 남아야 한다 | 119 실데이터 조회로 확인. 문서나 코드로 추정하지 않는다 |
| 2 | **계기(트리거)에도 원인의 흔적**이 있어야 한다. 이유 없는 인공 지연은 금지 | 주입이 만든 현상이 이벤트, 로그, 상태 변화로 남는지 조회 |
| 3 | 정답은 **관제 AI가 관제 데이터로 낼 수 있는 결론**이어야 한다 | 코드 설계 결함 추론이 필요한 결론을 정답으로 두지 않는다 |
| 4 | 근본 원인은 **증상을 낸 곳이 아니라 그것을 일으킨 잘못된 명령이나 로직**이다 | 정답지 세 칸(근본, 계기, 부분 점수)을 원칙대로 채운다 |
| 5 | 인시던트는 **겉 증상으로 실제로 생겨야** 한다. 감지, 피해 판정, RCA를 구분한다 | 시험 실행에서 이벤트, 군집, 인시던트 생성 확인 |
| 6 | 기전마다 **현실 근거**(공개 포스트모템, 실증 연구)가 있어야 한다 | `ref-real-world-incidents.md`의 기전 번호 인용 |
| 7 | **도메인과 원인 범주가 균형**을 이뤄야 한다 | §4 균형 규칙으로 계산 |
| 8 | 녹화는 **구간 안 모든 데이터**, 정답 표시는 하지 않는다, 주입 도구의 인공 흔적은 막는다 | 녹화본 구조 비교, 누설 검사 |
| 9 | 강도와 부하는 **테스트베드 한계 안에서 실제 피해가 나는 값**이어야 한다 | 부하 상한 계산, 시험 실행 실측 |

## 2. 원칙 상세

### 원칙 1. 관제 데이터 폐포

"데이터로 녹화되지 않으면 세상 어떤 천재가 와도 맞출 수 없다."

- 정답 원인, 계기, 전파의 각 단계, 피해의 흔적이 **119(테스트베드 관측 서버)에 실제로 쌓이는지**
  설계 단계에서 조회로 확인한다. "이 서비스는 OTel이 붙어 있으니 남을 것이다" 같은 추정은 확인이 아니다.
- 확인은 평시 데이터로 하고(같은 경로의 평시 기록이 있는지), 장애 시 형태는 시험 실행에서 다시 확인한다.

**수집 특성 (119, 2026.08.26-01 기준, 2026-10-07 실측)**

| 데이터 | 수집 정도 | 설계에 주는 의미 |
|---|---|---|
| 트레이스 (CH `otel_traces_local`) | **10% 표본.** 119 수집기 `LUCIDA_TRACE_SAMPLE_PCT: "10"`(제품 기본값). 앱과 109 중계기에는 샘플링 없음 | 몇 건의 요청에서만 생기는 증거는 트레이스에 거의 안 남는다. 트레이스만으로 증명하는 시나리오는 불합격 |
| APM 지표 (VM `apm.agent.otel.java.*`: rps, error_rate, percentile95, span_count) | 표본 스팬에서 계산, **서비스 단위**(경로, 호출자 구분 없음) | 추세 신호로만 쓴다. 경로별 건수 비교 같은 증명에 못 쓴다 |
| 로그 (CH `lucida_logs_local`) | **전수**, `trace_id` 포함. 은행 이체 741건 대 account 이체 로그 738건 대 api 접수 로그 742건 | 소수 요청의 증거는 로그로 잡는다. 앱이 그 지점에서 로그를 남기는지 코드와 실데이터로 확인 |
| 앱 DB의 업무 데이터 (이체 행, 주문 행 등) | **수집되지 않음.** DPM은 세션과 Top SQL만 | 업무 데이터 이상(중복, 불일치)은 러너가 판정할 수는 있어도 lucida-next 데이터로는 직접 보이지 않는다 |
| 쿠버네티스 이벤트, 파드 상태, 호스트 지표, syslog | 수집 중(`kcm_events_local`, `syslog_local`, VM 호스트 지표) | 수집 범위와 지연은 시나리오마다 실데이터로 확인 |

이 표는 제품 버전이 바뀌면 다시 실측한다(특히 119 패치 뒤).

### 원칙 2. 계기에도 흔적이 있어야 한다

현실의 장애에는 늘 이유가 있고, 관제 AI가 배워야 할 것은 그 이유를 찾는 일이다.

- 금지: 흔적 없이 "그냥 느려지게" 만드는 주입(요청 앞 sleep 같은 응답 지연 필터)을 계기로 쓰는 시나리오.
  관제 데이터로는 "느렸다, 이유는 모름"까지만 갈 수 있다.
- 허용: 현실에서 느려지거나 실패하는 **이유 자체**를 일으키는 주입. 설정 변경 배포, 잘못된 버전 롤아웃,
  자원 고갈, 의존 서비스 장애, 브로커나 캐시 정지, 데이터 이상 등. 그 이유가 이벤트, 로그, 상태 변화로 남아야 한다.
- 응답 지연 필터(`response_delay_control`)는 "원인 위치를 찾는 능력"만 보는 시나리오에 한해,
  정답이 지연 지점 자체일 때만 쓸 수 있다.

### 원칙 3. 정답은 관제 AI의 일 범위 안

관제 AI의 일은 **탐지하고, 위치를 찾고, 관제 데이터로 원인을 설명하는 것**이다.

- 정답이 코드 설계 결함(비멱등 재시도, 경쟁 조건 등)을 추론해야 나오는 결론이면, 그 시나리오는
  관제 AI 개선용으로 부적합하다. 사람이 포스트모템에서 며칠 걸려 내는 결론이다.
- 관제 데이터로 합리적인 AI가 낼 답을 부분 점수나 오답으로 처리하는 정답지를 만들지 않는다.
  학습이나 평가가 AI를 엉뚱한 방향으로 민다.
- 코드 결함이 피해를 키운 경우, 그 결함은 정답이 아니라 **피해 설명**(user_impact)에 적는다.

### 원칙 4. 원인 규정

장애가 A → B → C로 전파됐을 때:

- 요청 A가 B를 실행시켰고 C라는 증상이 났다면, **C를 낸 B가 아니라 B를 실행시킨 잘못된 명령 A**가 원인이다.
- 단, A 자체가 정당한 요청이었고 B의 로직이 잘못돼 있었다면 **B가 원인**이다.
- 정답지에는 세 칸으로 나눠 적는다(헌장 G7).
  - `root_cause.target_id`: 결함을 가진 곳, 고쳐야 재발이 막히는 곳
  - `root_cause.trigger_target_id`: 결함을 드러나게 한 사건이 난 곳(근본과 같으면 비운다)
  - `scoring.partial`: 원인 근처지만 정답이 아닌 답(증상 서비스, 계기만 본 답)
- 정답(`meta.json`의 시나리오 정답)은 시나리오 작성자가 적는다. 제품이 만든 인시던트나 RCA 결과는 정답이 아니다.

### 원칙 5. 감지, 피해 판정, RCA를 구분한다

| 층 | 누가 | 무엇으로 | 요구 |
|---|---|---|---|
| 감지 | lucida-next 이상 탐지 | 겉 증상(오류율, 지연, 오류 로그 급증, 상태 변화) | 별도 업무 규칙 없이 이벤트가 생기고 **인시던트까지 실제로 만들어져야** 한다 |
| 피해 판정 | 러너(우리) | 테스트베드 DB나 앱을 직접 조회 | 평시 0 근처이고 장애 시 확실히 오르는 값 |
| 원인 설명 | RCA | 녹화된 데이터 | 원칙 1~3을 만족하는 증거 경로 |

감지가 안 되는 장애(조용한 장애)는 헌장이 요구하는 유형이지만, 그 경우에도 원칙 1~3은 그대로 적용한다.

### 원칙 6. 현실 근거

- 기전마다 `ref-real-world-incidents.md`의 기전 번호(M1~M23)와 사례 하나 이상을 설계 시트에 인용한다.
- 신규 시나리오는 현실 분포를 따라간다. 실증 연구 기준 가장 흔한 원인은 **변경(배포, 설정)**이다.
  DB 잠금은 어느 연구에서도 상위 원인이 아니다.

### 원칙 7. 균형

**도메인 균형** (근본 원인이 속한 도메인 기준, `scenario-metadata.json`의 `domain`)

- 목표는 commerce, core-banking, food-delivery **1:1:1**.
- 2026-10-08 ready 39종: **commerce 25, core-banking 9, food-delivery 5.**
- 규칙: 신규 시나리오는 **가장 적은 도메인부터** 채운다. 세 도메인 차이가 ready 기준 3개 이내가 될 때까지
  commerce에는 새 시나리오를 더하지 않는다(예외: 도메인 간 전파 시나리오에서 근본이 commerce인 경우, 사유 기록).
- 같은 기전을 다른 도메인에 옮기는 것(R 변형)은 균형을 맞추는 좋은 수단이다. 단 서비스 이름만 바꾼 복제는
  금지(카탈로그 §1). DB 엔진, 진입 경로, 영향 범위, 노이즈 중 하나 이상이 달라야 한다.
- **새 서비스(도메인) 추가**는 기존 세 도메인으로 아이디어가 고갈됐거나, 특정 구조에서만 일어나는 장애를
  설계할 때만 한다. 그 외에는 늘리지 않는다.

**원인 범주 균형**

- 한 원인 범주가 ready의 **20%를 넘지 않게** 한다. DB 잠금 계열은 2026-10-08 기준 8/39(21%)라 추가하지 않는다.
- 빈 범주를 우선 채운다. 2026-10-08 기준 ready 0개 범주: 설정 오배포(1개뿐), 잘못된 버전 배포,
  네트워크 지연과 손실, DNS, 메시지 처리 막힘, Kafka 브로커 장애, 재시도 폭주, 메타스테이블 장애.
- 재현 불가 범주(TLS 없음, 멀티 AZ 없음, 시계 조작은 관측 오염)는 테스트베드 구조가 바뀌기 전까지 제외한다.

### 원칙 8. 녹화

- 녹화 구간(정상 2시간 + 장애 + 식힘 30분) 안의 데이터를 PG, CH, VM의 **모든 표**에서 담는다.
  필요 없는 것은 쓰는 쪽이 뺀다.
- 표나 데이터에 "정답" 표시를 하지 않는다. 정답은 `meta.json` 하나뿐이다.
- 주입 도구가 데이터에 남기는 **인공 흔적**(세션 태그, 실행 번호, 프로세스 이름에 시나리오 id 등)은
  주입 설계에서 막는다(헌장 G6). 현실 장애에는 없는 흔적이기 때문이다.

### 원칙 9. 강도와 부하

- 가장 자주 떨어지는 게이트는 G3(피해 실재)다. 설계 전에 부하 상한(target_rps 최대 180),
  타임아웃 사슬, 서킷브레이커 동작으로 피해가 실제로 나는지 계산한다.
- 강도는 시험 실행(calibration)에서 정하고 승인 고정값 하나로 둔다.

## 3. 설계 절차와 단계별 관문

하네스는 각 단계의 관문을 통과해야 다음 단계로 간다. 관문에서 막히면 **폐기 또는 재설계**하고 사유를 남긴다.

| 단계 | 할 일 | 관문 (하나라도 아니오면 중단) |
|---|---|---|
| 1. 후보 | 빈 도메인, 빈 범주에서 후보를 고른다 | 원칙 7 균형 규칙을 어기지 않는가 |
| 2. 현실 근거 | 기전 번호와 사례를 붙인다 | 원칙 6 출처가 있는가 |
| 3. 코드와 인프라 실측 | 결함이나 원인 지점을 `file:line`으로 확인 | 헌장 G1, G2 |
| 4. 관측 실측 | 근본, 계기, 전파 단계, 피해의 흔적을 119 실데이터로 조회 | 원칙 1, 2. 표본 데이터(트레이스, APM 지표)에만 의존하지 않는가 |
| 5. 원인 규정 | 정답지 세 칸 작성 | 원칙 3, 4. 합리적 관제 답을 오답 처리하지 않는가 |
| 6. 감별 | must_support, must_rule_out, contrast_with | 헌장 G5, G10 |
| 7. 설계 시트 | `docs/scenario-redesign-wip/design-<ID>-sheet.md` + 정답지 초안 | 이 문서 §5 점검표 전부 예 |
| 8. 등록과 배포 | 장부, manifest, 검사, 109 배포 | 저장소 검사 4종 통과 |
| 9. 시험 실행 | calibration으로 강도 결정 | 원칙 5(인시던트 실제 생성), 원칙 9(피해 실측) |
| 10. 녹화와 검증 | dataset 녹화, 누설 검사, 관측 재확인 | 원칙 1 증거가 녹화본에 실제로 있는가 |

**사람 검토가 필요한 경우만**: 새 패턴(P 번호) 신설, 새 도메인 추가, 원인 규정이 원칙 4로 결정되지 않을 때,
균형 규칙 예외, 테스트베드 앱 코드 변경이 필요할 때.

## 4. 균형 계산 (하네스용)

1. `catalog.json`에서 readiness가 ready인 id를 모은다.
2. 각 id의 `scenario-metadata.json` `domain`(근본 도메인)과 원인 범주(카탈로그 분류)를 센다.
3. 신규 후보의 도메인이 현재 최다 도메인이고 최소 도메인과 차이가 3을 넘으면 거절한다.
4. 신규 후보의 원인 범주가 ready의 20% 이상이면 거절한다.

## 5. 설계 시트 점검표 (전부 예여야 함)

- [ ] 현실 근거 기전 번호와 사례 링크가 있다 (원칙 6)
- [ ] 근본 원인 위치가 `file:line` 또는 인프라 지점으로 확인됐다 (G1)
- [ ] 근본 원인의 흔적이 119 실데이터에서 조회됐다. 어느 표, 어느 칸인지 적었다 (원칙 1)
- [ ] 계기의 흔적이 조회됐다. 이유 없는 인공 지연을 쓰지 않는다 (원칙 2)
- [ ] 핵심 증거가 표본 데이터(트레이스 10%, APM 지표)에만 있지 않다 (원칙 1)
- [ ] 정답이 관제 데이터로 낼 수 있는 결론이다. 코드 설계 결함 추론이 필요하지 않다 (원칙 3)
- [ ] 정답지 세 칸이 원칙 4대로 채워졌다
- [ ] 감지, 피해 판정, RCA 증거가 각각 적혀 있다 (원칙 5)
- [ ] 도메인과 원인 범주 균형 규칙을 통과한다 (원칙 7)
- [ ] 주입 도구가 데이터에 시나리오 id를 남기지 않는다 (원칙 8)
- [ ] 부하 상한과 서킷브레이커를 고려해 피해가 실제로 날 계산이 있다 (원칙 9)

## 6. 사례: F29-R 보류 (원칙 2, 3 위반)

2026-10-07 설계한 F29-R(은행 이체 재시도 중복)은 진짜 코드 결함이었지만 보류했다.
설계 시트: `docs/scenario-redesign-wip/design-F29-R-sheet.md`(브랜치 `design/f29-r-retry-duplicate-transfer`).

- 결함: 은행 api가 account를 10초만 기다리고 비멱등 이체를 3번까지 재시도. account는 15초를 기다려
  api가 포기한 시도도 끝까지 이체한다. 손님은 502를 받고 돈은 최대 3번 빠진다.
- **원칙 2 위반**: 계기를 응답 지연 필터(요청 앞 10초 sleep)로 만들었다. account가 느린 이유가 관제 데이터에 없다.
- **원칙 3 위반**: 정답 "api 재시도 규칙이 중복 이체를 만들었다"는 로그를 trace_id로 서비스 간에 엮고
  건수를 맞춰 설계 결함을 추론해야 나온다. 관제 AI의 합리적 답("account 지연이 api 502로 번졌다")이
  부분 점수로 깎인다.
- **원칙 1 함정 발견**: 처음에는 트레이스를 핵심 증거로 잡았으나 트레이스가 10% 표본이라 거의 녹화되지 않는다.
  로그는 전수라 증거 자체는 남는다.
- 다시 쓰려면: 계기를 흔적이 남는 현실 원인(예: account DB 커넥션 고갈)으로 바꾸고, 그 원인을 정답으로,
  재시도 중복은 피해 설명으로 둔다.
