# 장애 시나리오 설계 원칙과 자동화 점검표

## 0. 목적과 범위

관제 AI를 개선하는 데 가장 좋은 데이터는 **실제 장애 사례**다. 하지만 lucida-next 시점에서 녹화된
실제 장애는 없다. 그래서 테스트베드에서 **실제로 일어난, 또는 일어날 수 있는 장애를 재구성해**
장애 데이터를 쌓는다. 시나리오는 상상한 장애가 아니라 현실 장애의 재현이어야 한다.

RCA 평가용 시나리오가 100개 넘게 필요하고, 사람이 한 건씩 검토할 수 없다. 시나리오 작성
하네스(스킬)와 테스트베드 운영 에이전트가 **이 문서만 보고** 설계하고 스스로 판정할 수 있어야 한다.

- 이 문서는 2026-10-07~08 시나리오 설계 검토에서 나온 결정을 원칙으로 옮긴 것이다.
- [10게이트 품질 헌장](spec-scenario-quality-charter.md)을 대체하지 않는다. 헌장은 "편입 자격"을,
  이 문서는 "무엇을 골라 어떻게 재구성하고 무엇을 정답으로 삼는가"를 정한다.
  둘이 충돌하면 이 문서가 더 최근의 결정이다.
- 현실 근거 자료: [실제 운영 장애 사례와 원인 분포](ref-real-world-incidents.md).

## 1. 한눈에 보는 원칙

| # | 원칙 | 확인 방법 |
|---|---|---|
| 1 | 시나리오는 **실제로 보고된 장애 사례의 재구성**이다 | 설계 시트에 원본 사례(기업, 날짜, 링크)와 요소별 대응표 |
| 2 | 무엇을 만들지는 **숫자로 정한다**. 비슷한 장애가 이미 많으면 피하고 **없던 장애를 우선**한다 | 분류 장부(`ref-scenario-similarity-ledger.md`)의 묶음별, 서비스별 숫자 |
| 3 | 정답 원인과 전파 단계마다 흔적이 **lucida-next가 실제로 수집하는 데이터**에 남아야 한다 | 119 실데이터 조회. 문서나 코드로 추정하지 않는다 |
| 4 | **계기(트리거)에도 원인의 흔적**이 있어야 한다. 이유 없는 인공 지연은 금지 | 주입이 만든 현상이 이벤트, 로그, 상태 변화로 남는지 조회 |
| 5 | 정답은 **관제 AI가 관제 데이터로 낼 수 있는 결론**이어야 한다 | 코드 설계 결함 추론이 필요한 결론을 정답으로 두지 않는다 |
| 6 | 근본 원인은 **증상을 낸 곳이 아니라 그것을 일으킨 잘못된 명령이나 로직**이다 | 정답지 세 칸(근본, 계기, 부분 점수)을 원칙대로 채운다 |
| 7 | 인시던트는 **겉 증상으로 실제로 생겨야** 한다. 감지, 피해 판정, RCA를 구분한다 | 시험 실행에서 이벤트, 군집, 인시던트 생성 확인 |
| 8 | 녹화는 **구간 안 모든 데이터**, 정답 표시는 하지 않는다, 주입 도구의 인공 흔적은 막는다 | 녹화본 구조 비교, 누설 검사 |
| 9 | 강도와 부하는 **테스트베드 한계 안에서 실제 피해가 나는 값**이어야 한다 | 부하 상한 계산, 시험 실행 실측 |

## 2. 원칙 상세

### 원칙 1. 실제 장애 사례의 재구성

- 시나리오마다 **원본 사례**를 하나 정한다. 공개 포스트모템, 공식 상태 보고, 실증 연구에 나온 사례다
  (`ref-real-world-incidents.md`의 기전 번호 M1~M23과 사례, 또는 새로 찾은 공신력 있는 사례를 그 문서에 추가한 뒤).
- 설계 시트에 **요소별 대응표**를 둔다. 원본 사례의 각 요소가 테스트베드에서 무엇이 되는지 적는다.

| 요소 | 원본 사례 | 테스트베드 재구성 |
|---|---|---|
| 촉발 계기 | 예: 빈 필드가 든 정책 배포 | 예: 음식배달 주문 서비스에 필수 설정이 빠진 배포 |
| 원인이 된 결함 | | |
| 전파 경로 | | |
| 사용자 증상 | | |
| 탐지된 경로(원본에서 어떻게 알았나) | | |
| 완화와 복구 | | |

- **기전이 바뀌면 재구성이 아니다.** 우리 스택(Spring Boot, PostgreSQL, MySQL, Oracle, Kafka, Redis,
  Kubernetes)에 맞게 대상과 규모를 바꾸는 것은 괜찮지만, 원인에서 증상까지 이어지는 고리가 원본과 같아야 한다.
- 원본 사례를 못 찾는 기전은 우선순위를 낮춘다. 코드에 결함이 있다는 사실만으로 시나리오를 만들지 않는다.

### 원칙 2. 숫자로 정하고, 비슷한 장애가 쌓이지 않게 하고, 없던 장애를 우선한다

비슷한 장애가 반복되면 데이터가 한쪽에 몰린다. 처음 테스트베드를 만들 때의 장애(부품 다운 같은 것)에
끌려 비슷한 시나리오가 계속 나오는 것을 막기 위해, **후보를 고르기 전에 항상 숫자로 센다.**

- **비슷한 장애끼리 묶어서 센다.** 묶음은 [시나리오 유사 장애 분류 장부](ref-scenario-similarity-ledger.md)에
  기록돼 있다. 하네스는 매번 처음부터 묶지 않고, 장부를 읽은 뒤 **새로 생기거나 상태가 바뀐 시나리오만** 분류해
  장부를 갱신한다. 예를 들어 "Redis 다운"과 "Kafka 브로커 다운"은 둘 다 "부품 멈춤" 묶음이다.
  정답지에 새 칸을 만들지 않는다.
- **후보도 같은 방식으로 견준다.** 후보가 어느 묶음에 들어가는지, 그 묶음이 이미 몇 개인지 적는다.
- **없던 장애가 최우선이다.** 어느 묶음에도 들어가지 않는 후보가 가장 좋다.
- **현실과 견준다.** `ref-real-world-incidents.md` §1에서 현실에 흔한 장애인데 우리에게 적은 것을 우선한다.
- **고를 때는 정식 + 후보 합계로 센다.** 정식은 eval-cases 에 정상 녹화가 1개 이상 있는 시나리오, 후보는 등록됐지만 아직 녹화 전인 시나리오다([수명주기](spec-scenario-lifecycle.md)). 녹화보다 설계가 빨라 후보가 쌓이므로, 정식만 세면 같은 묶음에 후보가 몰린다.
- **상한**: 한 묶음이 (정식 + 후보)의 20%에 닿으면 그 묶음에는 추가하지 않는다.
- **정답 위치도 몰리지 않게 한다.** 장애 종류가 달라도 정답이 늘 같은 부품(예: 결제)을 가리키면, 관제 AI 가 추론 없이 "애매하면 결제를 찍는" 지름길로 점수를 얻는다. 장부 §2-1 의 정답 위치별로 (정식 + 후보)를 세어, 한 위치가 20%에 닿으면 그 위치가 정답인 후보는 만들지 않는다. **결제 경로**(외부 결제 의존 + 결제 서비스 + 결제 테이블)는 합쳐서도 같은 상한을 둔다.
- **서비스 균형**: 쇼핑몰(commerce), 은행(core-banking), 음식배달(food-delivery)을 **1:1:1**로 맞춘다.
  "문제가 시작된 서비스" 기준이다(`scenario-metadata.json`의 `domain`). 세 서비스의 (정식 + 후보) 수 차이가 3개 이내가 될
  때까지 가장 많은 서비스에는 추가하지 않는다.
- 같은 장애를 다른 서비스에 옮기는 것(R 변형)은 균형 수단이지만, 서비스 이름만 바꾼 복제는 금지(카탈로그 §1).
- **새 서비스 추가**는 기존 세 서비스로 아이디어가 고갈됐거나, 특정 구조에서만 일어나는 장애를 설계할 때만 한다.
- 설계 시트에 그때 센 숫자와 "왜 이 후보인가"를 적는다.

### 원칙 3. 관제 데이터 폐포

"데이터로 녹화되지 않으면 세상 어떤 천재가 와도 맞출 수 없다."

- 정답 원인, 계기, 전파의 각 단계, 피해의 흔적이 **119(테스트베드 관측 서버)에 실제로 쌓이는지**
  설계 단계에서 조회로 확인한다. "OTel이 붙어 있으니 남을 것이다" 같은 추정은 확인이 아니다.
- 확인은 평시 데이터로 하고(같은 경로의 평시 기록이 있는지), 장애 시 형태는 시험 실행에서 다시 확인한다.

**수집 특성 (119, 2026.08.26-01 기준, 2026-10-07 실측)**

| 데이터 | 수집 정도 | 설계에 주는 의미 |
|---|---|---|
| 트레이스 (CH `otel_traces_local`) | **10% 표본.** 119 수집기 `LUCIDA_TRACE_SAMPLE_PCT: "10"`(제품 기본값). 앱과 109 중계기에는 샘플링 없음 | 몇 건의 요청에서만 생기는 증거는 트레이스에 거의 안 남는다. 트레이스만으로 증명하는 시나리오는 불합격 |
| APM 지표 (VM `apm.agent.otel.java.*`: rps, error_rate, percentile95, span_count) | 표본 스팬에서 계산, **서비스 단위**(경로, 호출자 구분 없음) | 추세 신호로만 쓴다. 경로별 건수 비교 같은 증명에 못 쓴다 |
| 로그 (CH `lucida_logs_local`) | **전수**, `trace_id` 포함. 은행 이체 741건 대 account 이체 로그 738건 대 api 접수 로그 742건 | 소수 요청의 증거는 로그로 잡는다. 앱이 그 지점에서 로그를 남기는지 코드와 실데이터로 확인 |
| 앱 DB의 업무 데이터 (이체 행, 주문 행 등) | **수집되지 않음.** DPM은 세션과 Top SQL만 | 업무 데이터 이상(중복, 불일치)은 러너가 판정할 수는 있어도 lucida-next 데이터로는 직접 보이지 않는다 |
| 쿠버네티스 이벤트, 파드 상태, 호스트 지표, syslog | 수집 중(`kcm_events_local`, `syslog_local`, VM 호스트 지표) | 수집 범위와 지연은 시나리오마다 실데이터로 확인 |

이 표는 제품 버전이 바뀌면 다시 실측한다(특히 119 패치 뒤).

### 원칙 4. 계기에도 흔적이 있어야 한다

현실의 장애에는 늘 이유가 있고, 관제 AI가 배워야 할 것은 그 이유를 찾는 일이다.

- 금지: 흔적 없이 "그냥 느려지게" 만드는 주입(요청 앞 sleep 같은 응답 지연 필터)을 계기로 쓰는 시나리오.
  관제 데이터로는 "느렸다, 이유는 모름"까지만 갈 수 있다.
- 허용: 현실에서 느려지거나 실패하는 **이유 자체**를 일으키는 주입. 원본 사례의 계기(설정 변경 배포,
  잘못된 버전 롤아웃, 자원 고갈, 의존 서비스 장애, 데이터 이상 등)를 그대로 재현하고, 그 흔적이
  이벤트, 로그, 상태 변화로 남아야 한다.
- 응답 지연 필터(`response_delay_control`)는 정답이 지연 지점 자체인 시나리오에서만 쓸 수 있다.

### 원칙 5. 정답은 관제 AI의 일 범위 안

관제 AI의 일은 **탐지하고, 위치를 찾고, 관제 데이터로 원인을 설명하는 것**이다.

- 정답이 코드 설계 결함(비멱등 재시도, 경쟁 조건 등)을 추론해야 나오는 결론이면 관제 AI 개선용으로
  부적합하다. 사람이 포스트모템에서 며칠 걸려 내는 결론이다.
- 관제 데이터로 합리적인 AI가 낼 답을 부분 점수나 오답으로 처리하는 정답지를 만들지 않는다.
- 코드 결함이 피해를 키운 경우, 그 결함은 정답이 아니라 **피해 설명**(user_impact)에 적는다.

### 원칙 6. 원인 규정

장애가 A → B → C로 전파됐을 때:

- 요청 A가 B를 실행시켰고 C라는 증상이 났다면, **C를 낸 B가 아니라 B를 실행시킨 잘못된 명령 A**가 원인이다.
- 단, A 자체가 정당한 요청이었고 B의 로직이 잘못돼 있었다면 **B가 원인**이다.
- 정답지에는 세 칸으로 나눠 적는다(헌장 G7).
  - `root_cause.target_id`: 결함을 가진 곳, 고쳐야 재발이 막히는 곳
  - `root_cause.trigger_target_id`: 결함을 드러나게 한 사건이 난 곳(근본과 같으면 비운다)
  - `scoring.partial`: 원인 근처지만 정답이 아닌 답(증상 서비스, 계기만 본 답)
- 원본 사례의 포스트모템이 지목한 원인과 같은 층위로 지목한다.
- 정답(`meta.json`의 시나리오 정답)은 시나리오 작성자가 적는다. 제품이 만든 인시던트나 RCA 결과는 정답이 아니다.

### 원칙 7. 감지, 피해 판정, RCA를 구분한다

| 층 | 누가 | 무엇으로 | 요구 |
|---|---|---|---|
| 감지 | lucida-next 이상 탐지 | 겉 증상(오류율, 지연, 오류 로그 급증, 상태 변화) | 별도 업무 규칙 없이 이벤트가 생기고 **인시던트까지 실제로 만들어져야** 한다 |
| 피해 판정 | 러너(우리) | 테스트베드 DB나 앱을 직접 조회 | 평시 0 근처이고 장애 시 확실히 오르는 값 |
| 원인 설명 | RCA | 녹화된 데이터 | 원칙 3~5를 만족하는 증거 경로 |

감지가 안 되는 장애(조용한 장애)는 헌장이 요구하는 유형이지만, 그 경우에도 원칙 3~5는 그대로 적용한다.

### 원칙 8. 녹화

- 녹화 구간(정상 2시간 + 장애 + 식힘 30분) 안의 데이터를 PG, CH, VM의 **모든 표**에서 담는다.
  필요 없는 것은 쓰는 쪽이 뺀다.
- 표나 데이터에 "정답" 표시를 하지 않는다. 정답은 `meta.json` 하나뿐이다.
- 주입 도구가 데이터에 남기는 **인공 흔적**(세션 태그, 실행 번호, 프로세스 이름에 시나리오 id 등)은
  주입 설계에서 막는다(헌장 G6). 현실 장애에는 없는 흔적이기 때문이다.

### 원칙 9. 강도와 부하

- 가장 자주 떨어지는 게이트는 G3(피해 실재)다. 설계 전에 부하 상한(target_rps 최대 180),
  타임아웃 사슬, 서킷브레이커 동작으로 피해가 실제로 나는지 계산한다.
- 강도는 시험 실행(calibration)에서 정하고 승인 고정값 하나로 둔다.

## 3. 설계 절차와 단계별 관문

하네스는 각 단계의 관문을 통과해야 다음 단계로 간다. 관문에서 막히면 **폐기 또는 재설계**하고 사유를 남긴다.

| 단계 | 할 일 | 관문 (하나라도 아니오면 중단) |
|---|---|---|
| 1. 숫자 세기 | 분류 장부를 읽고, 장부에 없거나 상태가 바뀐 시나리오만 분류해 갱신한다 | 피할 묶음과 우선 서비스가 숫자로 정해졌는가 (원칙 2) |
| 2. 원본 사례 | 적거나 없는 장애 중에서 공신력 있는 실제 사례를 고른다 | 원본 사례와 출처가 있는가, 우리 스택에서 같은 기전으로 일어날 수 있는가 (원칙 1) |
| 3. 대응표 | 원본 요소별 테스트베드 재구성 | 기전이 원본과 같은가 (원칙 1) |
| 4. 코드와 인프라 실측 | 원인 지점을 `file:line` 또는 인프라 지점으로 확인 | 헌장 G1, G2 |
| 5. 관측 실측 | 근본, 계기, 전파 단계, 피해의 흔적을 119 실데이터로 조회 | 원칙 3, 4. 표본 데이터(트레이스, APM 지표)에만 의존하지 않는가 |
| 6. 원인 규정 | 정답지 세 칸 작성 | 원칙 5, 6. 합리적 관제 답을 오답 처리하지 않는가 |
| 7. 감별 | must_support, must_rule_out, contrast_with | 헌장 G5, G10 |
| 8. 설계 시트 | `docs/scenario-redesign-wip/design-<ID>-sheet.md` + 정답지 초안 | §5 점검표 전부 예 |
| 9. 등록과 배포 | 장부, manifest, 검사, 109 배포 | 저장소 검사 4종 통과 |
| 10. 시험 실행 | calibration으로 강도 결정 | 원칙 7(인시던트 실제 생성), 원칙 9(피해 실측) |
| 11. 녹화와 검증 | dataset 녹화, 누설 검사, 관측 재확인 | 원칙 3 증거가 녹화본에 실제로 있는가 |

**사람 검토가 필요한 경우만**: 새 패턴(P 번호) 신설, 새 도메인 추가, 원인 규정이 원칙 6으로 결정되지 않을 때,
원칙 2의 상한이나 균형 예외, 테스트베드 앱 코드 변경이 필요할 때.

## 4. 숫자 세기

[시나리오 유사 장애 분류 장부](ref-scenario-similarity-ledger.md)가 정본이다. 묶음 정의, 집계, 시나리오별 분류,
하네스 사용법(장부 읽기 → catalog와 대조 → 바뀐 것만 분류 → 집계 갱신 → 갱신 기록)이 모두 거기 있다.

2026-10-08 장부 요약(정식 35종): 현실에서 가장 흔한 변경(결함 있는 새 버전 배포 0, 설정 오배포 2)이 적고,
데이터 형식 불일치와 DNS는 0이다. 자원 부족, 부품 멈춤, DB 잠금은 정식의 20%에 닿아 추가하지 않는다.
서비스는 쇼핑몰 23, 은행 8, 음식배달 4라 음식배달과 은행을 먼저 채운다. 정답 위치는 결제 경로가 26%(외부 결제 의존 6, 결제 서비스 2, 결제 테이블 1)로 상한을 넘어 결제 쪽 정답은 만들지 않는다.

## 5. 설계 시트 점검표 (전부 예여야 함)

- [ ] 원본 실제 사례(기업, 날짜, 링크)와 요소별 대응표가 있고, 기전이 원본과 같다 (원칙 1)
- [ ] 분류 장부를 갱신했고, 후보가 들어갈 묶음과 정답 위치, 각각의 (정식 + 후보) 수와 결제 경로 합계, 서비스별 수, 이 후보를 고른 이유를 적었다. 어느 축도 20%에 닿지 않는다 (원칙 2)
- [ ] 근본 원인 위치가 `file:line` 또는 인프라 지점으로 확인됐다 (G1)
- [ ] 근본 원인의 흔적이 119 실데이터에서 조회됐다. 어느 표, 어느 칸인지 적었다 (원칙 3)
- [ ] 핵심 증거가 표본 데이터(트레이스 10%, APM 지표)에만 있지 않다 (원칙 3)
- [ ] 계기의 흔적이 조회됐다. 이유 없는 인공 지연을 쓰지 않는다 (원칙 4)
- [ ] 정답이 관제 데이터로 낼 수 있는 결론이다. 코드 설계 결함 추론이 필요하지 않다 (원칙 5)
- [ ] 정답지 세 칸이 원칙 6대로 채워졌다
- [ ] 감지, 피해 판정, RCA 증거가 각각 적혀 있다 (원칙 7)
- [ ] 주입 도구가 데이터에 시나리오 id를 남기지 않는다 (원칙 8)
- [ ] 부하 상한과 서킷브레이커를 고려해 피해가 실제로 날 계산이 있다 (원칙 9)
