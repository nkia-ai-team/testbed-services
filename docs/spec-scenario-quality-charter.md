# RCA 평가 시나리오 품질 기준서 (v2)

## 0. 왜 개정하는가

기존 헌장(`spec-scenario-design-charter.md`)의 **골든 4조건**은 전부 *만드는 쪽* 기준이다.

| 기존 조건 | 실제로 묻는 것 |
| --- | --- |
| ① 코드/인프라 앵커 | 우리가 근거를 댈 수 있나 |
| ② 정답 작성 | 우리가 답을 적어놨나 |
| ③ 감별 가능 | 우리 러너가 성공 판정할 수 있나 |
| ④ 주입 수단 실재 | 우리가 장애를 일으킬 수 있나 |

논문용 평가 데이터셋은 *푸는 쪽*과 *채점하는 쪽* 기준이 필요하다. 4조건을 전부 통과해도 다음이 성립하지 않을 수 있다.

- 캡처된 데이터만 보고 원인에 도달할 수 있는가 (러너는 클러스터에 직접 질의하지만, RCA 시스템은 캡처 파일만 본다)
- 정답을 기계가 채점할 수 있는가
- 정답이 입력 데이터에 새어 들어가 있지 않은가
- 방법 간 차이를 드러내는가

2026-07-27 전수 재감사(`scenario-redesign-wip/golden4-audit-0727.md`)에서 60건 중 26건이 CUT됐고, 살아남은 34건도 **전건이 위 네 질문 중 최소 하나를 만족하지 못했다.** 4조건은 필요조건이지 충분조건이 아니다.

본 기준서는 4조건을 흡수·재배열하고 6개 조건을 추가한 **10게이트**를 정의한다.

## 1. 10게이트 개요

| # | 게이트 | 한 줄 |
| ---: | --- | --- |
| **A. 결함의 진정성** | | |
| G1 | 실재 앵커 | 증상 메커니즘이 실제 코드·인프라에 박혀 있다 |
| G2 | 주입 수단 실재 | executor가 껍데기가 아니라 실제로 결함을 만든다 |
| **B. 사건성** | | |
| G3 | 서비스 피해 실재 | 실측 가능한 피해가 임계치를 넘어 발생한다 |
| **C. 풀 수 있는가** | | |
| G4 | 관측 폐포 | 캡처 데이터만으로 원인 도달 경로가 존재한다 |
| G5 | 감별 가능 | 혼동 후보와 구분되는 증거가 데이터에 있다 |
| G6 | 정답 무누설 | 주입 흔적이 정답을 데이터에 노출하지 않는다 |
| **D. 채점할 수 있는가** | | |
| G7 | 기계 채점 가능 정답 | 정답 입도와 매칭 규칙이 정의돼 있다 |
| G8 | 시간축 확정 | 장애 구간 경계가 관측 데이터와 정렬된다 |
| **E. 데이터셋 위생** | | |
| G9 | 재현·격리 | 반복 시 동일 라벨, cleanup 완전, 케이스 간 무오염 |
| G10 | 변별력 | 난이도가 양극단이 아니고 감별쌍이 존재한다 |

**판정은 이분법이다. 10게이트 전부 통과해야 데이터셋에 들어간다. 중간 등급은 없다.**

> `calibration`은 품질 등급이 아니다. "주입 강도가 아직 확정되지 않았다"는 **일시적 운영 상태**만을 뜻하며, 캘리브레이션 완료 시 승격된다. 품질 미달 케이스를 담는 용도로 쓰지 않는다.

## 2. A. 결함의 진정성

### G1. 실재 앵커

증상이 나는 메커니즘이 **실제 근거**에 박혀 있어야 한다.

- **Class A (코드 결함)**: 앱 코드 `file:line` + 결함 패턴(P1~P8) 매핑
- **Class B (인프라·설정 결함)**: 인프라 지점(자원·노드·NIC·probe·설정) + 조작 수단

**금지 사항**

1. **합성 지연 금지.** 시나리오를 위해 앱 소스에 심어둔 `Thread.sleep` 등은 앵커로 인정하지 않는다.
   - 실증: F03-H — `commerce/order-service/.../OrderController.java:70`의 `Thread.sleep`. 주석이 스스로 "F03-H 주입 표면"이라 밝힌다. → CUT
2. **Class A 위장 금지.** env로 코드 동작을 인위 왜곡(풀 크기 강제 축소, timeout 임의값)한 것을 코드 결함으로 제시하지 않는다. 자연 고갈이 아니면 **Class B로 명시**하거나 폐기.
   - 실증: F03-P(Hikari 10→2), F08-P(timeout 15s→250ms), F09-H(heap 강제 축소)
3. **A/B를 섞지 않는다.** 생성 시점에 `class` 필드로 라벨링하며, 이 필드 없이는 심사를 통과할 수 없다.

**판정 방법**: 앵커로 제시된 `file:line`을 열어 해당 심볼이 실제로 존재하는지 확인. 인프라 앵커는 매니페스트/실배치와 대조.

### G2. 주입 수단 실재

executor가 inert stub이 아니라 실제로 결함을 만들어야 한다.

**확인 항목 (전부 통과해야 함)**

- executor 내부 `CONTRACTS`에 시나리오가 등록돼 있는가
- `registry/profiles.json`의 `allowed_scenarios`에 포함되는가
- 두 곳의 파라미터가 정확히 일치하는가
- BLOCKED/fail-closed 목록에 있지 않은가

> **양방향 정합성이 필수다.** 한쪽만 있으면 실행 즉시 실패한다.
> 실증: F21-P/Q — registry에는 등록됐으나 executor `CONTRACTS`에 없어 `ExecutorError` 즉시 발생.
> 역방향: `host.stress`는 `build_invocation`이 빈 profile을 넘겨 registry allowlist를 아예 검증하지 않는다.

**CI 강제**: `test-scenarios.sh`에 executor CONTRACTS ↔ registry allowlist 교차 검증을 추가한다.

## 3. B. 사건성

### G3. 서비스 피해 실재

**실측 가능한 피해가 임계치를 넘어 발생해야 한다.** 피해는 다음 둘 중 **하나 이상**이며, 시나리오마다 임계치를 명시한다.

| 피해 유형 | 지표 예 | 성격 |
| --- | --- | --- |
| **가용성·성능 저하** | 오류율, p95 지연, 처리량 저하 | 사용자 체감 |
| **비즈니스 무결성 훼손** | 데이터 유실·중복·불일치, 큐 적체, 원장 불균형 | 5xx 없이 발생 |

**두 번째 유형을 반드시 포함시킨다.** 증상 없는 장애(silent failure)는 RCA 연구에서 가장 난도가 높고, 5xx 기반 기존 방법이 무너지는 지점이다. 이를 배제하면 데이터셋의 차별점을 스스로 버리게 된다.

- 살아야 할 예: F04-R(주문 200인데 배송 유실), F18-P(이체 성공인데 원장 미적재), F14-P(컨슈머 예외 삼킴으로 이체 영구 유실)
- 죽어야 할 예: F02-P(인덱스 드롭했으나 그 인덱스를 타는 쿼리가 없음 — 아무 일도 안 일어남), 음성 시나리오 전체

**파생 규칙 — 성공조건 작성법**

G3이 요구하는 "피해 증명"이 곧 success 조건의 본질이다. 따라서:

1. **동어반복 금지.** 주입 파라미터를 되읽는 조건은 success가 될 수 없다.
   - 금지 예: `achieved_rps >= 주입rps`, `replicas == 0`, `image_pull_failed == true`, `env == 주입값`, `index_present == false`
   - 이런 항목은 **preflight 또는 effect-gate**로 내린다.
2. **구조적 항상-참 금지.**
   - 금지 예: `pod_ready == true`(주입이 파드를 죽이지 않는 시나리오), 태그를 심지 않는 시나리오의 `tagged_sessions == 0`
3. **단일 샘플 금지.** 비율(rate) 지표를 쓴다.
   - 실증: `entry_status`는 rate가 아니라 마지막 요청 샘플 1건이다(`load_north_south_executor.py:174-175`). `entry_status >= 500` 게이트는 영향반경이 100%가 아니면 발화하지 않는다. `entry_status`는 abort의 `== 0`(도달 불가) 판정에만 쓴다.
4. **비특이 지표 금지.** 어떤 장애에서도 오르는 지표(게이트웨이 p95 등)만으로 성공을 주장할 수 없다.

**최소 요건**: success 조건 중 **최소 1개는 피해를 직접 증명**해야 하며, 그 조건이 없으면 나머지가 몇 개든 G3 불통과다.

## 4. C. 풀 수 있는가

### G4. 관측 폐포 (observability closure)

**캡처된 데이터만으로 원인에 도달하는 경로가 존재해야 한다.**

이것은 G5(감별)와 다르고, 기존 4조건 ③과도 다르다.

| 무엇을 묻나 | 관측 주체 | 데이터 출처 |
| --- | --- | --- |
| 기존 ③ / G5 | 러너 컨트롤러 | 클러스터에 **실시간 직접 질의** |
| **G4** | RCA 시스템 | **캡처된 파일만** |

러너는 `kubectl`·DB·Prometheus에 직접 물어볼 수 있지만, 데이터셋 소비자는 캡처된 테이블만 본다. 러너가 성공 판정을 했다고 해서 그 케이스가 풀리는 문제라는 보장이 없다.

**판정 방법**: 정답의 `root_cause`에 도달하기 위해 필요한 증거를 나열하고, 각 증거가 **캡처 대상 테이블 중 어디에 어떤 형태로 남는지** 명시한다. 하나라도 캡처 밖이면 불통과.

- 실증(불통과): F13-H — connect-phase 지연은 TCP 핸드셰이크 구간이라 OTel 서버측 span에 잡히지 않는다. 부하생성기 클라이언트 측정치로는 보이지만 **그것은 시스템 텔레메트리가 아니다.** NMS(SNMP)는 소스 0으로 관측 불가 확정. → 어떤 방법으로도 풀 수 없는 케이스이므로 CUT.
- 실증(불통과): F09-H — 정답이 "GC 압박"인데 `jvm.gc.*` 관측이 0건.

**규칙**: 부하생성기가 뱉는 클라이언트 측정치는 G4의 증거로 인정하지 않는다. 사용자 영향을 *기술*하는 데는 쓸 수 있으나, 원인을 *지목*하는 증거로는 쓸 수 없다.

### G5. 감별 가능

혼동 후보와 구분되는 증거가 데이터에 있어야 한다.

- `must_support`: 이 시나리오라면 반드시 보여야 하는 증거
- `must_rule_out`: 이 시나리오가 아니라면 보였을 증거 (없음이 확인돼야 함)
- `contrast_with`: 혼동 후보 시나리오 ID를 **명시적으로 지목**

**요구 사항**

1. 각 증거의 query_id가 저장소 `registry/queries.json`과 러너 `observation_queries.json` **양쪽**에 등록돼 있어야 한다.
2. 해당 신호가 실제 텔레메트리에 존재해야 한다. 정의만 있고 메트릭이 없으면 불통과.
   - 실증: `prometheus.circuitbreaker_open`, `prometheus.http_server_active_requests`는 양쪽 registry에 부재.
3. 신호 해상도가 감별 주장을 지탱해야 한다.
   - 실증: `loadgen.*_status_rate`는 `business.5xx.rate`라 **502와 503을 구분하지 못한다.** "502 전파"(F19-S), "503 배제"(F20-Q), "502 vs 503"(F24-Q)를 이 신호로 감별할 수 없다. → step×status 버킷 신설이 선행조건.

### G6. 정답 무누설 (leakage)

**주입 흔적이 캡처 데이터에 정답 문자열로 남아서는 안 된다.**

RCA 시스템이 추론 없이 문자열만 읽어 정답을 맞힐 수 있으면 벤치마크가 무효화된다. 리뷰어가 가장 치명적으로 지적하는 유형이다.

**누설의 4계층**

누설은 성격이 다른 네 층으로 나뉘며, 대응 방식도 다르다. **판정 기준은 "정답을 가리키는가"이지 "인위적인가"가 아니다.**

| 층 | 무엇이 새는가 | 정답 노출 | 조치 |
| --- | --- | --- | --- |
| **L1 직접 누설** | 정답 문자열이 그대로 데이터에 존재 | 예 — 추론 불필요 | **수정 필수** |
| **L2 주입 서명** | 태그를 지워도 남는 "인위적 주입" 흔적 | 예 — 주입 여부가 드러나 탐색 공간 붕괴 | **수정 필수** |
| **L3 창외 오염** | 다른 시나리오·다른 시점의 주입 흔적 유입 | 예 — 틀린 단서 제공 | **수정 필수** |
| **L4 합성 환경 서명** | 테스트베드 전반에 균일하게 존재하는 합성 흔적 | **아니오** — 전 케이스 동일이라 변별 정보 0 | **공개(disclose)** |

L4를 위조해 숨기지 않는다. 균일하게 존재하는 합성 흔적은 케이스 간 변별력이 없어 풀이에 도움을 주지 않으며, 위조는 발견 시 오히려 데이터셋 신뢰를 무너뜨린다. 데이터셋 문서에 **명시적으로 밝히는 것**이 정답이다.

> **경계 판정**: L4처럼 보여도 **케이스마다 값이 다르면 L1**이다. 균일성이 L4의 성립 조건이다.

**실측 결과 (2026-07-27, v3 케이스 11건 전수 스캔)**

*L1 — 확인됨.* `case-f01-r-v3-*/data/clickhouse/dpm_session_local.parquet`의 `body` 컬럼에 8행:

```json
{"pid":132233,"dbName":"commerce","user":"commerce",
 "program":"rca-F01-R-inventory-lock","waitEvent":"PgSleep",
 "sessionType":"blocking","relNames":"inventory, inventory_pkey, ...",
 "queryTime":8852.658}
```

한 레코드에 **시나리오 ID·차단자 여부·대상 테이블**이 모두 들어 있다. 영향 범위 = 세션 태그를 쓰는 6종(F01-P, F01-R, F06-H, F08-G, F15-G, F15-T1).

*L2 — 확인됨.* 태그를 중립화해도 `waitEvent: PgSleep`이 남는다. 실제 운영 환경의 락 대기는 `pg_sleep`을 기다리지 않으므로, 이 값 자체가 "누군가 의도적으로 락을 잡고 대기 중"이라는 서명이다. 영향 범위 = DB 락 계열 전체.

*L3 — 확인됨, 전 케이스.* v3 11건 **전부**의 `process_meta.parquet`에 다음 cmdline이 존재:

```
bash -c echo $$ >".../scenario-profile-state/F09-R.pgid.tmp"; ... ;
       for _ in $(seq 1 2); do yes >/dev/null 2>&1 & done; sleep 480
```

F09-R(노드 CPU 부하) 주입 프로세스가 **F04-R·F08-H 등 무관한 케이스에도 들어 있다.** 원인은 캡처 설계: `process_meta`와 `host_connections`는 시간 슬라이스 없이 **전체 테이블을 통째로** 캡처하기로 되어 있어(캡처 계약 v3 §CH 12테이블 중 "전체 2"), 케이스 시간 창 밖의 다른 시나리오 흔적이 그대로 유입된다.

L3은 단순 누설을 넘어 **틀린 단서 제공**이다. 소비자가 이를 근거로 F09-R을 원인으로 지목할 수 있다.

*L4 — 확인됨, 전 케이스 균일.* 두 종류.

| 흔적 | 위치 | 규모 |
| --- | --- | --- |
| `user_agent.original = "k6/0.57.0 (https://k6.io/)"` | `otel_traces_local.span_attributes` | 케이스당 1.7만~9.1만 스팬 (전 요청) |
| `orderId = "loadgen-<epoch>-<seq>"` | `lucida_logs_local.body` (비즈니스 데이터) | 케이스당 600~2000행 |

11건 전부 동일하게 존재하므로 **어느 시나리오인지에 대한 정보를 담지 않는다.** → 위조하지 않고 데이터셋 문서에 공개한다.

단, `loadgen-` 주문 ID는 비즈니스 데이터에 박히므로, 무결성 계열 시나리오(중복·유실·불일치)에서 해당 값을 다룰 때 부자연스러울 수 있다. 자연스러운 형식으로 교체하는 것은 저비용 개선 사항이다.

**정상 확인된 경로 (2026-07-27 실측, 누설 없음)**

| 점검 대상 | 결과 | 이유 |
| --- | --- | --- |
| k8s 조작값(이미지·env·CPU limit·replicas) | 누설 없음 | 토폴로지 번들에 서비스명·구성원 목록만 담기고 파드 스펙이 없음 |
| MockServer expectation 내용 | 누설 없음 | 로그 수집 대상이 앱 서비스 12종뿐 — 인프라·mock 파드 로그 미수집 |
| k6 시나리오 태그(`step=checkout`, `20-P` 등) | 누설 없음 | k6 자체 지표에만 존재, HTTP 요청에 실리지 않아 트레이스에 미유입 |

> 이 결과는 **현재 캡처 구성**에 한한다. 캡처 대상(수집 서비스·테이블·토폴로지 필드)을 넓히면 재검증해야 한다.

> 오탐 배제: 네임스페이스명(`rca-testbed-commerce` 등)과 Kafka Cluster ID는 모든 데이터에 상시 존재하는 인프라 명명이므로 누설이 아니다.

**요구 사항**

1. 시나리오마다 **누설 점검표**를 작성한다: 주입이 남기는 모든 흔적 × 그 흔적이 캡처 대상에 들어가는지 × 어느 층(L1/L2/L3)인지.
2. **L1 대응 — 식별자 중립화(기본 방식).** 세션 태그·프로세스 이름·부하 태그에 시나리오 ID를 쓰지 않는다. 무의미 식별자(예: `sess-a3f9c1`)로 교체하고, 러너가 run 상태에 매핑을 보유해 정리·판정에 쓴다. 캡처 데이터에는 매핑이 남지 않는다.
   - 대안인 *캡처 제외*는 G4(관측 폐포)를 깨뜨릴 수 있고, *후처리 마스킹*은 누락 위험이 있어 둘 다 차선이다.
3. **L2 대응 — 주입 방식의 자연화.** 결함을 유지하는 수단이 실제 운영에서 나타날 수 있는 형태여야 한다. `pg_sleep` 대기처럼 현실에 존재하지 않는 대기 형태는 그 자체가 정답 힌트다.
   - 판정 기준: *"이 흔적이 실제 장애 로그에도 나타날 수 있는가?"* 아니라면 L2 누설.
   - 완전 제거가 불가능한 경우가 있으므로(주입은 본질적으로 인위적이다), **잔여 서명을 시나리오 문서에 명시**하고 데이터셋 한계로 공개한다. 숨기는 것보다 밝히는 편이 방어 가능하다.
4. **L3 대응 — 시간 창 강제.** 모든 캡처 테이블에 케이스 시간 창 필터를 적용한다. "전체 테이블 통째 캡처"는 다른 시나리오·다른 시점의 주입 흔적을 유입시키므로 금지한다.
   - 창 밖 데이터가 관측에 필요하다면(예: 정상 기준선), **그 사실과 범위를 meta에 명시**하고 다른 시나리오의 주입 흔적이 없음을 검증한 뒤 포함한다.
   - **구현 완료 (2026-07-27).** `capture-eval-case.sh`의 전체 스냅샷 2종을 제거했다. `host_connections`는 `timestamp` 창 슬라이스, `process_meta`는 창 안 `process_snapshot`의 `(target_id, proc_key)` 조인으로 스코프한다(→ [데이터 캡처 스펙 §2.2](spec-eval-data-capture.md)).
   - 이때 **"창 필터"가 곧 "자기 시간 컬럼 슬라이스"는 아니다**. `process_meta`는 프로세스를 처음 봤을 때만 등록하므로 `seen_at` 슬라이스는 창 이전부터 돌던 앱 프로세스의 메타를 통째로 날린다(실측 57% 유실). 창 필터의 목적은 *"창 안에서 실제로 존재한 것만 남긴다"*이지 *"창 안 타임스탬프만 남긴다"*가 아니다. 테이블마다 그 뜻을 만족하는 조건을 따로 세워야 한다.
5. **L4 대응 — 공개(disclose).** 위조하지 않는다. 데이터셋 문서에 다음을 명시한다: 트래픽은 k6로 생성된 합성 부하이며, 요청의 `user_agent`와 일부 비즈니스 식별자에 그 흔적이 균일하게 존재한다. 케이스 간 변별 정보가 없음을 함께 기술한다.
6. **CI 강제 — 누설 스캐너.** 캡처 산출물 생성 후 자동 스캔을 실행한다. L1~L3 검출 시 케이스를 격리하고 승격을 차단한다.
   - 탐지 패턴: `rca-F\d{2}-[A-Z]`, `scenario-profile-state/F\d{2}`, 시나리오 ID 문자열, 알려진 주입 서명(`PgSleep` 등)
   - **균일성 검사**: 어떤 흔적이 L4인지 L1인지는 **케이스 간 값이 같은지**로 판정한다. 전 케이스 동일하면 L4, 케이스마다 다르면 L1이므로 차단.
   - 오탐 배제: 네임스페이스명(`rca-testbed-*`), Kafka Cluster ID 등 상시 인프라 명명

## 5. D. 채점할 수 있는가

### G7. 기계 채점 가능한 정답

정답이 존재하는 것과 채점이 가능한 것은 다르다.

**정답 스키마 (필수)**

```jsonc
{
  "class": "A",                          // A | B — §2 G1 라벨
  "fault_pattern": "P1",                 // Class A만. P1~P8
  "domain": "commerce",
  "root_cause": {
    "target_kind": "service",            // service | container | node | database | middleware | config
    "target_id": "commerce-payment",     // ★ 단일 식별자. 문장 금지
    "trigger_target_id": "external-pg",  // ★ 트리거가 다르면 분리 기재
    "mechanism": "...",                  // 서술은 여기에만
    "code_anchor": [
      "commerce/payment-service/.../PgApiClient.java:31-40 (PgApiClient.pay — CB 부재)"
    ],                                   // ★ 라인 + 심볼명 병기
    "infra_anchor": "..."                // Class B. 수단 선택 근거 포함 권장
  },
  "must_support": [ ... ],
  "must_rule_out": [ ... ],
  "related_scenarios": { "contrast_with": ["F06-H"] },
  "scoring": {
    "granularity": "service",            // ★ 채점 입도
    "accept": ["commerce-payment"],      // ★ 정답으로 인정하는 답
    "partial": ["commerce-order"]        // ★ 부분점수 대상(증상 서비스 등)
  }
}
```

★ 표시는 07-27 감사에서 **결함으로 확인되어 신설·수정된 항목**이다.

**신설·수정 근거**

1. `target_id` 단일 식별자화 + `trigger_target_id` 분리 — 기존 3건은 트리거와 결함 보유 대상을 한 문자열에 문단으로 욱여넣어 기계 매칭이 불가능했다.
2. `injected_fault` 신설 — 정답이 실제 주입과 어긋나는 것을 작성 시점에 드러낸다.
   - **구현 시 변경(2026-07-28)**: `root_cause` 안의 서술 문자열이 아니라 **항목 최상위의 구조체**로 둔다. `controllers.json`의 승인 프로필·레벨 파라미터에서 **기계 도출**하므로 손으로 옮겨 적을 여지가 없고, CI가 라이브 컨트롤러와의 일치를 매 실행 검증한다. 서술로 두면 그 자체가 또 하나의 표류 대상이 된다.
   - 실증: F21-P는 주입이 **노드 CPU 부하**인데 정답을 "api-service의 무튜닝 Tomcat"으로 선언했다. 더 심각하게, **F09-R과 완전히 동일한 주입**(`tb-w3 cpu×3, 480s`)에 서로 다른 정답이 존재한다. 이 필드가 있었다면 즉시 검출됐다.
3. `code_anchor` 심볼 병기 — 라인은 코드가 바뀌면 썩는다. 감사에서 라인 오차 3건 검출.
4. `scoring` 블록 신설 — 채점 입도·인정 답·부분점수를 정의하지 않으면 평가 결과가 채점자마다 달라진다.

**CI 강제**: `code_anchor`의 각 항목에 대해 "해당 라인 근처에 그 심볼이 실제로 있는가"를 grep으로 검증한다.

**템플릿 정본**: `F24-Q` 항목(위 4가지 수정 반영본). 기존 구조 보유 3건 중 F21-P·F21-Q는 CUT 판정이므로 예시로 쓰지 않는다.

> **정본 자체를 규격에 맞춰 교정함 (2026-07-28).** 시범 집필 중 F24-Q가 제 규격을 어기고 있었다 — `target_id`가 146자 문장이었고, `scoring` 블록이 없었으며, `code_anchor`가 경로를 `.../`로 생략하고 한 항목에 여러 위치를 콤마로 묶어 **기계 검증이 불가능**했다. 단일 식별자(`food-restaurant`)·`scoring` 신설·앵커 14개 원자 분해로 교정했다. 문장에 담겼던 정보는 `mechanism` 앞머리로 옮겨 손실이 없다.
>
> **앵커 작성 규칙**: 한 항목 = 한 위치. `경로:시작-끝 (심볼 — 설명)` 형식이며 경로는 저장소 루트 기준 전체 경로다. 심볼은 인용 구간 안에 실제로 존재해야 한다 — CI가 검사하며, 실제로 시범 집필에서 잘못된 앵커 1건(`RestaurantClient.java:69-71`에 없는 `getMenu`)을 잡아냈다.
>
> **`target_id`와 `scoring.granularity`는 같은 층위여야 한다.** 입도가 `database-relation`인데 `target_id`를 인스턴스(`commerce-postgres`)로 적으면 `accept`와 물리지 않는다. F01-R·F06-H는 `commerce-postgres:payment_schema.payments` 꼴로 적고, 인스턴스만 지목한 답은 덜 정밀하므로 `partial`에 둔다. CI가 `target_id ∉ partial`을 강제한다.

### G8. 시간축 확정

장애 구간의 경계가 관측 데이터와 정렬돼야 한다.

- 주입 시작·종료, 효과 시작·종료(회복 완료)를 각각 기록한다. **주입 종료 ≠ 효과 종료.**
- 기록된 경계가 캡처 데이터의 타임스탬프와 같은 시간축·같은 정밀도인지 확인한다.
- 평가 시 "언제부터 어디까지가 장애인가"가 모호하면 채점이 흔들린다.
- cleanup 실패로 효과 종료가 기록되지 않으면 후속 케이스까지 오염된다(과거 실증: 실패한 cleanup이 `effect_ended_at=null`을 남겨 영구 차단).

## 6. E. 데이터셋 위생

### G9. 재현·격리

1. **재현성** — 같은 시나리오를 반복 실행하면 같은 라벨이 나와야 한다. 주입 강도가 확정(fixed 승인 프로파일)돼야 하며, 실행마다 결과가 갈리면 캘리브레이션 미완이다.
2. **cleanup 완전성** — 주입이 만든 상태 변화를 전부 되돌려야 한다. 되돌릴 수 없는 변형을 만드는 시나리오는 전용 시드와 역보정 수단을 갖추기 전까지 실행 금지.
   - 실증: F17-P — 부하가 공유 계정 `ACC-1001`의 잔액을 차감하는데 cleanup은 프로세스 종료뿐이다. 원장 역분개가 없어 **다음 케이스 오염이 설계상 확정**. → CUT
3. **케이스 간 무오염** — 앞 케이스의 잔재가 뒤 케이스에 남지 않아야 한다. 사이클 간 골든 상태 복원으로 보장한다.
4. **선행 조건 검증** — 정답이 특정 배치·상태를 전제한다면 실행 시점에 그것을 확인해야 한다.
   - 실증: F09-R은 "commerce 파드가 tb-w3에 다수 배치됨"을 전제하는데, 확인 장치가 없고 실제로 nodeSelector도 없다.

### G10. 변별력

벤치마크는 방법 간 차이를 드러내야 한다. 전부 쉬우면 모두 만점, 전부 어려우면 모두 0점 — **어느 쪽도 논문에 쓸 수 없다.**

1. **감별쌍 명시** — 각 시나리오는 최소 1개의 혼동 후보를 `contrast_with`에 지목한다. 짝이 없는 시나리오는 "원인 서비스가 유일하게 에러를 내는" 자명한 문제일 가능성이 높다.
   - 좋은 예: F05-H ↔ F05-R (종료 사유 `Error` vs `OOMKilled`, 자원 변경 유무)
   - 좋은 예: F20-P(자기 스키마 느림) ↔ F20-R(남의 스키마까지 느림)
2. **난이도 축 기록** — 각 시나리오에 난이도 요인을 기록한다: 증상-원인 거리(홉 수), 신호 유무(5xx 있음/조용함), 혼동 후보 수, 노이즈 동반 여부.
3. **분포 관리** — 데이터셋 전체에서 난이도가 한쪽에 몰리지 않도록 한다.

## 7. 판정 절차

### 7-1. 신규 시나리오

G1 → G2 → G3 순으로 먼저 본다(여기서 떨어지면 나머지는 볼 필요 없다). 통과하면 G4~G6(풀 수 있는가), G7~G8(채점), G9~G10(위생) 순으로 심사한다.

### 7-2. 기존 시나리오 재심사

`scenario-redesign-wip/golden4-audit-0727.md`의 판정을 출발점으로 하되, 그 감사는 **G1~G5 중심**이었다. 살아남은 34건(KEEP 15 + 조건부 19)에 대해 **G6~G10을 추가 심사**해야 한다. 특히:

- **G6(누설)**: 전건 미심사. 태그·env·어노테이션의 캡처 유입 여부 확인이 선행.
- **G7(채점 가능 정답)**: 전건 미충족(44개 중 구조 보유 3건, 그중 2건은 CUT). 백필 필요.
- **G10(변별력)**: 감별쌍이 우연히 잘 짜인 것은 있으나 체계적으로 관리된 적 없음.

### 7-3. 기록

각 시나리오는 10게이트 판정 결과를 `scenario-metadata.json`에 남긴다. 통과 여부만이 아니라 **판정 근거**(어떤 파일 어떤 라인, 어떤 신호)를 함께 적는다.

## 부록 A. 주입 설계 결정 기록

### A-1. DB 락 유지 방식 (2026-07-27 확정)

**문제**: 기존 방식이 L1·L2 누설을 동시에 발생시킨다.

```sql
-- 기존
BEGIN;
LOCK TABLE inventory IN EXCLUSIVE MODE;
SELECT pg_sleep(600);   -- L2: 실운영에 존재하지 않는 대기
ROLLBACK;
-- 세션 이름: PGAPPNAME=rca-F01-R-inventory-lock  -- L1: 정답 문자열
```

**실측 근거** (`case-f01-r-v3-*`, `case-f04-r-v3-*`의 `dpm_session_local.parquet`)

| 항목 | 자연 분포 | 기존 주입 |
| --- | --- | --- |
| `program` | `PostgreSQL JDBC Driver` 319행 (commerce/commerce) | `rca-F01-R-inventory-lock` — **14,167행 중 유일** |
| `waitEvent` | `ClientRead`(idle in tx) 173행, `CPU` 170행 | `PgSleep` — **유일** |
| 차단 세션 | 락 시나리오 아닌 케이스(F04-R)에서 **0건** | 130건 유발 (= 피해, 정상) |
| idle-in-tx 지속 | p50 2.5s / max 20.3s | (해당 없음) |

**결정**

| 항목 | 변경 | 근거 |
| --- | --- | --- |
| 세션 이름 | `rca-<시나리오>-<설명>` → **`PostgreSQL JDBC Driver`** | 실제 앱 세션 319행과 동일 문자열. 자연 모집단에 편입 |
| 유지 방식 | `SELECT pg_sleep(N)` → **트랜잭션만 열고 클라이언트 대기**(idle in transaction) | 커넥션 풀 트랜잭션 누수는 운영에서 흔한 사고. `waitEvent=ClientRead` 자연 발생 173행 |
| **보유 시간** | **변경 없음** (440초 등 기존 값 유지) | 아래 참조 |
| cleanup | 이름 매칭 → **주입 시 백엔드 PID 기록 후 해당 PID만 종료** | 이름이 앱과 같아져 이름 기반 종료가 실 서비스 세션을 죽일 수 있음 |

**보유 시간을 자연 분포에 맞추지 않는 이유**

자연 `idle in transaction`의 최대치는 20.3초다. 여기에 맞추면 락이 20초만 유지되어 **장애가 발생하지 않는다** — G3(서비스 피해 실재)와 정면 충돌한다.

L2의 판정 기준은 *"흔적이 정상 운영처럼 보이는가"*가 아니라 ***"실제 버그가 이 흔적을 만들 수 있는가"*** 이다.

- 440초짜리 `idle in transaction` → **가능하다.** 커넥션 풀이 트랜잭션을 물고 놓지 않는 사고는 몇 분~몇 시간 지속된다. 교과서적 운영 장애다.
- 440초짜리 `pg_sleep` → **불가능하다.** 트랜잭션 안에서 `pg_sleep`을 호출하는 애플리케이션은 없다.

**장애는 정상 분포를 벗어나야 한다. 벗어나면 안 되는 것은 "이것은 시험 장비다"라는 흔적이다.** 이 둘을 혼동하면 G3와 G6이 서로를 무효화한다.

**부수 효과 (긍정)**: 전환 후 소비자가 마주하는 문제는 *"440초째 트랜잭션을 점유한 JDBC 세션 하나가 130개 세션을 차단하고 있다"*가 된다. 이는 실제 DBA의 장애 대응 경로와 동일하며 G4(관측 폐포)를 그대로 만족한다.

**적용 대상**: 세션 태그를 사용하는 6종 — F01-P, F01-R, F06-H, F08-G, F15-G, F15-T1. Oracle 계열(F01-P, F08-G)은 `client_identifier`와 대응 대기 이벤트에 같은 원칙을 적용한다.

### A-1. 신원을 지우면 신원 기반 판정도 함께 죽는다 (2026-07-27 후속)

주입 세션이 앱과 같은 이름을 달자 러너의 `database.tagged_session_count`(= `application_name`이 시나리오 태그인 세션 수)가 **항상 0**을 반환했다. F01-R의 `lock-present`·F06-H의 `db-lock-held`가 성립 불가가 되고, F06-H의 `must_rule_out.symptom-without-our-lock`은 상시 발화한다. 즉 **L1 대응은 판정 경로를 함께 갈아엎지 않으면 시나리오를 실행 불능으로 만든다.**

교체안: **`database.blocked_session_count`** — 대상 릴레이션을 만지면서 `pg_blocking_pids()`로 차단된 세션 수. 주입의 *서명*이 아니라 *피해자*를 센다.

이것이 단순 대체 이상인 이유는 G3다. 아무도 기다리지 않는 락은 사건이 아니다. 컨트롤러가 확인해야 할 명제는 "우리 세션이 거기 있다"가 아니라 **"그 락이 실제로 물었다"**이며, 새 관측은 후자를 직접 measure한다. 동어반복 성공조건(G3 부수효과)도 자동으로 배제된다.

실측 검증(커머스 PG 라이브, 2026-07-27): 락 보유·대기 1건 → `1`, 같은 시점 무관 릴레이션 조회 → `0`, 락 해제 후 → `0`. 근거 데이터로 F01-R 캡처의 blocking 130행(락 없는 F04-R은 0행)이 이미 대기자가 실제로 쌓임을 보인다.

**남은 것**: Oracle 경로(F01-P·F08-G)는 아직 구 태그 방식이라 이 문제를 겪지 않는다. 다만 A의 신원 사칭을 Oracle에 적용하는 시점에 같은 교체가 함께 필요하다.

### A-2. Oracle 태그의 L1 해소와 F15-G의 PG 경로 이관 (2026-07-28)

**Oracle — L1을 L4로 강등한다.** `client_identifier`가 `rca-F01-P-oracle-lock` 꼴로 시나리오 ID를 인코딩하고 있었다(F01-P·F08-G·F15-G). 태그 하나가 정답을 지목하므로 L1이다. PostgreSQL처럼 실 앱 신원을 사칭하는 것이 최종 목표지만, 실 앱 세션의 `program`/`module` 실측이 선행돼야 하므로 그 전 단계로 **전 케이스 균일한 상수 `dba-maintenance`** 로 통일했다. G6의 판정 규칙 그대로다 — 케이스마다 다르면 L1(차단), 균일하면 변별정보가 0이라 L4(공개).

값 선택 근거: 실 앱은 `dbms_session.set_identifier`를 호출하지 않으므로 무엇을 넣어도 앱과 같아지지는 않는다. 그렇다면 **특정 서비스를 지목하지 않는** 운영 주체 이름이 안전하다. `banking-interest-batch` 같은 값은 그럴듯하지만 무고한 서비스를 가리키는 **틀린 단서**가 되어 L3보다 나쁘다.

남은 Oracle L2 두 축은 그대로다 — `host sleep` 유지(인위적 대기)와 DB 파드 내부 실행(출처가 앱과 다름).

**F15-G의 PG 경로 — A-1을 뒤늦게 적용한다.** `db.lock` 실행기만 A-1로 전환됐고 `timeline.multi`의 `pg_lock`은 구 방식으로 남아 있었다. F15-G는 `readiness: ready`라 그대로 실행되면 한 세션에 세 유일값을 다시 남긴다 — `application_name=rca-F15-G-inventory-lock`(L1), `pg_sleep` 대기(L2), 클러스터 밖 tb-runner의 NAT 주소(L2). `db.lock`과 같은 클러스터 내 클라이언트 파드 방식으로 교체했고, 함께 판정도 A-1대로 태그(`database.tagged_session_count`)에서 피해자(`database.blocked_session_count`)로 옮겼다.

**클라이언트 파드 라벨의 L1도 함께 제거했다.** 주입용 파드에 `lucida.io/scenario-run: <시나리오 ID>` 라벨이 붙어 있었다. 세션은 익명화해 놓고 그 세션을 만든 파드가 이름표를 달고 있으면 KCM 계열 관측에서 그대로 새어 나간다. 라벨은 `lucida.io/db-client: session` 하나로 통일했다(회수는 이 라벨만으로 가능하며, 오히려 다른 시나리오가 남긴 잔재까지 잡는다).

### A-3. distractor 변형쌍의 채점 취급 (2026-07-28)

F08-H:F01-H, F08-G:F01-P는 **같은 주입에 무죄인 배포 하나를 더한 짝**이다. 근본도 `scoring.accept`도 동일하고, 뒤쪽이 추가로 요구하는 능력은 "변경 이력을 근거 없이 범인으로 지목하지 않는가" 하나다.

- **별개 케이스로 유지한다.** 그 능력은 실제 RCA에서 가장 흔한 오답원이고, 짝이 없으면 측정되지 않는다.
- **다만 정답 분포 계산에서는 같은 그룹으로 묶는다.** 두 건을 독립 표본으로 세면 같은 정답이 두 번 계산돼 데이터셋이 특정 근본에 치우친 것처럼 보인다.
- **판별 축은 시간 정렬이다.** 배포 무죄 계열은 실패 개시가 롤아웃과 어긋나고(F08-H·F08-G는 15초), 배포 유죄 계열(F08-P)은 새 파드 Ready 시각과 정렬된다. 이 축이 성립하려면 G8(시간축 확정)이 선행돼야 한다.

### A-4. `domain` 필드의 뜻 (2026-07-28)

크로스도메인 시나리오에서 값이 갈렸다 — F08-G는 `commerce`(증상), F01-P는 `core-banking`(근본). **정답지 필드이므로 근본이 속한 도메인으로 통일한다.** 증상 도메인은 `root_cause.trigger_target_id`와 `user_impact`가 이미 말한다. 카탈로그의 실행 도메인(부하·네임스페이스)과는 다른 개념이며 서로 달라도 정상이다.
