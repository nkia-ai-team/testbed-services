# 주입 강도 드리프트 가드 — 설계 (2026-08-07)

상태: **설계 승인, 구현 보류.** 구현은 아래 순서 제약에 걸려 있다.

대상: F20-P · F20-Q · F20-R (슬로우쿼리 패밀리, 2026-07-24 승격 `3408392`)

---

## 0. ⚠ 순서 제약 — 이걸 먼저 읽어라

```
정리(retention) 도입 → 표가 정상 상태 도달 → 그 크기에서 F20 셋 재보정(새 1.0×) → 가드 투입
```

**이 순서를 어기면 가드가 첫날부터 F20 셋을 전부 막는다.** 지금 배율이 2.11~46.3×라 어떤 합리적 밴드로도 통과하지 못한다.

그리고 그때 벌어질 일이 진짜 위험이다 — **"가드가 너무 엄격하다"고 오진하고 밴드를 넓히게 된다.** 그건 2026-08-07에 F20-Q의 `consecutive_ticks`를 2→1로 낮춘 것과 **똑같은 실수**다. 그때도 원인은 테스트베드가 낡은 것이었는데 증상을 보고 게이트를 낮췄고, 그 결과 드리프트가 더 진행돼도 안 보이게 됐다.

**가드는 드리프트를 되돌리는 장치가 아니라, 되돌린 뒤 그 상태를 지키는 장치다.**

---

## 1. 문제 — 주입 강도가 데이터 크기와 등가다

F20-Q의 주입은 두 질의이고 **둘 다 표 전체에 비례한다**:

```
GET /api/orders                      (page/size 미지정 → Pageable.unpaged())
GET /api/orders/stats/daily?days=90
```

`EXPLAIN`(ANALYZE 없이, 2026-08-07):

```
1) SELECT * FROM orders WHERE (NULL IS NULL OR ...) ...
   type=ALL, key=NULL, rows=1,020,625                    ← 풀스캔, 전량이 힙으로
2) SELECT DATE(created_at), COUNT(*), SUM(...) ...
   WHERE created_at >= NOW()-90d GROUP BY DATE(created_at)
   type=ALL, possible_keys=idx_orders_created_at, key=NULL, rows=1,020,625
   Extra: Using where; Using temporary; Using filesort
```

핵심은 `Pageable.unpaged()`다. 무제한 결과셋이 order JVM 힙(k8s limit **1Gi**)에 통째로 적재되는 것이 F20-Q의 **정체성**이다. 즉 주입 강도는 행수에 비례하는 게 아니라 **행수 그 자체다**.

`days=90`도 사실상 무제한이다 — 라이브 데이터가 25일치뿐이라 90일 창이 표의 99.6%(1,364,177 / 1,369,819)를 덮는다. 파라미터가 90이든 30이든 지금은 같은 뜻이다.

commerce(F20-R)는 한술 더 뜬다: `GET /api/orders?from=2000-01-01T00:00:00` — 연도를 2000으로 박아 **설계상 무한 창**이다.

### 실측된 드리프트 (승격 07-24 → 08-07, 14일)

| 시나리오 | 대상 표 | 보정 시점 | 지금 | **배율** | 상태 |
|---|---|---|---|---|---|
| **F20-Q** | food `orders` | 590,913 | 1,369,819 | **2.32×** | live |
| **F20-R** | commerce `order_schema.orders` | 566,279 | 1,195,109 | **2.11×** | live |
| **F20-P** | banking `transfers` | **19,102** | 883,643 | **46.3×** | parked |

F20-P가 46배인 이유는 시드가 19,102건으로 얇았고 라이브 부하가 그 위에 계속 썼기 때문이다.
**그리고 그 19,102이라는 숫자 자체가 의심스럽다** — 다른 둘이 56만·59만인데 혼자 1.9만이다. 승격 당시 이미 대표성 없는 상태에서 보정했을 가능성이 크다.

### 판정에 실제로 닿은 증거

| 배율 | 시점 | 관측된 영향 |
|---|---|---|
| **1.00×** | 07-24 보정 | `consecutive_ticks: 2`로 게이트가 작성됨 — **2연속이 채워졌다** |
| **2.32×** | 08-07 | 파드가 46초에 사망, 평가 창 1틱 → **게이트를 2→1로 낮춰야 했다.** 알려진 불량점 |
| ~3.55× | 08-19 투영 | 사망이 `min_hold`(30초) 앞으로 → **평가 틱 0개, 어떤 게이트로도 성립 불가** |

투영 근거: `min_hold 30s` · `tick 15s` · 관측된 사망 ≈ 46초. 사망 시각이 행수에 반비례한다고 보면 사망이 30초 앞으로 오는 지점은 약 2.10M행. 일 증가 58,700행 → (2.10M − 1.37M) / 58,700 ≈ **12일 후, 대략 2026-08-19**.

## 2. 정리(retention)만으로는 부족하다 — 산수

일 증가량으로 30일 보관 시 정상 상태를 계산하면:

| 표 | 일 증가 | 보정 시점 | 지금 | **30일 정상 상태** | 보정 대비 |
|---|---|---|---|---|---|
| food `orders` | 58,700 | 590,913 | 1,369,819 | **~1.76M** | **2.98×** |
| commerce `order_schema.orders` | ~44,900 | 566,279 | 1,195,109 | **~1.35M** | **2.38×** |
| banking `transfers` | ~61,800 | 19,102 | 883,643 | **~1.85M** | **97×** |

**정상 상태가 셋 다 지금보다 크다.** 30일 정리를 넣어도 F20-Q는 보정치의 2.98×에서 안정화되고, 그건 오늘 게이트를 깨뜨린 2.32×보다 **더 나쁘다**.

그래서 정리는 **필요조건이지 충분조건이 아니다**. 정리가 하는 일은 "무한히 자라는 것"을 "일정한 크기"로 바꾸는 것뿐이고, **그 일정한 크기가 보정치와 같아지도록 재보정하는 단계가 반드시 뒤따라야 한다.**

보관 기간을 30일보다 짧게 잡는 선택지도 있다. 다만 그러면 food `OrderCleanupBatch`의 30일 창을 함께 줄여야 한다 — 그 배치는 삭제가 아니라 **취소만** 하므로(`OrderRepository.java:18`, `UPDATE ... SET status='CANCELLED'`) 어차피 의미를 다시 정하는 김에 같이 보면 된다.

## 3. 설계

### 3.1 무엇을 재는가

```
scale_ratio = 현재 행수 / 보정 시점 행수
밴드 밖 → preflight 실패 → 런이 시작되지 않는다 (fail-closed)
```

**행수는 카탈로그 추정치를 쓴다. 정확한 `count(*)`를 쓰지 않는다.**

- postgres `pg_class.reltuples` / mysql `information_schema.tables.table_rows` / oracle `user_tables.num_rows`
- 이유: **스캔하는 프로브 문제를 스캔하는 프로브로 고치면 안 된다.** `count(*)`는 1.4M 행 풀스캔이고, `735e8c4`가 고친 F23-R 프로브에서 본 대로 161MB를 읽어 128MB 공유 버퍼 캐시를 통째로 밀어낸다. 밴드가 ±50% 수준의 성긴 판정이므로 추정치로 충분하다.
- autovacuum이 자주 돌고 있어(commerce outbox 계열 33~40회) `reltuples`는 이 용도에 충분히 정확하다.
- **⚠ 설계 제약**: 실측에서 `orders`의 `reltuples`는 1,020,625, 실제는 1,369,819로 **34% 낮다.** 따라서 **보정 시점 값도 반드시 같은 방식(추정치)으로 기록해야 한다.** 정확한 count로 기록한 값과 추정치를 비교하면 배율이 34% 왜곡된다.

### 3.2 어디에 기록하는가 — **러너 단일 출처**

`rca-scenario-runner/backend/app/live_probes.py`, `WORKER_COHORT_PLACEMENT` 옆:

```python
# scenario_id -> (도메인, 표, 보정 시점 추정 행수, 밴드)
INJECTION_SCALE_BASELINES = {
    "F20-Q": ("food-delivery", "orders",              590_913, (0.5, 1.5)),
    "F20-R": ("commerce",      "order_schema.orders", 566_279, (0.5, 1.5)),
    "F20-P": ("core-banking",  "transfers",            19_102, (0.5, 1.5)),
}
```

`APPROVED_CHECK_IDS`에 `injection-scale-band`를 추가하고, `inspect()`의 `checks` 맵에 연결한다.

**왜 레지스트리가 아니라 러너인가 — 세 가지:**

1. **시나리오가 자기 밴드를 선언하면 가드가 자기를 무력화한다.** 드리프트로 걸린 시나리오가 밴드를 넓히면 끝이다. 이건 주입 파라미터가 아니라 **판정 계약**이라 `THROTTLE_TARGETS`·`APPROVED_APM_SERVICES`·`WORKER_COHORT_PLACEMENT`과 같은 자리에 있어야 한다. `WORKER_COHORT_PLACEMENT` 주석이 이미 같은 논리를 담고 있다 — *"Server-side on purpose: the scenario may not nominate the node it is about to be judged against."*

2. **한 곳에 두면 갈라질 수 없다.** `c367f7c`에서 같은 사실(F23-R `window_minutes`)이 레지스트리·매니페스트·러너 상수 세 곳에 있어 하나만 고쳐진 것을 봤다. 여기서는 레지스트리에 복제하지 않는다.

3. **미등록이 곧 실패다.** `_worker_cohort_is_placed`가 미등록 시나리오에 `LiveProbeError("no worker cohort placement is registered for ...")`를 던지는 그대로 — 체크를 선언했는데 등록이 없으면 조용히 통과하지 않고 멈춘다.

**대가**: 시나리오 승격에 러너 변경이 필요해진다. 다만 이건 이미 사실이다 — 새 관측 대상마다 `APPROVED_*`를 건드려야 한다.

### 3.3 밴드 — **[0.5×, 1.5×], 경고 1.25×**

**이건 측정이 아니라 판단이다.** 데이터 점이 둘뿐이다: 1.00×에서 정상, 2.32×에서 불량. 그 사이에 점이 없다.

- **상한 1.5×**: 알려진 유일한 불량점(2.32×) 아래로 여유를 두는 보수적 선택.
- **하한 0.5×**: 과소 주입도 실패다. 표가 너무 얇으면 시나리오가 자기 정체성(힙 고갈)에 도달하지 못한다. **F20-P의 19,102행이 바로 그 사례로 의심된다.** 하한이 있으면 그런 승격이 preflight에서 걸린다.

**세 번째 점은 언제 얻는가**: 정리 도입 → 정상 상태 도달 → 재보정 후의 **첫 런들**이 준다. 그때 1.0× 근처에서 게이트가 어떻게 서는지 보고 밴드를 좁히거나 넓힌다. 그전까지 [0.5, 1.5]는 잠정값이다.

### 3.4 범위와 가드의 가드

**지금 범위**: F20-P · Q · R 3종. 부하 스크립트 16개 전수 확인 결과이며, 나머지 13개는 전부 `page=&size=20`으로 경계가 있다 (commerce `script.js`·`surge.js`·`capacity-probe.js`, food `script.js`·`surge.js`·`order-surge.js`·`create-heavy-surge.js`·`capacity-probe.js`, banking `script.js`·`surge.js`·`transfer-heavy-surge.js`·`frozen-bypass.js`·`capacity-probe.js`).

**앞으로 잊지 않는 방법** — 레포 테스트로 강제한다:

```
*/loadgen/*.js 를 스캔해 "데이터 크기 비례" 패턴을 찾고,
그 스크립트를 script_path 로 쓰는 시나리오가
INJECTION_SCALE_BASELINES 에 등록돼 있지 않으면 실패한다.
```

탐지 패턴(전부 이번 실측에서 나온 것):
- 목록/집계 엔드포인트 호출에 `page=`·`size=`가 **없음** (→ `Pageable.unpaged()`)
- `days=` 같은 기간 파라미터
- 과거로 못 박은 날짜 리터럴 (`from=2000-01-01`)

**이 테스트는 러너 레포에 둔다.** 맵이 러너에 있고, 러너의 `test_external_live_manifests.py`가 이미 testbed-services 레지스트리를 건너와 읽는 패턴(체크아웃 없으면 skip)을 갖고 있다. 교차 레포 사실은 갈라지므로 **읽는 쪽에 검사를 둔다.**

## 4. 대안 비교 — 기각 사유 포함

| 대안 | 판정 | 이유 |
|---|---|---|
| 주입 파라미터를 표 크기로 자동 보정 (`LIMIT` 등) | **기각** | 정체성 파괴. F20-Q가 주입하는 결함이 "무제한 결과셋이 힙을 채운다"인데 `LIMIT`을 걸면 페이지네이션 있는 정상 API가 된다. `days`를 줄여도 표가 자라면 결국 같은 크기가 된다 |
| 주기적 재보정 | **단독으로는 기각** | 증상 처리. 드리프트가 다시 시작되고, 사후에 "시나리오가 나빠진 것"과 "테스트베드가 커진 것"을 **구분할 수 없게** 된다. 단 정리 뒤 **1회** 재보정은 필수(§0) |
| **배치마다 리시드/초기화** | **기각 — 다만 기록을 지우지 말 것** | **드리프트를 완전히 없애는 유일한 대안이다.** "노화된 시스템"의 현실성을 잃고 배치마다 시간 비용이 크다는 이유로 채택하지 않았을 뿐이다. 현실성 요구가 바뀌거나 배치 시간이 여유로워지면 **판단이 바뀔 수 있다** |
| 게이트를 상대화 (절대 바이트 대신 힙 증가율) | **부분 기각** | F20-Q 하나에는 유효할 수 있으나 일반화되지 않고, **`min_hold` 전에 파드가 죽는 문제를 못 막는다.** 평가 창 자체가 사라지면 어떤 게이트도 소용없다 |
| 정리(retention) | **채택 — 치료이지 탐지가 아님** | 분모를 붙잡는 유일한 방법. **가드와 둘 다 필요하다** — 정리가 밴드를 만족시키고, 가드가 밴드를 벗어났을 때 알려 준다. 그리고 §2대로 정리만으로는 부족하다 |

## 5. 정리(retention) 우선순위 재평가

본체(`orders`/`payments`/`transfers`)가 F20 패밀리의 **분모**이므로, 이건 위생이 아니라 **판정 정확성** 항목이다.

| 순위 | 종전 초안 | 갱신 | 목적 |
|---|---|---|---|
| 1 | outbox_events (~3.5GB) | outbox_events | 디스크 회수 |
| 2 | payment_logs | **`orders`/`payments`/`transfers` 본체** | **보정 안정화 (승격)** |
| 3 | 이벤트 표들 | payment_logs (읽는 코드 없음) | 디스크 회수 |
| 4 | **본체** | 이벤트 표들 | 디스크 회수 |

삭제 순서 제약(commerce FK 8개 전부 `NO ACTION`, CASCADE 없음)은 종전 초안 그대로:
```
payment_logs → payments,  order_items → orders,  shipment_events → shipments,
auth_tokens·addresses → users,  cart_items → carts,  product_variants → products
outbox_events : FK 없음 — 독립 삭제 가능
```

## 6. 즉시 반영할 별표

재배치·승격 판단에 아래 단서를 붙인다.

- **F20-P** — 승격 검토 시 **보정치의 46.3×**(19,102 → 883,643). 덧붙여 **보정 자체가 의심스럽다**(§1).
- **F20-Q** — 재배치 결과는 **보정치의 2.32×로 주입된 값**이다.
- **F20-R** — 재배치 결과는 **보정치의 2.11×로 주입된 값**이다.
