# 남은 9종 — 설계 결정 요청서 (2026-08-09)

배치 4회(23 → 25 → 27 → 26)를 거치며 **조정으로 해결되는 것은 전부 조정했다.**
여기 남은 9종은 임계를 옮기거나 게이트를 손보는 것으로는 풀리지 않고, **시나리오가 무엇을
주장하려는 것인지**를 다시 정해야 한다. 그래서 결정을 요청한다.

각 항목은 이렇게 적었다: **무엇이 막고 있나 / 왜 조정으로 안 되나 / 선택지 / 내 권고**.
권고는 근거와 함께 적었으니 동의하지 않으시면 그 근거를 반박하시면 된다.

## 0. 먼저: 이 아홉을 관통하는 하나의 질문

여덟 중 다섯이 같은 뿌리다 — **"관측이 불가능한 순간을 판정에서 어떻게 다룰 것인가."**

측정 게이지는 서비스가 포화되면 눈이 먼다. APM 백분위는 완료 트랜잭션이 없으면 표본이 없고
(`"the service completed no transaction in the last 60s"`), 이건 버그가 아니라 **의도된 설계**다.
빈 창에 0을 내던 이전 동작이 `gte` 게이트를 망가뜨려서 일부러 `unusable` 로 바꾼 것이다.

문제는 그 다음이다. `adaptive.py:_updated_streaks` 는 `if result is not True` 로 판정하므로
**`False`(조건 미달)와 `None`(관측 불가)을 똑같이 취급해 성공 스트릭을 0으로 리셋한다.**
그래서 **주입이 가장 잘 먹히는 구간에서 성공 확정이 가장 어려워진다.**

### 결정 D0 — `success` 게이트가 관측 불가 틱에서 스트릭을 유지할 것인가

- **유지 안 함(현행)**: 지금처럼. 관측 공백이 성공을 계속 리셋한다
- **유지함**: `success` 만 `unknown` 에서 스트릭을 보존하고, `abort`·`must_rule_out` 은 계속 리셋한다.
  보존 상한을 독립성 창의 N 배로 둔다(예: N=2)

**내 권고: 유지함(상한 있는 형태).** 근거는 비대칭성이다 — `abort`/`must_rule_out` 은 "위험하거나
다른 원인이 있다"를 주장하므로 모르면 침묵하는 쪽이 안전하다(fail-closed). 반면 `success` 는
"이미 관측된 피해"를 세는 것이고, 관측이 잠시 끊겼다고 **이미 본 피해가 없던 일이 되지는 않는다.**

**부작용(반드시 인지하실 것)**: 관측 공백을 가로질러 성공이 확정될 수 있다. 상한을 두는 이유가
이것이고, 상한을 넘으면 리셋하면 된다.

**영향 범위**: `41종 전체의 판정`을 지배하는 코드다. 그래서 무단으로 바꾸지 않았다.
이 결정 하나로 **F15-H · F05-P** 가 직접 풀리고, **F09-P · F12-H · F07-H** 의 여유가 넓어진다
(지금은 ct=2 로 낮춰 통과시켰지만 스트릭이 정확히 2 로 아슬아슬하다).

## 1. F03-H — 성공 조건 둘이 서로를 배제한다

**막는 것**: `success = order_p95 >= 2000 AND checkout_5xx_rate >= 0.05`

**왜 조정으로 안 되나**: 5xx 로 실패한 요청은 완료 트랜잭션이 아니라서 **백분위 표본에 들어가지
않는다.** 두 조건이 물리적으로 반대 방향이다. 실측(108 평가틱):

| | `checkout_5xx` 평균 |
|---|---|
| `order_p95` 정상 틱 (84개) | 0.130 |
| `order_p95` unusable 틱 (24개) | **0.691** |

**5.3배 차이.** 주입이 셀수록 게이지가 눈이 먼다. 동시 만족은 13/108틱뿐이고 최대 스트릭은 1이라
`ct` 를 낮춰도 통과하지 못한다.

**선택지**
- (a) `all` → `any` — "지연이 나빠졌거나 **또는** 에러가 늘었다"
- (b) `order_p95` 를 5xx 에도 살아남는 포화 신호로 교체(스레드 풀 대기/큐 깊이 등)
- (c) "완료 트랜잭션 없음"을 지연 손상의 충족으로 인정

**내 권고: (b).** 이 시나리오는 `order-thread-saturation` 이다 — 주장하려는 것이 **스레드 포화**이므로
포화를 직접 재는 신호가 원래 맞다. (a)는 쉽지만 두 개의 다른 피해를 하나로 뭉개서 시나리오의
주장이 흐려진다.

## 2. F15-H · 3. F05-P — D0 에 직접 묶인다

**F15-H**: 세 성공 조건이 모두 충족 가능한데(`blocked_db_sessions` max 13 / `429_rate` 0.80~1.00 /
`order_p95` max 3,623) `commerce_order_p95` 가 **21/53 = 40%** unusable 이다. 최대 스트릭 1.
→ **ct 를 2로 낮춰도 부족하다**(인접한 두 표본조차 없다). D0 가 필요하다.

**F05-P**: 레벨 2(`node_mem_util` 96.83)에서 성공 가능 창이 **네 틱**인데 그 한가운데
`checkout_5xx_rate` 가 unusable 로 떨어져 스트릭이 리셋되고, 곧 노드가 NotReady 가 되어 abort 한다.
```
el= 64  5xx=1.0   suc=1
el= 79  5xx=1.0   suc=1
el= 95  5xx=None  suc=0   <- 관측 불가가 리셋
el=121  entry=0   ab=1
```
→ D0 로 풀린다. (레벨 1(mem 94)에서는 5xx 가 내내 0 이라 주입이 물지 않는다 — 사다리 하단을
올리는 것도 함께 고려할 만하다.)

## 4. F15-T2 — 429 를 주는데 서비스가 5xx 로 바꾼다

**막는 것**: `must_rule_out` 의 `food-promoted-to-5xx: food_create_5xx_rate >= 0.1`. 실측 0.81~0.91.

**형제 비교가 원인을 가리킨다**

| | 설계 부하 | food 429 | food 5xx |
|---|---|---|---|
| F15-H (동시, offset 0) | **5 rps** | 0.80~1.00 | **0.00** |
| F15-T2 (지연, offset 240) | **40 rps** | 0.00~0.37 | **0.98** |

같은 mock·같은 429 인데 **부하가 8배 다르고 결과가 정반대다.** 40 rps 에서는 429 응답이
주문 서비스의 재시도/스레드를 소진시켜 5xx 로 승격되는 것으로 보인다.
**감별자는 옳게 작동하고 있다** — 설계 의도(429 전파)와 실제 거동(5xx)이 다르다고 말하는 중이다.

**선택지**
- (a) F15-T2 의 설계 부하를 F15-H 수준으로 낮춰 429 가 전파되게 한다
- (b) 5xx 승격을 시나리오의 정상 거동으로 받아들이고 성공 조건을 5xx 기준으로 바꾼다
- (c) 서비스의 429 처리(재시도/백오프)를 고쳐 승격되지 않게 한다 — 앱 수정

**내 권고: (a).** F15-T2 는 F15-H 의 **시간차 변형**이지 부하 변형이 아니다. 둘의 부하가 8배
다른 것 자체가 설계 실수로 보인다. (c)는 테스트베드 앱을 고치는 일이라 범위가 크고, 사실
"고부하에서 429 가 5xx 가 된다"는 것은 **관측할 가치가 있는 진짜 현상**이라 지우기 아깝다.

## 5. F20-Q — 주입이 판정할 시간을 안 준다

**막는 것**: 평가틱 **2개**. `entry_status` 200 → **0**(el=46s) → abort.

주입 전 진입은 정상 200 이었다. 즉 환경 결함이 아니라 **주입이 46초 만에 진입을 죽인다.**

**선택지**
- (a) 주입 강도를 낮춰 진입이 살아 있는 채로 피해가 관측되게 한다
- (b) `abort` 의 `entry-unreachable` 에 유예를 준다(`consecutive_ticks` 상향 또는 `min_hold` 도입)
- (c) 이 시나리오의 성공 조건 자체를 "진입 소실"로 바꾼다 — 즉 즉사가 곧 피해다

**내 권고: (a).** 진입이 죽으면 그 뒤의 어떤 관측도 무의미하므로 (b)는 판정 품질을 떨어뜨린다.
(c)는 시나리오를 다른 것으로 바꾸는 것이라 `F20-Q` 의 원래 의도를 확인해야 한다.

## 6. F10-P — 인과 사슬이 없다 (게이지 대조군으로 확정)

**막는 것**: 디스크 주입이 DB 풀 경합을 **한 번도** 만든 적이 없다.

**확정 근거**: `transfer_hikari_pending` 이 63틱 전부 정확히 0 인데, 이게 사슬 부재인지 죽은
게이지인지 대조군으로 갈랐다 — **이 게이지를 쓰는 7런 중 5런에서 0 초과**(max 38·31·30·26·6).
게이지는 살아 있다. 0 인 두 런은 정확히 **B 수리(무제한 조회 제거) 이후의 두 런**이다.

즉 과거의 pending 38·31·30 은 주입이 아니라 **B 결함이 만든 부하 오염**이었고,
**이전의 통과는 거짓 통과였다.** 사다리를 끝까지 올려도(`disk_io_util` 84%, 5단 소진) pending 0,
`transfer_2xx_rate` 는 0.800 아래로 안 내려간다.

**선택지**
- (a) 주입을 Oracle 이 실제로 쓰는 디스크로 향하게 한다(현재 IO 압박이 DB 경로에 닿는지 확인 필요)
- (b) 성공 조건을 디스크 압박이 실제로 만드는 신호로 바꾼다
- (c) 시나리오 폐기

**내 권고: (a) 를 먼저 확인.** "디스크 포화 → DB 지연"은 실제 장애에서 흔한 사슬이라 시나리오
자체는 가치가 있다. 다만 지금 주입이 DB 데이터 경로에 닿지 않을 가능성이 높으니 그것부터 재야 한다.
닿지 않는 것으로 확인되면 (b).

## 7. F15-P — escalate 와 must_rule_out 이 같은 신호를 같은 방향으로

**막는 것**: 두 게이트가 같은 관측을 같은 방향으로 굴리는데 평가 순서가 `must_rule_out` → `escalate`
이므로 **승격이 구조적으로 불가능하다.**

**선택지**
- (a) `escalate` 를 다른 신호로 바꾼다
- (b) `must_rule_out` 의 임계를 `escalate` 보다 확실히 바깥으로 옮긴다
- (c) 평가 순서에 예외를 둔다 — **권하지 않음**(41종 전체에 영향)

**내 권고: (a) 또는 (b).** 어느 쪽이든 "이 시나리오가 승격으로 무엇을 확인하려 했는가"를 먼저
정해야 한다. 그 답 없이는 둘 중 하나를 고를 수 없다.

## 8. F20-R — 임계가 도달 불가

**막는 것**: `payment_p95 >= 500` 인데 게이지 최대가 **269~302ms**(6런 이상 일관).

**선택지**
- (a) 임계를 실측 분포에 맞춰 재보정(예: p95 의 평시 대비 배수로)
- (b) 주입을 강화해 500ms 를 넘게 한다
- (c) 다른 피해 신호로 교체

**내 권고: (a)+(b) 중 어느 쪽이든 좋으나 순서가 중요하다.** 먼저 **평시 분포를 재고**(현재 정상
구간의 `payment_p95` 가 얼마인지), 주입 시 그 대비 몇 배가 되는지를 본 다음 임계를 정해야 한다.
절대값 500 을 어디서 가져왔는지 근거가 레지스트리에 없다.

## 9. F09-R · 10. F03-P — parked 권고 (재설계 대 폐기)

두 종 모두 **네 배치 연속 스킵**이고 인과 사슬이 성립하지 않는다.
- **F09-R**: 노드 CPU 99.9% 인데 pricing 12.8 — 압박이 대상 서비스에 닿지 않는다
- **F03-P**: payment 1,614ms 인데 checkout 5xx 가 전 틱 0 — 지연이 사용자 피해로 이어지지 않는다

**선택지**: 재설계 / 폐기 / 보류 유지

**내 권고: 이 둘은 폐기 또는 장기 보류.** 41종 중 두 종을 살리려고 매 배치 40분 이상을 쓰고 있고,
둘 다 "주입은 되는데 피해가 안 생긴다"는 같은 성격이다. 살리려면 **주입 지점 자체를 바꿔야 하므로**
사실상 새 시나리오를 만드는 일이다. 다음 주 목표가 "모든 시나리오가 문제없이 돈다"라면,
이 둘을 라이브 집합에서 빼는 것이 목표에 가장 빠르게 닿는 길이다.

**39종 중 37종**이 통과 가능한 상태가 된다(D4·D5·D6 은 측정이 선행되어야 해서 다음 주기).
