# APM error_rate 단위 결함 — ready 13종 임계가 100배 어긋나 있다 (2026-07-29 실측)

`observation-defect-class-0728`("주입은 멀쩡한데 판정하는 쪽이 틀림") 계열의 확장.
그때 발견된 7건보다 넓다 — **ready 13종 전부**가 걸린다.

## 사실

`prometheus.apm_service_error_rate` → 템플릿 `apm-agent-error-rate-v1` →
`max without(grade) (apm.agent.otel.java.error_rate{service_name="%s"})`.

이 메트릭은 **0~100 백분율**이다. 119:18428 48시간 이력의 고유 비영값:

```
commerce-order    [50.0, 66.667, 100.0]
commerce-payment  [33.333, 50.0, 66.667, 75.0, 100.0]
```

1/3·1/2·2/3·3/4·1 을 백분율로 찍은 값. 분수라면 상한이 1.0이어야 한다.

러너에 정규화가 없다 — `live_probes.py::_prometheus_observation`은 `numeric < 0`과
유한성만 검사하고 원값을 그대로 게이트에 넘긴다. loadgen 계열에 있는
`value > 1 → LiveProbeError` 상한 검사는 prometheus 경로에 **없다**.

틀렸다면 일괄 곱셈으로 끝나지만, 그렇지 않으므로 게이트별로 의도를 확정해야 한다.

## 교정 결과 (2026-07-29 완료)

의도 %는 **이웃 게이트가 증언한다**. 모든 APM 임계가 진짜 0~1 스케일인 loadgen rate와
나란히 놓여 있다 — 예: F01-P는 `payment_error_rate gte 0.1` 옆에 `checkout_5xx_rate gte 0.05`.
작성자가 같은 분수 스케일로 썼다는 뜻이므로 교정은 **일괄 ×100**이고, 표의 "의도 추정"이
그대로 확정값이 됐다.

정본은 `registry/controllers.json`이고 매니페스트는 `generate-manifests.py`가 생성한다.
레지스트리만 고치고 재생성했다 — 값 21개(live 15 + parked 6)만 바뀌고 포맷은 보존.

- live 15건: F01-P·F06-H·F08-P·F17-R·F19-P·F19-S·F20-Q·F20-R·F21-P·F21-Q
- parked 6건: F07-P(3)·F20-P(3) — 승격 때 결함이 되살아나지 않도록 함께 교정
- F12-H(`gt 0`)는 단위 무관이라 불변

**재발 방지**: `test_rate_thresholds_are_stated_in_the_metric_unit` 신설.
07-28 ms/s 사고 때 만든 `test_latency_thresholds_are_stated_in_the_metric_unit`과 같은 자리·같은 형태.
비영 임계가 1 미만이면 분수 오작성으로 보고 실패시킨다. parked까지 병합해 검사하므로
승격 경로로도 재유입되지 않는다. 값을 0.3으로 되돌려 실제로 실패하는 것까지 확인했다.

## 남은 것

- **`design-*.json`(wip) 20여 건은 여전히 0~1이다.** 설계 시점 기록이라 그대로 두었다.
  승격 시 controllers.json으로 옮겨질 때 위 가드가 잡는다 — 방어선은 레지스트리다.
- **죽은 must_rule_out 규칙 3건**(단위와 무관한 기존 결함). F19-P·F20-Q의 `payment-5xx-cascade`,
  F20-R의 `payment-service-down`은 값이 20인데 같은 `any` 블록의 `payment-also-erroring`이 5다.
  `>=5`가 `>=20`을 완전히 포섭하므로 20 규칙은 **발동할 수 없다**. 교정 전에도(0.2 vs 0.05)
  마찬가지였다. 이름이 캡처·정답지에 남는 규칙이라 임의로 지우지 않고 남겨 둔다 —
  "cascade와 also-erroring을 구분해 기록할 것인가"는 설계 판단이다.

## 교정 시 결정한 것

1. **의도 %를 시나리오별로 확정** — 위 표의 "의도 추정"은 문서가 아니라 추론이다.
   각 매니페스트의 설계 시트·정답지에서 근거를 찾아 확정한다.
2. **단위를 어디서 맞출 것인가** — 두 갈래.
   - (a) 매니페스트 임계를 백분율로 재작성 (`0.1` → `10`). 변경 지점이 13곳으로 분산.
   - (b) 러너가 프로브 단계에서 /100 정규화. 변경 1곳이지만 이미 기록된 캡처의
     의미가 바뀌고, 다른 0~1 지표들과의 일관성을 별도로 확인해야 한다.
   - 권고 = (a). 메트릭의 실제 단위를 숨기지 않는 쪽이 정직하고,
     "지표에 직접 물어본 값이 정본"이라는 07-28/29 원칙과 맞는다.
3. **상한 검사 신설** — prometheus 경로에도 값역 검사를 넣어 다음 단위 사고를
   프로브 단계에서 잡는다. 단 `error_rate`는 0~100이고 다른 prometheus 쿼리는
   단위가 제각각이므로 쿼리별 값역을 레지스트리에 선언하는 형태여야 한다.

## 부수 실측 (같은 세션)

- **APM은 4xx를 관측 신호로 쓸 수 없다.** 404 60건·정상 200 60건을 각각
  1 rps로 보냈으나 `apm.agent.otel.java.rps`가 잡음 범위(0.017~0.2)를 벗어나지
  않았다 — 평균 창이 길어 소량 버스트가 흡수된다. 4xx 집계 여부와 무관하게
  **429 계열 arm은 부하 문서(loadgen)로만 관측 가능**하다.
- `_loadgen_live_document()`는 `/tmp/rca-scenario-<id>-live.json` **시나리오당 한 문서**를
  읽고 `load.north_south`는 **시나리오당 도메인 하나**다. 두 도메인의 부하 지표를
  동시에 요구하는 시나리오(F15-H·F15-T2)는 현행 계약으로 불가능 — 이것이
  매니페스트에 적힌 "food dispatch baseline" 사유를 대체하는 진짜 블로커다.
