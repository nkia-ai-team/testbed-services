# F57-R 설계 시트

## 1. 요약

banking 의 transfer-service 는 모든 이체를 Oracle `BANKING.TRANSFERS`(2026-10-10 109 실측 최대 키 6,485,033, 약 638만 행)에 둔다. 키 `ID` 는 `GENERATED BY DEFAULT AS IDENTITY`(생성기 `ISEQ$$_73040`, 캐시 20)이고 기본 키 `SYS_C008658` 이 지킨다. 운영자가 이 표를 옮기는 이전 작업을 했다: 스냅숏에서 새 표를 만들고 그 뒤 쌓인 행은 따라잡기로 모두 옮겼는데, 표의 값과 달리 identity 생성기의 상태는 옮겨지지 않았다. 전환은 원본처럼 표를 잠깐(약 6초) 읽기 전용으로 둔 뒤 쓰기를 다시 여는 것이었다. 읽기 전용 동안 이체는 INSERT 에서 `ORA-12081: update operation not allowed on table "BANKING"."TRANSFERS"` 로 실패하고 거래 내역(읽기)은 된다. 쓰기가 열린 표의 생성기는 스냅숏 시점 값에서 다시 시작한다. 이번 재구성에서 스냅숏 시점은 약 5일 전(이체 약 40만 건 전)이다.

쓰기가 열린 순간부터 새 이체는 모두 이미 있는 키를 받는다. 이체(`POST /api/transfers`)는 banking 고객 쪽(nginx → api → account → transfer)이든 commerce checkout 의 정산(commerce-payment → transfer)이든 두 계좌를 `FOR UPDATE` 로 잠그고 잔액을 고친 뒤 transfers INSERT 에서 `ORA-00001: unique constraint (BANKING.SYS_C008658) violated on table BANKING.TRANSFERS columns (ID)` 와 `ORA-03301: (ORA-00001 details) row with column values (ID:6085034) already exists` 로 실패한다. 트랜잭션이 되돌려져 잔액은 움직이지 않고 transfer 는 수십 ms 안에 500 으로 답한다. account 는 재시도 뒤 서킷을 열고 502, api 도 502, commerce-payment 는 정산 실패를 502 로 바꿔 commerce checkout 이 실패하고 예약 재고를 풀어 준다. 실패한 시도마다 생성기는 한 칸씩 나아가므로 오류 문장의 'ID:N' 이 하나씩 커지지만, 다시 시작한 자리부터 최대 키 - 1000 까지(가장 새 1000 키는 커밋 전 거래의 것일 수 있고 되감은 생성기가 거기까지 가지 않음) 키가 모두 차 있어(읽기 전용 구간 뒤, 아무것도 쓰일 수 없을 때 다시 확인) 빈 키를 만나지 않는다.

이 표에서 읽는 것과 이 표를 부르지 않는 것은 그대로다: 거래 내역(`GET /api/transfers`), 1분마다 도는 보존 정리 배치(오래된 행 지우기), 잔액 조회와 계좌 목록(nginx → account), 원장, outbox 릴레이. 표의 행, 인덱스, 제약은 그대로이고 롤아웃도 재시작도 없다. Oracle 은 떠 있고, transfer 는 Ready 이며 풀도 비지 않는다.

비유: 송금 장부를 새 바인더로 옮겨 적으면서 기존 쪽은 다 옮겼는데, 다음 쪽 번호를 매기는 넘버링 도장은 5일 전 숫자로 돌려놓은 채 두었다. 창구 직원이 새 송금을 적으려고 도장을 찍으면 이미 있는 쪽 번호가 나와 장부 규칙(같은 쪽 번호 금지)에 걸려 송금을 거절한다. 장부를 읽는 일(거래 내역)과 잔액 조회는 멀쩡하다.

## 2. 원본 사례

- 기업: RevenueCat (앱 구독 결제 인프라)
- 날짜: 2022-11-23 (UTC 9:34 옛 클러스터 읽기 전용, 트래픽 전환과 장애 시작, 13:07 대시보드와 SDK 끝점 100% 회복)
- 링크: [Postmortem for Aurora Postgres Migration November 23 2022 (공식 엔지니어링 블로그)](https://www.revenuecat.com/blog/engineering/postmortem-aurora-postgres-migration) (자료 문서 `ref-real-world-incidents.md` M21 에 이번에 추가)
- 요약(출처가 말한 것만): Aurora Postgres 10 에서 14 로 올리려고 스냅숏에서 새 클러스터를 만들고(2:51) 논리 복제로 따라잡은 뒤(8:51) 9:34 에 옛 클러스터를 읽기 전용으로 두고 트래픽을 넘겼다. 연쇄 장애 가운데 하나가 기본 키 중복이었다: "We did not realize that the state of sequences would not be copied to the databases." PostgreSQL 논리 복제는 표 값은 옮기지만 시퀀스 상태는 옮기지 않아 "For a handful of large tables, we ended up with primary key sequences running into their values", 이미 표에 있는 행의 유일 제약을 위반했다("violating unique constraints for rows already in the tables"). 미리 준비한 스크립트로 해당 시퀀스 값을 자동으로 올려 빠르게 완화했다. 교훈에 "Missing sequence replication limitations: Assume that the state was replicated as well." 과 시험 이전이 쓰기 트래픽을 재생하지 않아 이 문제를 드러내지 못했다는 점을 적었다. (같은 사고의 주 원인은 새 클러스터에 ANALYZE 가 돌지 않은 질의 계획 문제였고, 이번 재구성은 그중 기본 키 중복 고리만 쓴다.)

기전은 원본과 같다: "표 이전이 행은 옮기고 키 생성기 상태는 옮기지 않음 → 생성기가 이미 쓰인 키를 다시 내줌 → 기본 키가 새 행을 거절해 그 표에 쓰는 요청이 모두 실패 → 생성기를 최대 키 뒤로 올리면 회복". 우리 스택에 맞춘 것은 엔진(Postgres 시퀀스 → Oracle identity 생성기)과 규모(표 하나)다.

재구성의 경계: 이전 작업 중 행 복사(약 638만 행, 784MB)는 다시 하지 않는다. 전환과 그 결과는 재현한다: `ALTER TABLE BANKING.TRANSFERS READ ONLY`, 6초 유지(원본의 '옛 쪽 읽기 전용, 쓰기는 2분 안 되게 실패'), `ALTER TABLE BANKING.TRANSFERS MODIFY (ID GENERATED BY DEFAULT AS IDENTITY (START WITH <최대 키 - 400000 + 1>))`, `ALTER TABLE BANKING.TRANSFERS READ WRITE`. 행, 인덱스, 제약은 그대로다. 400000(약 5일치)은 스냅숏에서 전환까지 걸린 시간으로 둔 값이고, 그 자리부터 최대 키 - 1000 까지(가장 새 1000 키는 커밋 전 거래의 것일 수 있고 되감은 생성기가 거기까지 가지 않음) 키가 모두 차 있음을 실행 직전과 읽기 전용 구간 뒤(표가 멈춘 최대 키로) 두 번 확인한다(109 실측: 최근 100만 키 중 최대 키 쪽 70만이 5만 단위로 모두 50000, §4). 두 번째 확인이 실패하면 표를 쓰기 가능으로 되돌리고 멈춘다.

(1차 평가 FAIL 반영, 2026-10-10: 처음 재구성은 ALTER 한 문장(생성기 되감기)뿐이어서 원본의 계기인 전환(옛 쪽 읽기 전용, 쓰기 실패 구간, 트래픽 전환 시점)의 흔적이 녹화 창에 하나도 남지 않았고, 정답지는 오히려 '그 시각에 다른 변경 없음' 을 지지 근거로 내세워 이야기와 데이터가 어긋났다. 평가의 지적이 맞다. 전환 앞 읽기 전용 구간을 실제로 만들어, 같은 INSERT 가 약 6초 ORA-12081 로 실패한 뒤 ORA-00001 로 바뀌는 두 구간이 로그에 남게 했다. 같은 평가의 권고도 반영했다: 키 구간 확인을 5만 칸에서 되감는 40만 칸 전체로 넓힘, 조회 실패가 '앞/뒤' 판정을 통과시키지 않게 수를 숫자인지 확인하고 아니면 멈춤(fail-closed), DDL 이 ORA-00054 로 끝나면 다섯 번까지 다시 시도, user_rollbacks 는 평시 7일 최대 58.97 이라 보조 증거로만 씀.)

(2차 평가 FAIL 반영, 2026-10-10: 1차 반영 판은 run 이 읽기 전용 90초를 기다렸는데, run 은 러너 coordinator lock 을 쥔 채 돌고 lease 가 30초라 apply 중 lease 가 끝나 watchdog 이 cleanup 을 가져간다(k8s_env_executor 의 2026-08-04 실측 '58초 대기로 lease 만료' 와 같은 벽). 평가의 지적이 맞다. 평가가 낸 두 길 가운데 상태 파일과 분리된 작업자가 필요 없는 (b) 를 골랐다: 읽기 전용 구간을 6초로 줄이고 run 의 DDL 대기와 재시도를 묶어 run 최악 시간을 약 21초로 두었으며 그 상한을 단위 테스트로 고정했다. 원본의 '쓰기는 2분 안 되게 실패' 안이고 ORA-12081 흔적은 짧아도 남는다(로컬 26건). 같은 평가의 권고대로 '롤아웃, 재시작 없음, USERS 그대로' 를 정답지 must_support 에서 must_rule_out(배제용)으로 옮기고, 되감는 구간 행의 날짜를 109 실조회 값으로 고쳤다. 1분 주기 보존 정리 배치는 6초 창에 걸리는 일이 드물어 그 ORA-12081 WARN 은 must_support 에 넣지 않았다. 고친 판을 109 에서 preflight 로 돌리다 한 번 1 이 나와 두 경쟁을 찾아 고쳤다: 키 구간 확인은 아직 커밋되지 않은 가장 새 1000 키를 빼고(되감은 생성기는 약 1.4만 키만 써 거기까지 가지 않는다), 생성기가 앞인지 볼 때는 최대 키를 먼저 읽는다(반대 순서는 그 사이 캐시 블록이 넘어가면 거짓이 된다). 그 뒤 109 preflight 12번 모두 0, 로컬 preflight, run(8.7초), cleanup 두 번, recovery 모두 기대대로.) 되돌리기는 원본의 '시퀀스 값 올리기' 그대로 `START WITH LIMIT VALUE`(표의 최대 키 다음으로)다. 상태 파일이 필요 없다.

관계와 id: 원본(RevenueCat 2022-11-23)과 기전(키 생성기 상태가 데이터와 어긋남)이 기존 시나리오 어디에도 없어 새 사례군 F57 의 R 이다. 같은 표의 F35-H(표 지움)와 겉 증상(이체와 commerce 정산 실패)이 같지만 원본, 원인 꼴, 수단 모드, 오류가 다르다. 같은 수단(db.ddl)이지만 새 모드(Oracle identity 되감기)와 새 파라미터라 같은 주입 중복이 아니다. rejected 의 '(사례 없음) banking Oracle 백필 명시 id → ORA-00001' 은 공식 사례가 없어 막혔던 것이고, 이번 후보는 공식 사후 보고(RevenueCat)의 기전(시퀀스 상태 미이전)을 그대로 따른다(명시 id 백필이 아니다).

묶음 해석: 바뀐 것은 표의 키 생성기 상태 하나다. 설정값 배포가 아니라 G 가 아니고, 코드나 이미지 배포가 없어 J 가 아니다. 운영 작업의 대상은 맞았고(옮기려던 표) 빠뜨린 것이 작업 내용(생성기 상태)이라 대상 착오인 P 가 아니며, 표가 사라진 것도 아니다. 계획된 스키마 변경과 코드의 순서 문제(L)도 아니다(스키마와 코드는 그대로). 계정(O), 잠금(D), 자원(A), 질의 비용(F)도 그대로다. 그래서 Q 를 새로 정의한다: "데이터 이전, 복원, 복제 전환에서 표 데이터와 함께 가야 할 부속 상태(식별자 생성기, 카운터)가 따라오지 않아 새 쓰기가 기존 데이터와 충돌함". 현실 근거는 RevenueCat 2022-11-23 과 M21 의 이전 작업 사례다.

계기의 흔적: 계기는 표 이전의 전환이고, 그것은 로그에 두 구간으로 남는다. 먼저 약 6초 같은 transfers INSERT 가 'ORA-12081: update operation not allowed on table "BANKING"."TRANSFERS"' 로 실패하고 같은 시각 같은 표를 읽는 거래 내역은 성공한다(표 하나가 쓰기를 막은 전환 구간, 평시 0건). 이어서 쓰기가 열린 첫 INSERT 부터 오류 문장이 'TRANSFERS 의 ID 기본 키에 이미 있는 행 (ID:N)' 을 말하고 N 이 시도마다 하나씩 커진다. INSERT 는 키를 생성기에 맡기므로(`values (...,default)`, 같은 ERROR 의 SQL 에 보임) 새 행의 키가 이미 있다는 것은 생성기가 데이터 뒤에 있다는 뜻 말고는 설명되지 않는다(정상 생성기는 이미 내준 키를 다시 내주지 않는다). 중복 요청이라면 기본 키가 아니라 transfer_ref 의 유일 제약(SYS_C008659)이 걸린다. 전환 문장(ALTER) 자체는 Top SQL 에도 Oracle 지표에도 남지 않는다(DDL 문장 미수집, 시퀀스 지표 없음). 롤아웃, 재시작, 표 공간 변화가 없다는 것은 다른 원인(F35-H, F52-R 등)을 배제하는 데만 쓰고 계기의 근거로 쓰지 않는다. 인공 지연은 없다.

원칙 8 참고: 실행기는 기존 Oracle 실행기(F14-P, F35-R, F35-H)처럼 파드 안 SYSDBA sqlplus 로 접속해 DPM 세션 표본에 'sqlplus@testbed-oracle-0' SYS 세션이 잡힐 수 있다. 시나리오 id 와 SQL 은 남지 않는다.

## 8. 감별

- must_support: 약 6초 transfer WARN 'SQL Error: 12081, SQLState: 99999' + ERROR 'ORA-12081: update operation not allowed on table "BANKING"."TRANSFERS"'(그동안 거래 내역 200), 이어서 transfer WARN 'SQL Error: 1, SQLState: 23000' + ERROR 'ORA-00001: unique constraint (BANKING.SYS_C008658) violated on table BANKING.TRANSFERS columns (ID)' 와 'ORA-03301 ... row with column values (ID:N) already exists'(이체마다, N 이 하나씩 커짐), 'Transfer COMPLETED' 멈춤, account 'Transfer service call failed ...: 500' 과 서킷 열림, api 502, commerce-payment 실패, commerce-order 'Checkout payment failed', 거래 내역과 잔액 조회 두 구간 내내 200, 롤아웃과 재시작 없음(배제용), transfer 와 Oracle Ready, USERS 사용량 그대로. DPM user_rollbacks 상승은 보조.
- must_rule_out: F35-H(ORA-04043/00942, 거래 내역도 실패, USERS 사용량 급락), F38-R 꼴 DB 전체 읽기 전용(모든 쓰기가 창 내내 실패, 여기서는 이 표만 6초 뒤 기본 키 충돌로 바뀜), F35-R(ORA-28000, 풀 비움, 잔액 조회도 실패), F01-P(대기 뒤 시간 초과, 차단 세션), transfer 파드 소실(F17-H, F50-R, F51-R, F52-R), transfer 새 버전(F40-H, F42-R: 롤아웃, 앱 검증 오류), Oracle 다운이나 포화(F25-H 꼴), 중복 요청(같은 transfer_ref 의 유일 제약 SYS_C008659 가 아니라 기본 키 SYS_C008658 이다).
- contrast_with: F35-H, F35-R, F01-P, F52-R(정답지 `related_scenarios`).

가르는 관측 근거 한 줄: 같은 INSERT 의 오류가 약 6초 ORA-12081(표 읽기 전용) 뒤 Oracle 의 ORA-00001 로 바뀌고, 그 문장이 TRANSFERS 의 ID 기본 키와 이미 있는 키 값을 가리키며, 같은 표의 읽기(거래 내역)와 같은 Oracle 의 다른 표, 모든 파드, 풀, 세션, 표 공간이 정상이다.

## 9. 러너 판정 조건과 강도, 부하

- 주입: db.ddl(Oracle identity 되감기 모드) 1단 고정(`approved-fixed-f57-r`, rewind_rows 400000, read_only_seconds 6). run 은 러너 coordinator lock 을 쥔 채 돈다(`scripts/scenarios/profile-control.py:281-296`). 러너 lease 는 30초이고 heartbeat 가 멎은 채 30초를 넘기면 watchdog 이 cleanup 을 가져가므로(`k8s_env_executor.py:112-116` 의 2026-08-04 실측 기록과 같은 벽), run 안의 모든 대기를 묶었다: 읽기 전용 6초, run 의 DDL 은 ddl_lock_timeout 2초에 1초 간격 최대 두 번, run 이 내는 DDL 은 많아야 셋(읽기 전용, 되감기와 쓰기 열기, 실패 때 쓰기 열기). 최악 6 + 3 × (2 × 2 + 1) = 21초에 조회 몇 개(109 preflight 전체 1.6초)라 lease 안이다. 로컬 실측 10.7초(부하 중), DDL 잠금 경합 때 6.7초에 실패로 끝나고 표는 원래 상태(위 §4). 이 상한은 단위 테스트가 고정한다. 강도 축이 없다: 읽기 전용 동안과 생성기가 꽉 찬 키 구간에 있는 동안 모든 INSERT 가 요청량과 무관하게 실패한다.
- 창 계산: 실패한 시도마다 키 하나를 쓴다. 기준선 이체 0.81/s 와 동반 부하 이체 약 2/s 가 account 재시도(최대 3회)를 거치고 commerce 정산 약 0.6/s 를 더하면 초당 약 9개, 25분이면 약 1.4만 개로 확인한 40만 칸 안이다.
- 동반 부하: load.north_south `core-banking transfer-heavy-surge.js` 5rps(이체 40%, 잔액 35%, 거래 내역 15%, 목록 10%), ramp 2m, hold 21m, entry 30082(F35-H, F51-R, F52-R 과 같은 스크립트와 세기). 부하 상한 180 의 3%.
- 피해 계산(원칙 9): 실패가 시간 초과가 아니라 즉시 나는 SQL 오류라 서킷브레이커는 실패를 빠르게 만들 뿐이다(account, api 서킷 열림 → 502). 상주 commerce 부하의 checkout 이 정산마다 실패한다(분당 약 36건).
- success: 동반 부하 이체 5xx 비율 ≥ 0.5, 3틱.
- must_rule_out: achieved_rps < 1.25, 잔액 조회(step get) 실패율 ≥ 0.2(account 나 Oracle 전체 장애), Oracle 파드 NotReady, transfer 파드 NotReady, transfer 재시작 ≥ 2.
- abort: entry_status == 0(nginx 나 노드가 죽음).
- recovery: target_health 200, Oracle Ready, transfer Ready, 기준선 이체 5xx < 0.05, 2틱, 10m.
- cleanup: 표가 읽기 전용이면 `READ WRITE`, 생성기가 뒤에 있으면 `ALTER TABLE BANKING.TRANSFERS MODIFY (ID GENERATED BY DEFAULT AS IDENTITY (START WITH LIMIT VALUE))`(DDL 마다 ddl_lock_timeout 5초, 두 번까지), 그 뒤 원래 상태(쓰기 가능, 생성기가 최대 키 앞, 기본 키) 확인, 부하 종료. 이미 원래 상태면 아무것도 하지 않는다. run 이 읽기 전용 구간 중에 끊겨도 cleanup 이 쓰기를 연다.
