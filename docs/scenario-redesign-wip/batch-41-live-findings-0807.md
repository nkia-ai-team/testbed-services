# 41종 라이브 배치 결함 기록 (2026-08-06~07 진단·수리)

파킹 3종을 뺀 ready 41종 기준. [08-04 배치](batch-44-live-findings-0804.md)가
남긴 실패·스킵을 run 아티팩트와 트레이스 직독으로 되짚은 사이클이다.

이번 사이클에서 확인된 것 셋.

**하나, 실패의 다수는 주입이 아니라 판정과 환경이었다.** 수리 10건 중 8건은 주입도
피해도 실증된 상태에서 판정 계약이 못 받아준 것이고, 나머지는 사다리가 성공 구간을
건너뛴 것이다. "주입이 안 된다"는 진단은 이번에 한 건도 없었다.

**둘, 통과 이력이 있어도 신뢰할 수 없는 조건이 있었다.** F19-P·F19-S의 성공 조건은
주입과 무관한 dispatch 노이즈(0.098)만으로 임계(0.1)에 닿을 수 있었다 — 아깝게 못
넘는 실패가 아니라 **주입 없이도 성립 가능한 거짓 양성 구조**다. 데이터셋 품질에
직결되므로 통과 여부와 별개로 틀린 조건이었다.

**셋, 층이 한 칸 더 내려갔다.** 08-04에는 시나리오·러너 층이 주였는데, 이번에는
테스트베드 **환경 자체**의 자립성 결함 2건(commerce 재고 고갈, banking transfer
flapping)이 여러 시나리오의 판정을 동시에 오염시키고 있었다. 시나리오를 아무리
고쳐도 그 아래가 흔들리면 결과가 흔들린다.

## 1. 전역 판정 결함 — APM 백분위의 표본 없는 창이 0.0으로 들어온다

**이 사이클에서 가장 파급이 큰 항목이다.** 시나리오 하나가 아니라 prometheus
`apm_service_p95`를 판정에 쓰는 모든 시나리오가 영향을 받는다.

트래픽이 없거나 스팬이 안 잡힌 창에서 APM 백분위 질의는 값 없음이 아니라 **0.0**을
반환하고, 러너는 그것을 `usable: true`로 받는다. 그리고 adaptive의 streak 갱신은

```
if result is not True: updated[name] = 0
```

이라 0.0이 만든 False 한 번이 **연속 카운터를 통째로 리셋**한다. 즉 밑 신호가 내내
나빠도 표본이 한 번 비면 연속 요건이 구조적으로 성립하지 않는다.

### 증거 — F20-R run fa6749a8

원본 15초 시계열(ms)에는 진동이 없다:

```
39389 / 46503 / 30016 / 20466 / 30010 / 30008 / 33988 / 30005 / 19981 / 27992
```

그런데 틱 값에는 0.0이 섞인다. 그 0.0이 나온 분(05:09·05:14·05:17)은 payment
스팬이 **0건**인 분과 정확히 대응한다. 신호가 좋아진 것이 아니라 **표본이 없었던
것**이고, 판정은 그것을 "임계 미달"로 읽었다.

### 같은 병으로 의심되는 것

F10-H의 "톱니형 p95"(#5)가 같은 계열로 보인다. run 748dd9c8에서 disk가
75·77·75·76으로 포화인 동안 order_p95 독립 표본이 797ms와 7691ms 사이를 오갔고
success streak이 1에서 올라가지 못했다. #5의 수리는 p95를 성공 게이트에서 빼는
쪽이라 이 병을 피해 가지만, **회피이지 치료가 아니다.**

### 조치와 순서 의존

수리는 rca-scenario-runner에서 별도 에이전트가 진행 중이다(표본 없는 창을 값이
아니라 `unusable`로 표시). **F20-R의 새 사다리(#14)는 이 수리가 배포된 뒤에
돌려야 한다** — 그 전에는 0.0 아티팩트가 escalate를 즉시 발화시켜 사다리가
최상단까지 헛돈다.

## 2. 환경 자립성 결함 2건

시나리오 결함이 아니라 테스트베드가 스스로를 유지하지 못하는 문제다. 둘 다 여러
시나리오의 판정을 동시에 오염시키고 있었다.

### 2a. commerce 재고 상시 고갈 (수리 `52f23b6`)

`ReconciliationBatch`는 10분마다 `stock < 20`인 상품만 `target 200`으로 채운다.
그런데 상주 부하의 소비는 **~110 units/min**이다(원장 분당 집계 40분 실측).
평균 공급은 맞지만 **버스트**라 주기 끝마다 전 상품이 마른다 — 08:07 시점
flagship 16종 전부 `stock=0`을 DB 직독으로 확인했다.

재고가 0인 구간에서는 checkout이 payment에 닿기 전에 409로 걸러진다
(`OrderService.checkout`은 `reserveStock`을 payment보다 먼저 호출한다).

피해:
- **F05-R** (run 95b07798): 01:11~01:14:30 창구에서 checkout **142건 전부 409**,
  `payment_reqs` 0. payment가 OOMKilled를 3회 냈는데도 `checkout_5xx_rate`가
  런 내내 0.0이라 성공이 서지 못했다. 관측 배선은 정확했고 **피해가 실제로 0**이었다.
- **F25-H** (run af660719): 레벨 전환 recovery가 이 409 flakiness에 걸려 dirty.

수리: 주기 600s→60s, target 200→60, threshold 20 유지. 주기를 줄이는 것이
"0에 닿지 않음"을 만들고, target을 줄이는 것이 F23-R의 성립을 운에서 결정론으로
바꾼다(#12).

**세 파라미터는 서로 당긴다.** `ReconciliationBatch` javadoc에 제약을 남겼다:
① 평시 0 미도달 = `threshold > 상품당수요 × 주기` ② F23-R 결정론 = 풀(16×target)이
min_hold 안에 마를 것 ③ restock 감별자 = 룩백 창이 주기에 비해 너무 넓지 않을 것.
하나만 바꾸면 다른 데서 깨진다.

기본값은 **코드에만** 뒀다. 배포 매니페스트 env로 올리면 F23-R이 k8s.env로 잡아둔
baseline 환경변수 배열(정확히 11개, 매니페스트와 바이트 일치)이 달라져 승인된
계약이 깨진다. 주입(`SPRING_APPLICATION_JSON`)은 코드 기본값을 그대로 덮으므로
계속 동작한다.

### 2b. banking transfer flapping (수리 `dec83d4`)

`testbed-transfer`의 SIGKILL(137) 반복은 자원 부족이 아니라 구조 결함이었다.
체인은 릴레이에서 시작해 헬스 프로브에서 끝난다:

```
@Transactional relay()가 루프에서 최대 100건을 kafkaTemplate.send(...).get()으로
순차 대기 → producer 타임아웃 미설정이라 건당 최대 delivery.timeout 120s
→ 그 시간 내내 Hikari 커넥션 점유 → transfer 풀(15) 고갈
   (실측: total=15 active=15 waiting=1, 획득 6105ms 타임아웃)
→ DataSourceHealthIndicator가 같은 풀을 타서 /actuator/health가 probe timeout 3s 초과
→ livenessProbe 실패 누적 → SIGKILL
```

수리: 발행을 트랜잭션 밖으로(짧은 읽기 → 트랜잭션 밖 발행 → 성공분만 짧은 배치
UPDATE), Kafka producer 타임아웃 명시(request 5s / delivery 15s / max.block 5s),
liveness를 DB에서 분리(`/actuator/health/liveness`), transfer 힙 `-Xmx512m` 명시.
readiness는 `/actuator/health`를 그대로 본다 — F17-R의 승인된 스냅샷이 그 블록이다.

## 3~12. 판정 계약 수리 10건

전부 run 아티팩트의 틱 증거로 확정했다.

### 3. F16-H — min_hold가 신호 생존 창 밖이었다 (`5178218`)

run aea47b5c: `write_401_rate`가 31초부터 252초까지 **1.0으로 15틱 연속**,
success streak이 8까지 갔는데 판정 사유가 내내 `min_hold`였다. 조건은 진작
충족됐는데 창이 안 열린 것이다. 267초에 baseline loadgen이 로그인 불능이 되며
신호가 0.0으로 붕괴, 13m 레벨 타임아웃까지 끝내 돌아오지 않아 failed.

min_hold 8m→**150s**. 붕괴 이전 창 안에서 3연속(필요 45s)을 확정한다.

**남은 결함(미수리)**: 신호가 죽은 뒤의 0.0이 `usable=true`로 들어와 '성공 조건
미달'과 구분되지 않는다. #1과 같은 계열의 관측 평면 문제라 이번에 건드리지 않고
컨트롤러 주석으로만 남겼다.

### 4. F20-Q — 유효 평가 틱이 물리적으로 하나였다 (`5178218`)

run 543dda48: `evaluating` 페이즈 틱이 **1개**뿐이다. 31초 틱에서 메모리 867MB·
주문 생성 5xx 0.6으로 두 조건이 동시에 서고(streak 1), 46초 틱에는 이미 파드가
죽어 `entry_status` 0·5xx `usable=false`다.

success `consecutive_ticks` 2→**1**. 1틱이 정당한 근거는 둘이다 — gate가 서로 다른
평면의 독립 신호 AND(k8s 컨테이너 메모리 · k6 주문 생성 5xx)라 단일 틱도 우연
일치가 아니고, 죽기 전 물리적 창이 1틱뿐이다.

### 5. F10-H — 피해는 실증됐고 실패한 건 판정이다 (`f60c903`)

run 748dd9c8: `order_create_5xx_rate`가 세 레벨 내내 **0.90~0.99로 안정**,
`disk_io_util`도 62~87을 오갔다. 피해와 원인이 둘 다 서 있었는데
`calibration_levels_exhausted`로 끝났다.

원인은 신호 선택이다. `order_p95`는 `update_interval 60s`라 gate 전체를 60초
페이스로 묶고(러너는 틱이 아니라 독립 표본을 센다), 그 표본이 797ms와 7691ms
사이를 톱니로 오가 2500 이상 3연속이 한 번도 서지 않았다. 같은 레벨에서 disk가
75·77·75·76으로 포화인데 success streak이 1에서 못 올라간 틱들이 그 증거다.

피해 신호를 `order_create_5xx_rate >= 0.5`(30s 케이던스)로 교체.
`device-saturated` 임계 70→**60**(최상위 레벨에서 69·66·66 같은 골이 3연속 창을
계속 깼다. 러너 문법에 M-of-N이 없어 연속 계약은 유지하고 임계를 실측 골 아래로
내렸다). escalate의 `device-not-yet-saturated`도 같이 60으로 — 어긋나 있으면
disk 60~69에서 성공과 승급이 동시에 참이 되어 서로를 잡아먹는다.

### 6. F03-H — 근접 실패, rps가 아니라 요청 무게가 병목 (`32c4308`)

run a4875aa9: 60rps 단에서 `order_p95`가 2000ms를 **7틱 연속** 넘겼는데
(1638→2904ms) escalate streak 2/4에서 렌더 부하가 꺼져 p95가 15ms로 돌아왔고,
사다리는 그대로 `maximum_injection_duration`까지 갔다.

병목이 도착률이 아니라 직렬 렌더 상한이므로 최상위 단의 `days` 120→**240**
(렌더 비용은 days에 제곱 비례 — 실측 30→1.18ms, 90→5.69ms, 180→17.09ms,
365→62.34ms). 하위 두 단은 120 유지로 무릎 아래/근처 대조군을 남긴다.

### 7. F05-P — 사다리가 성공 구간을 건너뛰었다 (`32c4308`)

run 3ce101d5: 5500MiB는 node_mem 47~56.5%로 무효과라 254초에 escalate,
다음 단 7000MiB는 **67초 만에** 노드를 NotReady로 보내 abort. 성공 구간
(node_mem>=92%이면서 노드는 살아 있음)을 통째로 건너뛴 것이다.

5500과 7000 사이에 **6250** 삽입. min_hold 4m·timeout 8m은 기존 단과 동일.
단이 4개가 되어 최악 32m이므로 `max_injection_duration`도 30m→**32m**.

### 8. F25-H — 무효과인 첫 단 제거 (`32c4308`)

run af660719: 레벨0 256Mi가 min_hold+timeout 내내 `pg_restart` 0. 실사용
124MiB의 2배라 여전히 넉넉했다. 사다리를 **192Mi→128Mi→96Mi**로 재구성.
96Mi 아래에서 postgres가 OOM이 아니라 기동 자체를 실패하면 성공 조건
(`termination_reason == OOMKilled`)이 서지 않아 조용히 통과하는 대신 정직하게
실패한다.

recovery는 완화하지 않았다 — 회복 검증은 전역 계약이라 느슨하게 하면 뒤따르는
모든 런의 clean-window가 거짓이 된다. 409 관찰만 주석으로 기록(#2a에서 근본
원인 확인).

### 9. F06-P — 감별자가 무관한 도메인 노이즈를 세고 있었다 (`fb9ce09`)

run 4957e483 트레이스 직독. must_rule_out `promoted-to-5xx`
(`order_create_5xx_rate >= 0.1`)는 "429가 5xx로 승격됐는가"를 재려 했으나,
그 지표가 세는 order의 5xx는 payment가 아니라 **dispatch**에서 온다.

```
POST /api/orders : 200=358 · 429=33 · 400=5 · 503=43   → 43/439 ≈ 0.098
POST /api/payments: 429=33 · 200=2 · 5xx 0건            → pass-through 정상
```

그 503은 dispatch-service 자체 SERVER 500(capacity 3·상세 2·목록 2)과 order의
CLIENT 500=3에 대응한다. `OrderService`가 `checkCapacity`·`dispatchCourier` 실패를
무조건 503으로 바꾸고 CB fallback도 503이라(OrderService.java:94-112,
DispatchClient.java:66-79) dispatch 노이즈만으로 임계 0.1에 붙는다.

게다가 payment 호출은 capacity 검증(96)과 dispatch fan-out(145)을 통과해야
도달한다(154). **dispatch 503은 정의상 payment 이전에 끝난 요청**이므로 429
pass-through의 실격 사유가 될 수 없다.

감별자를 `payment_error_rate >= 5`로 교체. F19-P·F20-Q·F20-R이 이미 쓰는 같은
이름의 감별자이고, 관측은 F06-P에 **이미 선언돼 있었으나 어느 게이트에도 물려
있지 않았다** — 배선만 이어주면 되는 상태였다.

### 10. F05-R — OOM이 구조적으로 불가능한 단을 뺐다 (`d628ba9`)

run 95b07798: 576Mi 단에서 OOMKilled 3회, 성공의 나머지 두 조건은 8틱 연속 참.
`checkout_5xx_rate`만 0.0이라 실패했고 재시작 예산(abort restart>=3)이 먼저 닿아
aborted. 그 0.0의 원인은 #2a다.

**메모리를 더 조이는 것은 해법이 아니다.** fault companion이 힙을 `-Xms384m
-Xmx384m -XX:+AlwaysPreTouch`로 고정·선점하므로 컨테이너 바닥은 384MiB + 비힙이다.
평시 cgroup 실측 415MiB(최대 힙 256MiB)에서 역산하면 비힙 ~160MiB, 바닥 **~544MiB**.
576Mi 아래로 내리면 부하 중 OOM이 아니라 **기동 중 OOM**이 되어 트래픽을 한 건도
못 받고 crashloop한다 — 피해가 커지는 게 아니라 사라진다.

같은 바닥 계산이 위쪽 두 단을 반증한다. 768Mi는 바닥 위 220MiB, 640Mi는 100MiB
여유라 OOM이 불가능하고, 실제로 두 단 모두 restart 0으로 승급만 하며 6.5분을
태웠다. 768Mi 제거(640Mi→576Mi). 피해 창이 3.2분 앞당겨진다 — **부분 완화이지
근본 수리가 아니다**(근본은 #2a).

### 12. F23-R — 룩백 창을 새 배치 주기에 맞춰 재척도 (`52f23b6`)

`restock-still-running` 감별자의 룩백 창 12m는 **종전 배치 주기 10분에 맞춰 잡힌
값**이다. #2a로 주기가 60초가 되면 낡은 척도가 된다.

**줄이지 않으면 오히려 오발화한다**: 주기 60초에서는 주입 직전과 k8s.env 롤아웃
중(구 파드가 수십 초 더 산다)에 RESTOCK 행이 거의 확실히 쓰이고, t=+60s 행이
12분 창에서 t=13m까지 남는다. 판정은 min_hold 12m에 열리므로 그 행 하나가 15초
틱 5개를 덮어 3연속 요건을 넘겨 실격시킨다.

12m→**5m**. 5분은 새 주기의 5배라 배치가 계속 돌면 창에 ~5행이 들어오므로 "정지
명령이 먹지 않았다"를 여전히 넉넉히 잡는다. **감별력을 깎는 완화가 아니라 주기에
맞춘 재척도다.**

부수 효과로 F23-R이 개선된다. 풀이 3200→960이라 배치 정지 후 ~8.7분에 고갈해

**F23-R은 주입 시점이 톱니의 낮은 구간이었나에 기대고 있었다**). recovery의
`restock-resumed`도 배치 주기 10m == recovery timeout 10m이던 잠재 DIRTY 위험에서
벗어난다.

## 13. F15-P — 복합 압박의 CPU 절반만 주입되고 있었다 (`e526dbd`)

run 8f317c57은 must_rule_out `cpu-only-pressure`로 abort했다. **감별자가 옳았다** —
메모리 압박이 실제로 없었다.

`pressure` 모드가 `stress-ng --cpu N --vm M --vm-bytes B`만 실행했다. `--vm-keep`이
없으면 vm stressor가 매 반복 munmap/mmap을 되풀이해 페이지가 상주하지 않는다:

```
node_cpu_util: 15.43 → 88.26 → 99.36   (정상 상승)
node_mem_util: 61.62(최대) → 60.40 → 58.49 → 57.83~57.91  (하락)
```

이 한 플래그가 세 게이트를 동시에 깨고 있었다 — success `node-memory-pressured`
(mem>=75) 도달 불가, escalate `memory-not-yet-pressured`(mem<75) 영구 발화,
must_rule_out `cpu-only-pressure`(mem<60) 370s에 streak 3 → abort.

둘째, host.stress 계열 5종 중 **F15-P만 companion_refs가 비어 있었다**. 동종은 전부
load.north_south + achieved_rps 관측 + `user-load-overshot` 감별자를 함께 갖는다.
F10-P 파라미터를 그대로 따라 추가했다.

**피해 임계는 의도적으로 유지했다.** account 컨테이너 `cpu_throttled_time`이 0이었다는
관측은 배제 근거가 아니다 — 정답지 `root_cause.mechanism`이 "cgroup 한도를 넘지
않으므로 컨테이너 지표는 정상"인 상태를 노린다고 명시하므로 **throttle 0은 설계된
결과**다. 임계 재조정은 ①②가 적용된 재실행 실측을 보고 판단한다.

## 14. F20-R — 주입이 자기 감별자를 위반하고 있었다 (`d1df8a5`)

run fa6749a8은 `evaluation_level_timeout`으로 실패했는데, 실패한 건 판정만이 아니라
주입 자체였다. target_rps 30에서 order-service는 "느려진" 게 아니라 무너졌다:

```
/api/orders   : 99건 전부 500, p95 30013ms (30초 타임아웃 벽)
/stats/daily  : 54×500(30025ms) + 45×200(p95 47121ms, max 49493ms)
/checkout     : 22×500, 17×200(30529ms), 2×400
/actuator/health: 10×200 p95 26129ms, 1×503
```

주입 직전 baseline은 완전히 건강했다(checkout 40건 전부 200에 p95 203.7ms,
health p95 1.6ms). 정답지 must_rule_out은 "증상이 타임아웃 5xx가 아니라 지연이다.
5xx면 F19-P 계열"이라고 못박는데, rps 30의 F20-R은 그 조건을 **주입 자신이 위반**
하며 F19-P를 연기하고 있었다.

evaluation/fixed → **calibration/adaptive_ladder(1·2·3 rps)**로 강등. must_rule_out은
그대로 유지한다 — 사다리의 목적이 그 조건을 만족하는 단을 찾는 것이다. 하단 1 rps는
추측이 아니라 실측이다(k6 ramp-up이 저부하 구간을 훑어준 곡선: 첫 15초 버킷 ≈1 rps에서

공유 PG 중간 고리는 **관측만** 배선했다(`database.pg_slow_active_query_count`).
값의 정상 범위를 모르는 채 임계를 붙이면 그게 곧 추측 수리다.

**주의**: 이 사다리는 #1의 러너 수리가 배포된 뒤에 돌려야 한다.

## 17. 거짓 양성 — 주입 없이 성립 가능한 성공 조건 (`147363d`)

**이 항목은 통과 이력과 무관하게 데이터셋 신뢰성 문제다.** 별도로 세운다.

F19-P·F19-S의 success는 `order_create_5xx_rate >= 0.1`이었다. 그런데 #9에서 확인한
dispatch 노이즈 상한이 **0.098**이다. 즉 임계가 노이즈 바로 위에 있었고, 주입이
전혀 없어도 dispatch가 평소보다 조금만 나빠지면 성공이 설 수 있었다.

이건 "아깝게 못 넘는 실패"가 아니라 **구조적 거짓 양성**이다. 이 조건으로 통과한
런이 있었다면 그 런이 진짜 주입 인과를 증명했다는 보장이 없다 — 데이터셋으로는
신뢰할 수 없었다.

임계를 정할 근거는 실측 주입 피해다. 노이즈와 자릿수가 다르다:

| 시나리오 | run | 평가 틱 실측 |
|---|---|---|
| F19-P | d68b4fb3 | 0.73 → 0.99로 올라 **0.93~0.98** 유지 |
| F19-S | b7d83934 | 평가 틱 **41개 전부 0.913~1.0** (최솟값도 노이즈의 9배) |

**0.5**로 올렸다 — 노이즈의 5배이면서 주입 정상구간의 절반이라 양쪽에서 안전하고,
F10-H(#5)와 같은 값이다.

AND를 하나 더 붙이는 방식은 쓰지 않았다. `c887e20`이 두 시나리오의 두 번째 AND를
내린 판단이 실측으로 재확인된다 — F19-S의 `payment_error_rate`는 b7d83934에서
**초반 3틱만 66.67이고 이후 내내 0.0**이다. 서킷이 열리면 payment가 PG를 부르지
않고 즉시 반려하므로 자기 오류율이 사라진다. 감별자로 must_rule_out에 두는 것은
맞지만(F19-P는 이미 그렇게 쓴다) 성공 조건으로는 지속되지 않는다.

**판정 기준으로 삼을 질문**: "주입 없이 이 조건이 설 수 있는가." 답이 "설 수 있다"면
그 조건은 틀린 것이다. 두 시나리오 모두 이제 답이 "없다"이다.
