# 41종 라이브 배치 결함 기록 (2026-08-06~07 진단·수리)

파킹 3종을 뺀 ready 41종 기준. [08-04 배치](batch-44-live-findings-0804.md)가
남긴 실패·스킵을 run 아티팩트와 트레이스 직독으로 되짚은 사이클이다.

이번 사이클에서 확인된 것 셋.

**하나, 실패의 다수는 주입이 아니라 판정과 환경이었다.** 수리 10건 중 8건은 주입도
피해도 실증된 상태에서 판정 계약이 못 받아준 것이고, 나머지는 사다리가 성공 구간을
건너뛴 것이다. "주입이 안 된다"는 진단은 이번에 한 건도 없었다.

**둘, 통과 이력이 있어도 신뢰할 수 없는 조건이 있었다.** F19-P·F19-S의 성공 조건은
주입과 무관한 dispatch 노이즈(0.098)만으로 임계(0.1)에 닿을 수 있었다 — 아깝게 못
넘는 실패가 아니라 **주입 없이도 성립 가능한 거짓 양성 구조**다. 데이터셋 품질에
직결되므로 통과 여부와 별개로 틀린 조건이었다.

**셋, 층이 한 칸 더 내려갔다.** 08-04에는 시나리오·러너 층이 주였는데, 이번에는
테스트베드 **환경 자체**의 자립성 결함 2건(commerce 재고 고갈, banking transfer
flapping)이 여러 시나리오의 판정을 동시에 오염시키고 있었다. 시나리오를 아무리
고쳐도 그 아래가 흔들리면 결과가 흔들린다.

## 1. 전역 판정 결함 — APM 백분위의 표본 없는 창이 0.0으로 들어온다

**이 사이클에서 가장 파급이 큰 항목이다.** 시나리오 하나가 아니라 prometheus
`apm_service_p95`를 판정에 쓰는 모든 시나리오가 영향을 받는다.

트래픽이 없거나 스팬이 안 잡힌 창에서 APM 백분위 질의는 값 없음이 아니라 **0.0**을
반환하고, 러너는 그것을 `usable: true`로 받는다. 그리고 adaptive의 streak 갱신은

```
if result is not True: updated[name] = 0
```

이라 0.0이 만든 False 한 번이 **연속 카운터를 통째로 리셋**한다. 즉 밑 신호가 내내
나빠도 표본이 한 번 비면 연속 요건이 구조적으로 성립하지 않는다.

### 증거 — F20-R run fa6749a8

원본 15초 시계열(ms)에는 진동이 없다:

```
39389 / 46503 / 30016 / 20466 / 30010 / 30008 / 33988 / 30005 / 19981 / 27992
```

그런데 틱 값에는 0.0이 섞인다. 그 0.0이 나온 분(05:09·05:14·05:17)은 payment
스팬이 **0건**인 분과 정확히 대응한다. 신호가 좋아진 것이 아니라 **표본이 없었던
것**이고, 판정은 그것을 "임계 미달"로 읽었다.

### 같은 병으로 의심되는 것

F10-H의 "톱니형 p95"(#5)가 같은 계열로 보인다. run 748dd9c8에서 disk가
75·77·75·76으로 포화인 동안 order_p95 독립 표본이 797ms와 7691ms 사이를 오갔고
success streak이 1에서 올라가지 못했다. #5의 수리는 p95를 성공 게이트에서 빼는
쪽이라 이 병을 피해 가지만, **회피이지 치료가 아니다.**

### 같은 병의 clickhouse 쌍둥이 — **아직 안 고쳐졌다** (2026-08-07 추가)

APM 수리로는 안 잡히는 같은 계열 결함이 하나 더 있다. `clickhouse.service_error_rate`
템플릿이 이렇게 생겼다:

```sql
SELECT if(count() = 0, 0, round(100.0 * countIf(...) / count(), 4)) AS value
```

**스팬이 없으면 에러가 아니라 0을 만들어낸다.** APM 0.0과 정확히 같은 조작이지만
소스가 달라 APM 수리 범위 밖이다.

증상은 abort가 아니라 더 나쁜 쪽이다 — **조용한 거짓 음성**이다. payment가 죽어서
스팬이 끊긴 바로 그 순간, 감별자는 "payment 오류율 0 = 정상"으로 읽는다. 즉
**교란 요인이 실재하는 순간에 정확히 눈이 먼다.** must_rule_out에서 이 질의를 읽는
조건이 넷이다:

| 시나리오 | 조건 | 대상 |
|---|---|---|
| F06-P·F19-P·F20-Q | `payment-also-erroring` | food-delivery-payment |
| F20-R | `payment-also-erroring` | commerce-payment |

109에 배포된 러너에 이 코드가 그대로 있는 것을 확인했다(`live_probes.py:104`).
러너 담당에게 넘겼다 — **수리되면 여기에 해시를 채운다: (미수리)**.

### 조치와 순서 의존

수리는 rca-scenario-runner에서 별도 에이전트가 진행 중이다(표본 없는 창을 값이
아니라 `unusable`로 표시). **F20-R의 새 사다리(#14)는 이 수리가 배포된 뒤에
돌려야 한다** — 그 전에는 0.0 아티팩트가 escalate를 즉시 발화시켜 사다리가
최상단까지 헛돈다.

## 2. 환경 자립성 결함 2건

시나리오 결함이 아니라 테스트베드가 스스로를 유지하지 못하는 문제다. 둘 다 여러
시나리오의 판정을 동시에 오염시키고 있었다.

### 2a. commerce 재고 상시 고갈 (수리 `52f23b6`)

`ReconciliationBatch`는 10분마다 `stock < 20`인 상품만 `target 200`으로 채운다.
그런데 상주 부하의 소비는 **~110 units/min**이다(원장 분당 집계 40분 실측).
평균 공급은 맞지만 **버스트**라 주기 끝마다 전 상품이 마른다 — 08:07 시점
flagship 16종 전부 `stock=0`을 DB 직독으로 확인했다.

재고가 0인 구간에서는 checkout이 payment에 닿기 전에 409로 걸러진다
(`OrderService.checkout`은 `reserveStock`을 payment보다 먼저 호출한다).

피해:
- **F05-R** (run 95b07798): 01:11~01:14:30 창구에서 checkout **142건 전부 409**,
  `payment_reqs` 0. payment가 OOMKilled를 3회 냈는데도 `checkout_5xx_rate`가
  런 내내 0.0이라 성공이 서지 못했다. 관측 배선은 정확했고 **피해가 실제로 0**이었다.
- **F25-H** (run af660719): 레벨 전환 recovery가 이 409 flakiness에 걸려 dirty.

수리: 주기 600s→60s, target 200→60, threshold 20 유지. 주기를 줄이는 것이
"0에 닿지 않음"을 만들고, target을 줄이는 것이 F23-R의 성립을 운에서 결정론으로
바꾼다(#12).

**세 파라미터는 서로 당긴다.** `ReconciliationBatch` javadoc에 제약을 남겼다:
① 평시 0 미도달 = `threshold > 상품당수요 × 주기` ② F23-R 결정론 = 풀(16×target)이
min_hold 안에 마를 것 ③ restock 감별자 = 룩백 창이 주기에 비해 너무 넓지 않을 것.
하나만 바꾸면 다른 데서 깨진다.

기본값은 **코드에만** 뒀다. 배포 매니페스트 env로 올리면 F23-R이 k8s.env로 잡아둔
baseline 환경변수 배열(정확히 11개, 매니페스트와 바이트 일치)이 달라져 승인된
계약이 깨진다. 주입(`SPRING_APPLICATION_JSON`)은 코드 기본값을 그대로 덮으므로
계속 동작한다.

### 2b. banking transfer flapping (수리 `dec83d4`)

`testbed-transfer`의 SIGKILL(137) 반복은 자원 부족이 아니라 구조 결함이었다.
체인은 릴레이에서 시작해 헬스 프로브에서 끝난다:

```
@Transactional relay()가 루프에서 최대 100건을 kafkaTemplate.send(...).get()으로
순차 대기 → producer 타임아웃 미설정이라 건당 최대 delivery.timeout 120s
→ 그 시간 내내 Hikari 커넥션 점유 → transfer 풀(15) 고갈
   (실측: total=15 active=15 waiting=1, 획득 6105ms 타임아웃)
→ DataSourceHealthIndicator가 같은 풀을 타서 /actuator/health가 probe timeout 3s 초과
→ livenessProbe 실패 누적 → SIGKILL
```

수리: 발행을 트랜잭션 밖으로(짧은 읽기 → 트랜잭션 밖 발행 → 성공분만 짧은 배치
UPDATE), Kafka producer 타임아웃 명시(request 5s / delivery 15s / max.block 5s),
liveness를 DB에서 분리(`/actuator/health/liveness`), transfer 힙 `-Xmx512m` 명시.
readiness는 `/actuator/health`를 그대로 본다 — F17-R의 승인된 스냅샷이 그 블록이다.

## 3~12. 판정 계약 수리 10건

### 3. F16-H — min_hold가 신호 생존 창 밖이었다 (`5178218`)

run aea47b5c: `write_401_rate`가 31초부터 252초까지 **1.0으로 15틱 연속**,
success streak이 8까지 갔는데 판정 사유가 내내 `min_hold`였다. 조건은 진작
충족됐는데 창이 안 열린 것이다. 267초에 baseline loadgen이 로그인 불능이 되며
신호가 0.0으로 붕괴, 13m 레벨 타임아웃까지 끝내 돌아오지 않아 failed.

min_hold 8m→**150s**. 붕괴 이전 창 안에서 3연속(필요 45s)을 확정한다.

**남은 결함(미수리)**: 신호가 죽은 뒤의 0.0이 `usable=true`로 들어와 '성공 조건
미달'과 구분되지 않는다. #1과 같은 계열의 관측 평면 문제라 이번에 건드리지 않고
컨트롤러 주석으로만 남겼다.

### 4. F20-Q — 유효 평가 틱이 물리적으로 하나였다 (`5178218`)

run 543dda48: `evaluating` 페이즈 틱이 **1개**뿐이다. 31초 틱에서 메모리 867MB·
주문 생성 5xx 0.6으로 두 조건이 동시에 서고(streak 1), 46초 틱에는 이미 파드가
죽어 `entry_status` 0·5xx `usable=false`다.

success `consecutive_ticks` 2→**1**. 1틱이 정당한 근거는 둘이다 — gate가 서로 다른
평면의 독립 신호 AND(k8s 컨테이너 메모리 · k6 주문 생성 5xx)라 단일 틱도 우연
일치가 아니고, 죽기 전 물리적 창이 1틱뿐이다.

### 5. F10-H — 피해는 실증됐고 실패한 건 판정이다 (`f60c903`)

run 748dd9c8: `order_create_5xx_rate`가 세 레벨 내내 **0.90~0.99로 안정**,
`disk_io_util`도 62~87을 오갔다. 피해와 원인이 둘 다 서 있었는데
`calibration_levels_exhausted`로 끝났다.

원인은 신호 선택이다. `order_p95`는 `update_interval 60s`라 gate 전체를 60초

`device-saturated` 임계 70→**60**(최상위 레벨에서 69·66·66 같은 골이 3연속 창을
계속 깼다. 러너 문법에 M-of-N이 없어 연속 계약은 유지하고 임계를 실측 골 아래로

disk 60~69에서 성공과 승급이 동시에 참이 되어 서로를 잡아먹는다.

### 9. F06-P — 감별자가 무관한 도메인 노이즈를 세고 있었다 (`fb9ce09`)

run 4957e483 트레이스 직독. must_rule_out `promoted-to-5xx`
(`order_create_5xx_rate >= 0.1`)는 "429가 5xx로 승격됐는가"를 재려 했으나,
그 지표가 세는 order의 5xx는 payment가 아니라 **dispatch**에서 온다.

```
POST /api/orders : 200=358 · 429=33 · 400=5 · 503=43   → 43/439 ≈ 0.098
POST /api/payments: 429=33 · 200=2 · 5xx 0건            → pass-through 정상
```

그 503은 dispatch-service 자체 SERVER 500(capacity 3·상세 2·목록 2)과 order의
CLIENT 500=3에 대응한다. `OrderService`가 `checkCapacity`·`dispatchCourier` 실패를
무조건 503으로 바꾸고 CB fallback도 503이라(OrderService.java:94-112,
DispatchClient.java:66-79) dispatch 노이즈만으로 임계 0.1에 붙는다.

게다가 payment 호출은 capacity 검증(96)과 dispatch fan-out(145)을 통과해야
도달한다(154). **dispatch 503은 정의상 payment 이전에 끝난 요청**이므로 429
pass-through의 실격 사유가 될 수 없다.

감별자를 `payment_error_rate >= 5`로 교체. F19-P·F20-Q·F20-R이 이미 쓰는 같은
이름의 감별자이고, 관측은 F06-P에 **이미 선언돼 있었으나 어느 게이트에도 물려
있지 않았다** — 배선만 이어주면 되는 상태였다.

### 10. F05-R — OOM이 구조적으로 불가능한 단을 뺐다 (`d628ba9`)

-Xmx384m -XX:+AlwaysPreTouch`로 고정·선점하므로 컨테이너 바닥은 384MiB + 비힙이다.
평시 cgroup 실측 415MiB(최대 힙 256MiB)에서 역산하면 비힙 ~160MiB, 바닥 **~544MiB**.
576Mi 아래로 내리면 부하 중 OOM이 아니라 **기동 중 OOM**이 되어 트래픽을 한 건도

태웠다. 768Mi 제거(640Mi→576Mi). 피해 창이 3.2분 앞당겨진다 — **부분 완화이지
근본 수리가 아니다**(근본은 #2a).

## 16. 미해결 — 설계 결정이 필요한 것들

이 절의 F03-P는 이 문서를 쓴 뒤 실측으로 뒤집혀 **미해결에서 빠졌다**. 원래 판정과
정정 근거를 함께 남긴다 — 판정이 바뀐 과정 자체가 다음 사람에게 필요한 정보다.

### F09-R — 클린 베이스라인 미확보

노드를 100% 태워도 동거 서비스가 멀쩡하다는 08-04 #6의 판정이 아직 뒤집히지도
확정되지도 않았다. 컨테이너 `cpu_throttled` 계열의 깨끗한 평시 분포를 못 잡아
"압박이 전이되지 않았다"와 "전이됐는데 지표가 못 잡는다"를 가르지 못한다.
F09-R 관측에는 현재 throttle 계열이 없다.

### F03-P — 미해결에서 **재배치 확인 가설로 강등** (2026-08-07 재평가)

> 이 항목은 이 문서 안에서 한 번 뒤집혔다. 처음 적은 판정은 "레버가 없어 구조적으로
> 불가"였고, 근거는 **이론 계산**이었다 — "풀을 2로 줄여도 이론 처리량이 ~400rps인데
> 부하는 60rps라 풀이 물리적으로 포화될 수 없다". 그 계산이 틀렸다.

**풀은 실제로 막힌다(run 4a1cbd57 실측).** 평가 틱 42개 중 `payment_p95>=500`이
14틱이고 **최장 11틱 연속**이다(요구 3틱). 최대 1552.51ms까지 올라간다.

이론 논거가 틀린 이유는 유효 서비스 시간을 DB 작업 시간으로 잡았기 때문이다. payment는
`@Transactional` 안에서 커넥션을 쥔 채 외부 HTTP(PG mock·banking transfer, read-timeout
각 10s)를 호출한다. 커넥션 점유 시간은 DB 작업 5ms가 아니라 **그 왕복 전체**이므로
60rps로도 풀 2는 충분히 마른다.

**막힌 쪽은 p95가 아니라 다른 축이다.** 성공은 AND 2항이고
(`payment_p95>=500` **AND** `checkout_5xx_rate>=0.05`, 3연속),
`checkout_5xx_rate`는 **42틱 전부 0.00**이었다(min=max=0.0).

그리고 그 0.00은 **F05-R(#10)을 막은 것과 같은 기전으로 보인다.** 재고가 마르면
checkout이 `reserveStock`에서 409로 조기 종료돼 payment에 **도달하지 못한다**
(`OrderService.checkout`은 reserveStock을 payment보다 먼저 호출한다). payment가 아무리
느려도 checkout은 5xx를 내지 않는다. 재고 재설계(#2a `52f23b6`)가 그 409 지배를 없앤다.

**따라서 F03-P는 `db.workload` 없이도 재배치에서 풀릴 수 있다.** 등급을 "미해결(구조적
불가)"에서 **"재배치에서 확인할 가설"**로 내린다.

다만 의존성이 **둘**이라는 점은 같이 기록해 둔다. `payment_p95`가 읽는 commerce-payment는
#1에서 측정한 8개 서비스 중 **표본 결손이 유일하게 있는 서비스**다(APM 원시 샘플 57/60,
최대 간극 120s로 freshness 계약 경계, 0.0 아티팩트 52회). 실제로 이 run의 `payment_p95`도
0.0을 포함하며 98→1552→1201→25→32→3ms로 크게 요동친다. 즉 F03-P의 성립은
(a) 재고 수리가 `checkout_5xx_rate`를 풀어주는가 **와** (b) 러너 관측 수리 후
`payment_p95`가 어떻게 달라지는가에 **둘 다** 걸려 있다.

`db.workload`는 그 사이 `4a2f465`로 라이브가 됐고 `allowed_scenarios`는 **F02-H 하나**다.
즉 이 레버의 정당화는 F03-P가 아니라 F02-H(캐시 무력화 광역 스캔)로 좁혀졌다.

> **교훈: 이론적 논거로 시나리오를 불가 판정하지 말 것.** 이 레포가 이미 여러 번
> 배운 "기록된 원인을 믿지 말고 재라"와 같은 계열이다. 계산은 모델이고 모델은 항상
> 무언가를 뺀다 — 여기서는 커넥션을 쥔 채 나가는 외부 호출이 빠졌다. 불가 판정은
> 실측으로만 내린다.

## 17. 거짓 양성 — 주입 없이 성립 가능한 성공 조건 (`147363d`)

**이 항목은 통과 이력과 무관하게 데이터셋 신뢰성 문제다.** 별도로 세운다.

F19-P·F19-S의 success는 `order_create_5xx_rate >= 0.1`이었다. 그런데 #9에서 확인한
dispatch 노이즈 상한이 **0.098**이다. 즉 임계가 노이즈 바로 위에 있었고, 주입이
전혀 없어도 dispatch가 평소보다 조금만 나빠지면 성공이 설 수 있었다.

이건 "아깝게 못 넘는 실패"가 아니라 **구조적 거짓 양성**이다. 이 조건으로 통과한
런이 있었다면 그 런이 진짜 주입 인과를 증명했다는 보장이 없다 — 데이터셋으로는
신뢰할 수 없었다.

임계를 정할 근거는 실측 주입 피해다. 노이즈와 자릿수가 다르다:

| 시나리오 | run | 평가 틱 실측 |
|---|---|---|
| F19-P | d68b4fb3 | 0.73 → 0.99로 올라 **0.93~0.98** 유지 |
| F19-S | b7d83934 | 평가 틱 **41개 전부 0.913~1.0** (최솟값도 노이즈의 9배) |

**0.5**로 올렸다 — 노이즈의 5배이면서 주입 정상구간의 절반이라 양쪽에서 안전하고,
F10-H(#5)와 같은 값이다.

AND를 하나 더 붙이는 방식은 쓰지 않았다. `c887e20`이 두 시나리오의 두 번째 AND를
내린 판단이 실측으로 재확인된다 — F19-S의 `payment_error_rate`는 b7d83934에서
**초반 3틱만 66.67이고 이후 내내 0.0**이다. 서킷이 열리면 payment가 PG를 부르지
않고 즉시 반려하므로 자기 오류율이 사라진다. 감별자로 must_rule_out에 두는 것은
맞지만(F19-P는 이미 그렇게 쓴다) 성공 조건으로는 지속되지 않는다.

**판정 기준으로 삼을 질문**: "주입 없이 이 조건이 설 수 있는가." 답이 "설 수 있다"면
그 조건은 틀린 것이다.

### ⚠ 위 수리는 실패했다 — 임계 상향으로는 안 닫힌다 (2026-08-07 후속, `7c90e08`)

**바로 위 문단의 결론("두 시나리오 모두 이제 답이 '없다'")이 실측으로 반증됐다.**
답은 여전히 "있다"였다. 0.1→0.5 상향은 거짓 양성을 못 막았다.

`order_create_5xx_rate_baseline`은 **무주입 대조 팔**이다(같은 질의를
`domain=food-delivery`로 읽어 baseline loadgen 문서를 본다). 두 팔을 나란히 놓으면
수리가 왜 실패했는지가 한눈에 보인다 — F19-P run cae8c16c(succeeded):

```
        주입 팔   대조 팔
el= 79   0.911    1.000   ← 대조가 더 높다
el=143   0.973    1.000
el=473   0.978    0.892
전 구간  payment_error_rate = 0.000 · order_hikari_pending = 0.000
```

**주입이 만든 차이가 없다.** 그런데 성공이 확정됐다. 게다가 이 시나리오가 주장하는
기전(order 커넥션 풀 고갈)의 신호도 전 구간 0이다 — 피해도 기전도 없이 통과했다.

**한 런의 사고가 아니다.** 기록된 F19 런 6개 전부 대조 팔 중앙값이 0.93~1.00이다:

| run | 주입 팔 | 대조 팔(중앙) |
|---|---|---|
| F19-P aa75203a | 0.533~0.993 | 0.933 |
| F19-P cae8c16c | 0.795~0.978 | 0.938 |
| F19-P d68b4fb3 | 0.267~0.994 | 0.931 |
| F19-S 01df886f | 0.881~0.982 | 1.000 |
| F19-S 377a2aad | 0.897~0.981 | 0.967 |
| F19-S b7d83934 | 0.913~1.000 | 0.967 |

원인은 **`dispatches`에 `status` 인덱스가 없는 것**이다(`fd9b7e8`에서 확정).
`DispatchService.countByStatus("ASSIGNED")`가 주문 생성마다 **두 번** 도는데 그 질의를
탈 인덱스가 없어 처음부터 풀스캔이었고, 표가 137만 행에 이르자 임계를 넘었다.
라이브 옵티마이저 실측: `type=ALL · key=NULL · rows=1,012,216` — 1,408행을 돌려주려고
100만 행을 훑는다. 그 결과 `/api/deliveries/capacity`가 500을 내고 dispatch 헬스가
503이 되며, `OrderService`가 그것을 `catch (Exception) → 503 "Dispatch service
unreachable"`로 바꾼다. **그 지점이 payment 호출보다 앞이라 하류 주입이 통째로 가려진다.**

결정적 증거: 두 통과 창(F19-P cae8c16c / F19-S 377a2aad)에서 order `POST /api/orders`가
503을 각각 221·258건 냈는데, **그 503 트레이스 482건 안의 payment 스팬이 0건**이다.
주입은 mock `/pay` 지연이므로 그 5xx를 만들었을 가능성이 0이다.

> **처음 적었던 원인(courier 풀 고갈)은 틀렸다.** `ASSIGNED`는 F19-P 시작 1406 →
> 성공 시점 975 → F19-S 성공 시점 532로 **오히려 줄고 있었고** 상한 2000 근처에도 가지
> 않았다. 즉 "No courier available" 분기가 아니라 "Dispatch service unreachable"
> 분기였다. 나는 전달받은 설명을 그대로 옮겨 적었고, 더 깊이 판 조사가 그것을 뒤집었다 —
> **전달받은 인과도 실측 전까지는 가설이다**(§16b에서 배운 것과 같은 교훈).

즉 위 표에서 "주입 피해 0.93~0.98"이라고 읽었던 값은 사실 대부분 이 dispatch 503이었다.

> **교훈(§17의 진짜 결론): 임계 상향은 거짓 양성을 막지 못한다.** 환경이 신호를
> 포화시키면 **어떤 절대 임계도 넘어간다** — 1.0에 붙은 신호 앞에서 0.5든 0.9든
> 의미가 없다. 노이즈가 "작다"고 가정하고 그 위에 선을 긋는 방식 자체가 틀렸다.
> **대조군이 있으면 대조군을 써라.** 환경 노이즈는 양쪽 팔에 똑같이 실리므로
> 차이로 판정하면 상쇄된다.
>
> 그리고 "주입 없이 이 조건이 설 수 있는가"는 **머리로 답하면 안 된다.** 나는 노이즈
> 상한(0.098)을 근거로 "없다"고 답했지만, 실제 대조 팔은 그 10배였다. 답은 **대조 팔을
> 재서** 내야 한다.

### 지금 할 수 있는 것과 러너가 필요한 것

**러너는 두 관측의 비교를 지원하지 않는다.** `adaptive.py`의 `Condition`은
`id/signal/operator/value: Scalar`이고 `StrictModel`이라 필드 추가도 거부한다 —
`_condition_result`는 `signal`을 **리터럴**과만 비교한다. 따라서 '주입 팔 − 대조 팔'
게이트는 **러너 변경 건**이다(별도 이관).

그때까지 표현 가능한 것은 "대조군이 이미 깨졌으면 실격"이다. `must_rule_out`에
`baseline-arm-also-failing`(대조 팔 ≥ 0.2)을 걸어 **fail-closed**로 만들었다. 차이를
증명하지는 못하지만 **대조군이 오염된 런에 성공을 주지 않는다.** F19-P·F19-S와,
같은 노출을 가진 F10-H에 적용했다(F10-H는 대조 관측이 아예 없어 신설).

**이 감별자와 인덱스 수리(`fd9b7e8`)는 서로를 대체하지 않는다.** 인덱스가 배포되면
dispatch 503이 멎어 대조 팔이 정상(≈0)으로 돌아오고, 그러면 이 감별자는 **조용해진다**
— 막으려던 상황이 사라졌으니 그것이 맞는 동작이다. 감별자는 그 뒤로도 **다음 번
환경 오염을 잡는 그물**로 남는다. 원인이 무엇이든(인덱스든 다른 것이든) 대조군이
깨진 채로는 성공을 주지 않는다는 계약 자체가 이 사건의 교훈이기 때문이다.

### 이번 배치 F19-P·F19-S 통과는 무효다

**데이터셋 사용 불가로 기록한다.** 통과했으나 위 근거로 거짓 양성이 확정됐다 —
주입 피해가 관측되지 않았고 대조 팔이 주입 팔과 구분되지 않는다. 이번 배치의 통과
개수는 **21이 아니라 19로 읽어야 한다.**

### 대조 팔은 아무 데나 쓸 수 없다 — 확장하며 배운 것 (`5862289`)

대조 관측을 가진 나머지 6건에 같은 계약을 넓히려고 **시나리오마다 대조 팔 분포를
실측**했다(F19의 0.2를 복사하지 않고). 그 결과 **넷은 적용하면 안 되는 것**으로 나왔다.

| 시나리오 | 대조 팔 실측 | 판단 |
|---|---|---|
| F03-H | **0.000** (228 표본, min=p50=p99=max) | **적용** ≥0.02 |
| F03-P | **0.000** (98 표본, 동일) | **적용** ≥0.02 |
| F06-P | 주입 팔을 그대로 따라감 (주입 0.429/0.385/0.333 ↔ 대조 0.541/0.594/0.655) | **미적용** |
| F15-H | 양쪽이 함께 오르고 함께 0으로 내려감 | **미적용** |
| F15-T2 | 잴 수 없음 — 런 3개 전부 `ticks.jsonl`이 없다 | **미적용** |
| F25-H | p50 0.000이나 **max 0.154로 자기 성공 임계(0.1)를 넘는다** | **미적용** |

**적용한 둘의 임계 0.02도 실측에서 나왔다.** 두 컨트롤러가 이미 recovery의
`checkout-cleared`/`pool-restored`에서 같은 신호의 "정리됐다" 경계로 0.02를 쓴다 —
새 상수를 들이지 않고 그 값을 재사용했다. 성공 임계가 0.05로 낮아 대조 팔이 0.02만
돼도 귀속 여유가 절반 이하로 줄어든다.

> **일반 규칙: 대조 팔은 주입면이 baseline 트래픽 경로 밖일 때만 오염 탐지기다.**
>
> F06-P·F15 계열의 주입은 **공유 mock의 429**이고 baseline loadgen 트래픽도 같은 mock을
> 지난다. F25-H는 postgres를 OOM시키는데 baseline checkout도 같은 postgres를 쓴다.
> 이 경우 대조 팔은 "무주입 팔"이 아니라 **주입면을 공유하는 다른 트래픽원**이므로,
> "대조 팔이 높으면 실격"을 걸면 **주입이 잘 될수록 실격되는 역설**이 된다.
>
> F19 계열에서 그것이 성립한 이유는 그 5xx가 주입(mock 지연)이 아니라 **dispatch 인덱스
> 부재**에서 왔기 때문이다 — `fd9b7e8`의 트레이스 482건에 payment 스팬이 0건이라는 것이
> 그 증거다. 즉 "대조 팔이 오염됐다"는 판단 자체가 **오염원이 주입 밖임을 먼저 보인 뒤에만**
> 가능하다.

**fail-closed는 차분의 대용이지 대체가 아니다.** 지금 걸어둔 감별자는 "대조군이
깨졌으면 실격"까지만 한다. **"주입이 대조군보다 얼마나 더 나쁜가"는 여전히 못 묻는다** —
그건 러너에 두 관측 비교 문법(`compare_to`)이 들어와야 가능하고, 그때 비로소 위의
"주입면 공유" 케이스도 제대로 판정할 수 있다(공유돼도 차이는 남기 때문이다).

여전히 오염된 것만 남기고 나머지는 (a)의 가설이 맞았다는 뜻으로 지우면 된다. 미적용 4종은
러너 `compare_to`가 들어온 뒤에야 판정 가능하므로 그 전까지는 이 목록에 남는다.

## 18. F12-H — "관측 불가능한 감별자"로 의심했으나 실측이 반증했다 (수리 불요)

`must_rule_out`의 `cross-service-overload`(`pricing_p95 >= 300`)가 **부하를 받지 않는
서비스를 읽는 것 아니냐**는 의심에서 시작했다. 러너 수리로 APM p95가 표본 없는 창에서
에러를 내게 되면, `must_rule_out`은 `any` 매칭이라 조건 **하나만** 불가용이어도
레벨 타임아웃 시 `ABORTED / safety_observation_unavailable`로 실격된다
(`adaptive.py:277`). 그래서 새 abort 위험 후보로 지목됐다.

**실측은 정반대였다.**

| 측정 | commerce-pricing |
|---|---|
| ClickHouse SERVER 스팬(60분) | 4399건, **61/61분 존재, 빈 분 0** |
| APM 원시 샘플(60분) | 60/60, median·max 간극 **모두 60s** |
| freshness 120s 계약 위반 | **0회** |
| 0.0 아티팩트 | **0회** — 잰 8개 서비스 중 유일하게 gateway·product와 함께 0 |
| 실제 F12-H 런 (1918e0d6 / 9252ae2f) | `pricing_p95` 불가용 **0/18 · 0/58**, 값 1.05~7.48ms, 0.0 없음 |

**구조가 이 결과를 설명한다.** `OrderService.checkout`은 cart → **pricing(155)** →
inventory 예약(product 경유, 160) → payment 순이다. pricing은 주입 대상인 product보다
**상류**라, product를 조여도 pricing 호출은 줄지 않는다. 굶을 수가 없는 배치다.

### 두 측정이 갈린 이유 — 창이 다르다

같은 신호를 두고 상반된 수치가 나왔다. 7일 창에서는 공백이 **376건**이고, 60분 창과
실제 런에서는 **0건**이다. 둘 다 맞다.

7일치에는 **loadgen이 돌지 않는 유휴 구간**이 섞인다. 부하가 없으면 저트래픽 서비스는
당연히 발행이 끊긴다. 그러나 판정은 유휴 구간에 돌지 않는다 — 게이트가 신호를 읽는
시간은 런 중이고, 런 중에는 baseline loadgen이 항상 살아 있다(preflight
`baseline-traffic`이 그것을 강제한다).

> **교훈: 판정 창 밖의 공백은 감별자 재설계의 근거가 아니다.** 저트래픽 서비스의
> 지표 연속성을 볼 때 유휴 구간을 섞으면 "이 신호는 자주 끊긴다"는 잘못된 결론이
> 난다. 재야 할 창은 **런 창**이고, 가장 좋은 것은 그 시나리오의 실제 run 아티팩트에서
> `usable=false` 틱을 세는 것이다(위 0/18·0/58처럼).

수리하지 않았다. 지웠다면 정답지가 명시한 **범위 축**을 잃었을 것이다 — "느려지는
것은 product와 그 상류뿐이고, product를 거치지 않는 경로(pricing 등)는 정상이다.
노드 전역이 느려지면 F09-R이다." 이 감별자는 F09-R과의 변별을 혼자 지고 있다.

원칙("관측 불가능한 감별자는 감별자가 아니다")은 옳다. **F12-H가 그 사례가 아니었을
뿐이다.** 전수 확인 결과 ready 41종에서 `must_rule_out`이 표본기아 질의를 읽는 조건은
5개뿐이고, **abort 게이트는 하나도 없다.** 나머지 4개는 전부 위 clickhouse 쌍둥이(#1)에
걸린 `payment-also-erroring`이며, 그쪽은 abort가 아니라 거짓 음성으로 샌다.

## 19. 정답지 산문 드리프트 — 데이터셋 품질 결함의 한 범주 (`bd10144`·`f833e50`)

**구조적 사각지대다.** 구조화된 `injected_fault.levels`는 컨트롤러와 기계 대조되는데
(`test_stated_injection_matches_the_live_controller`) **산문 필드는 아무도 대조하지
않는다.** 그런데 채점자가 실제로 읽는 것은 산문 쪽이다. 즉 사다리를 고칠 때마다
정답지의 사람이 읽는 면이 조용히 낡고, 아무 테스트도 붉어지지 않는다.

ready 41종 + parked 승격 후보 3종의 정답지를 계약과 대조해 **10건**을 찾았다 — 산문 8건과
구조화 필드 2건이다.

### 유형 1 — 실행기·대상이 틀렸다 (`bd10144`)

| 시나리오 | 필드 | 산문 | 실제 |
|---|---|---|---|
| F18-P | injection_summary | `k8s.env`로 env 교체 + rollout | `app.control`이 Oracle 제어행 UPDATE |
| F15-R | injection_summary | `timeline.flap` | `timeline.compose` (레지스트리에 없는 이름) |
| F12-H | injection_summary | `k8s.resource` | `k8s.patch` |

**F18-P가 가장 심각했다.** `e1f17b6`이 **폐기한** 설계를 정답으로 가리키고 있었다.
폐기 이유가 maxSurge=0에서 롤아웃이 유일한 파드를 먼저 내려 자기 감별자를 켜기
때문인데, 산문만 남아 그 접근을 정답처럼 읽히게 했다.

### 유형 2 — 사다리 수치가 낡았다 (`f833e50`)

| 시나리오 | 필드 | 산문 | 실제 |
|---|---|---|---|
| F05-R | description·cause | `768Mi→640Mi→576Mi` | `640Mi→576Mi` (#10에서 뺀 단) |
| F09-H | injection_summary | `256→208→176`, `-XX:+UseParallelGC` | `208→160→128→112→96`, `-XX:+AlwaysPreTouch` |
| F12-H | cause | `500m → 250/100/50m` | `250m→200m→175m` |
| F25-H | cause | `512Mi → 320Mi` | `192Mi→128Mi→96Mi` (`9e23a9a` 전환 전 값) |

**드리프트는 수리와 함께 태어난다.** F05-R은 이 사이클의 #10이 남긴 것이고, F12-H의
`cause`는 `bd10144`이 `injection_summary`만 고치며 놓친 것이다. 같은 사실이 여러 필드에
흩어져 있으면 하나만 고치게 된다.

### 유형 3 — 구조화 필드가 어긋났다 (`59c484c`)

**산문만 대조하면 구조화 필드가 남는다.** 위 두 유형을 고친 뒤 별도 감사에서 같은
계열이 `injected_fault.companions`에서 나왔다. `levels`는 컨트롤러와 대조되는데
(`test_stated_injection_matches_the_live_controller`) **companions는 아무도 대조하지
않았다.**

| 시나리오 | 정답지 companions | 실제 companion_refs | 성격 |
|---|---|---|---|
| F05-R | `[load.north_south]` | `[k8s.env, load.north_south]` | **주입의 절반을 감춤** |
| F14-P | `[load.north_south]` | `[]` | **주입하지 않는 것을 주장** |

F05-R이 특히 나쁘다. 빠진 `k8s.env`가 **힙을 `-Xms384m -Xmx384m -XX:+AlwaysPreTouch`로
고정하는 두 번째 레버**이고, 그것 없이는 OOM이 나지 않는다 — #10의 바닥 계산(~544MiB)이
바로 그 레버 위에 서 있다. 정답지만 읽으면 "메모리 한도만 내렸다"로 읽힌다.

**두 건 다 자기 산문과 모순이었다.** F05-R의 `injection_summary`는 k8s.env companion을
정확히 설명하고, F14-P는 "부하는 baseline loadgen이 공급한다"고 쓴다. 산문·컨트롤러·
카탈로그 셋이 일치하고 구조화 필드 하나만 어긋나 있어 정본은 명확했다.

배포 블로커는 아니다 — 디스패치는 이 필드를 읽지 않는다(러너는 plan의
`companion_profile_ids`를 쓴다). 그러나 캡처 케이스에 실려 sha256으로 봉인되므로
**채점자가 읽는 면**이다.

**같은 뿌리의 부수 건**: `load.north_south`의 `tag_pattern`이 `14-P`를 받아주는데
`allowed_scenarios`에는 없었다(차집합이 정확히 이것 하나, 51 vs 50). 2026-08-03에
정규식으로 들어갔다가 그 뒤 companion이 빠지면서 allowlist에서만 사라진 것이다.
fail-closed라 실행은 막히지만 계약 안에 거짓 흔적이 남는다. 기존 가드가 **한 방향만**
(allowlist → 정규식) 보고 있어서 반대 방향이 살아남았다 — 양방향으로 넓혔다.

> **교훈: 대조 면을 하나 고치면 나머지 면이 드러난다.** 산문 감사(유형 1·2)를 통과한
> 뒤에도 구조화 필드가 남아 있었고, 그 구조화 필드를 고치자 같은 계약 안의 정규식이
> 남아 있었다. "무엇이 무엇과 대조되는가"를 목록으로 관리하지 않으면 매번 한 겹씩만
> 벗겨진다.

### 어디까지 기계화했는가

**기계화됨(가드 5종)**: ① 나열형 사다리 수치 ↔ 계약(`f833e50`) ② `injection_summary`의
실행기 이름 ↔ 바인딩(`bd10144`) ③ `code_anchor` 줄번호·심볼(기존) ④ `companions` 3면
합의(`59c484c`) ⑤ `tag_pattern` ↔ `allowed_scenarios` 양방향(`59c484c`). ③은 지금 green이라
오늘 앱 코드 변경(ReconciliationBatch·OutboxRelay·ResponseDelayFilter)으로 밀린 앵커는
없다.

수치 가드의 범위는 **의도적으로 좁다** — "A→B→C"처럼 **나열로** 쓴 것만 본다. 서술 속
단일 값("한도 1Gi")이나 측정 서술("anon 413MiB")은 계약 밖 사실을 정당하게 인용할 수
있기 때문이다. 단위 동치 넷(Gi↔Mi, 바이트 임계, 정수 파라미터, JVM 힙 플래그)을 넣어
오탐 0·진탐 5를 만들었다.

**사람 눈에 남는 것**: 인과 서술의 논리, 감별 근거의 타당성, 그리고 **폐기된 설계를
가리키는 서술**(F18-P 류 — 값이 아니라 접근이 낡은 경우라 수치 대조로 잡히지 않는다).

### 고치지 않고 남긴 것 (판단 필요)

- **F20-R**: 산문이 사다리 강등(#14)을 반영하지 않는다. 다만 rps를 **틀리게 적은 게
  아니라 언급하지 않는다** — 오류가 아니라 불완전이라 손대지 않았다.
- **F15-P**: `--vm-keep`과 새로 붙은 `load.north_south` companion(#13)이 산문에 없다.
  같은 이유로 불완전이지 오류는 아니다.
- **F21-Q(parked)**: 산문이 `host.stress`/`db.workload` 선택지를 말하는데 parked
  컨트롤러도 `host.stress`라 **현재는 일치**한다. 그러나 `a709606`의 app.control
  재설계가 승격되면 그 순간 F18-P와 같은 상태가 된다 — 승격 시 함께 고쳐야 한다.
- **F11-R**: 산문이 primary(`load.north_south`) 대신 companion(`cache.control`)을 먼저
  소개하지만 내용은 정확하다. 그래서 가드도 "primary인가"가 아니라 "바인딩된 것 중
  하나인가"로 설계했다.

   (#2a `52f23b6`)·같은 확인 항목**이므로 한 줄로 묶어 본다. 둘 다 나머지 성공
   조건은 이미 실증돼 있다 — F05-R은 OOMKilled 3회, F03-P는 `payment_p95>=500`
   11틱 연속. 이것이 안 움직이면 재고가 아니라 피해 경로 자체를 다시 의심해야 한다.
2. **F25-H의 409 dirty가 풀렸는가** — #2a의 부수 효과로 기대하지만 가설이다.
   위 1번과 세 번째 형제다(같은 409 지배가 원인).
3. **F23-R이 결정론적으로 성립하는가** — 배치 정지 후 ~8.7분 고갈이 min_hold 12m

4. **transfer flapping이 재발하지 않는가** — `restartCount` 5분 관찰(#2b).
5. **톱니형 p95가 사라졌는가** — 러너 관측 계약 수리(#1) 이후 F10-H·F20-R에서
   0.0 아티팩트가 없어졌는지.
