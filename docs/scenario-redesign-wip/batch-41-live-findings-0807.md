# 41종 라이브 배치 결함 기록 (2026-08-06~07 진단·수리)

파킹 3종을 뺀 ready 41종 기준. [08-04 배치](batch-44-live-findings-0804.md)가
남긴 실패·스킵을 run 아티팩트와 트레이스 직독으로 되짚은 사이클이다.

이번 사이클에서 확인된 것 셋.

**하나, 실패의 다수는 주입이 아니라 판정과 환경이었다.** 수리 10건 중 8건은 주입도
피해도 실증된 상태에서 판정 계약이 못 받아준 것이고, 나머지는 사다리가 성공 구간을
건너뛴 것이다. "주입이 안 된다"는 진단은 이번에 한 건도 없었다.

**둘, 통과 이력이 있어도 신뢰할 수 없는 조건이 있었다.** F19-P·F19-S의 성공 조건은
주입과 무관한 dispatch 노이즈(0.098)만으로 임계(0.1)에 닿을 수 있었다 — 아깝게 못
넘는 실패가 아니라 **주입 없이도 성립 가능한 거짓 양성 구조**다. 데이터셋 품질에
직결되므로 통과 여부와 별개로 틀린 조건이었다.

**넷째 범주가 하루 끝에 하나 더 나왔다(§20).** 지금까지 결함을 "측정이 거짓말한다 /
환경이 판정을 뒤집는다 / 대조군을 안 본다"로 나눠 왔는데, F23-R 프로브는 **관측 행위
자체가 대상을 교란**한다 — 판정 장치가 판정 대상을 느리게 만든다.

**다섯째 범주는 우리 수리가 배포된 뒤에 나왔다(§23·§24).** `e723d9b` 배포 후 첫
배치(`live-41-58c5b3e5`)에서 F11-R이 abort했고, 규명해 보니 수리는 의도대로
작동했으며 성공을 막은 것은 **감별자가 성공의 부수 효과를 실격 사유로 읽는 구조**
였다 — "부하가 안 온다"와 "너무 망가져 처리량이 무너졌다"가 같은 값을 낸다.
라이브 13종이 노출돼 있고, **F06-P·F15-H는 이미 상시 발화 상태**다.

**셋, 층이 한 칸 더 내려갔다.** 08-04에는 시나리오·러너 층이 주였는데, 이번에는
테스트베드 **환경 자체**의 자립성 결함 2건(commerce 재고 고갈, banking transfer
flapping)이 여러 시나리오의 판정을 동시에 오염시키고 있었다. 시나리오를 아무리
고쳐도 그 아래가 흔들리면 결과가 흔들린다.

## 1. 전역 판정 결함 — APM 백분위의 표본 없는 창이 0.0으로 들어온다

**이 사이클에서 가장 파급이 큰 항목이다.** 시나리오 하나가 아니라 prometheus
`apm_service_p95`를 판정에 쓰는 모든 시나리오가 영향을 받는다.

트래픽이 없거나 스팬이 안 잡힌 창에서 APM 백분위 질의는 값 없음이 아니라 **0.0**을
반환하고, 러너는 그것을 `usable: true`로 받는다. 그리고 adaptive의 streak 갱신은

```
if result is not True: updated[name] = 0
```

이라 0.0이 만든 False 한 번이 **연속 카운터를 통째로 리셋**한다. 즉 밑 신호가 내내
나빠도 표본이 한 번 비면 연속 요건이 구조적으로 성립하지 않는다.

### 증거 — F20-R run fa6749a8

원본 15초 시계열(ms)에는 진동이 없다:

```
39389 / 46503 / 30016 / 20466 / 30010 / 30008 / 33988 / 30005 / 19981 / 27992
```

그런데 틱 값에는 0.0이 섞인다. 그 0.0이 나온 분(05:09·05:14·05:17)은 payment
스팬이 **0건**인 분과 정확히 대응한다. 신호가 좋아진 것이 아니라 **표본이 없었던
것**이고, 판정은 그것을 "임계 미달"로 읽었다.

### 같은 병으로 의심되는 것

F10-H의 "톱니형 p95"(#5)가 같은 계열로 보인다. run 748dd9c8에서 disk가
75·77·75·76으로 포화인 동안 order_p95 독립 표본이 797ms와 7691ms 사이를 오갔고
success streak이 1에서 올라가지 못했다. #5의 수리는 p95를 성공 게이트에서 빼는
쪽이라 이 병을 피해 가지만, **회피이지 치료가 아니다.**

### 같은 병의 clickhouse 쌍둥이 — **아직 안 고쳐졌다** (2026-08-07 추가)

APM 수리로는 안 잡히는 같은 계열 결함이 하나 더 있다. `clickhouse.service_error_rate`
템플릿이 이렇게 생겼다:

```sql
SELECT if(count() = 0, 0, round(100.0 * countIf(...) / count(), 4)) AS value
```

**스팬이 없으면 에러가 아니라 0을 만들어낸다.** APM 0.0과 정확히 같은 조작이지만
소스가 달라 APM 수리 범위 밖이다.

증상은 abort가 아니라 더 나쁜 쪽이다 — **조용한 거짓 음성**이다. payment가 죽어서
스팬이 끊긴 바로 그 순간, 감별자는 "payment 오류율 0 = 정상"으로 읽는다. 즉
**교란 요인이 실재하는 순간에 정확히 눈이 먼다.** must_rule_out에서 이 질의를 읽는
조건이 넷이다:

| 시나리오 | 조건 | 대상 |
|---|---|---|
| F06-P·F19-P·F20-Q | `payment-also-erroring` | food-delivery-payment |
| F20-R | `payment-also-erroring` | commerce-payment |

109에 배포된 러너에 이 코드가 그대로 있는 것을 확인했다(`live_probes.py:104`).
러너 담당에게 넘겼다 — **수리되면 여기에 해시를 채운다: (미수리)**.

### 세 번째 인스턴스 — 이번엔 **대조군을 생산하는 쪽**이다 (`4e07550`)

같은 병의 세 번째 사례이고, **레포 경계를 넘어서** 나왔다. 앞의 둘은 러너
(rca-scenario-runner)였는데 이번 것은 testbed-services의
`scripts/scenarios/profiles/loadgen_monitor.py`다 — 러너 어댑터 전수 점검이
못 본 이유가 그것이다.

loadgen은 요청 0건인 창에서 비율을 `... if checkout_count else 0.0`으로 접어
**"오류율 0%"로 발행**하고 있었다. 소비자(러너)가 아니라 **생산자**가 없는 측정을
0으로 만들어 내보낸 것이다.

수리는 둘이다. ① 빈 창은 비율 필드를 **싣지 않는다** — 러너의
`_loadgen_observation`이 필드 부재를 이미 `LiveProbeError`로 처리하므로 러너 변경
0줄이다. ② **분모(`checkout_count`·`read_count`)를 항상 발행한다** — 계산해놓고
버리고 있었다.

> **`achieved_rps`는 일부러 고치지 않았다.** 그 분모는 요청 수가 아니라 **시간**이라
> 0이 "부하가 전달되지 않았다"는 **진짜 측정값**이다. 여러 시나리오가
> `achieved_rps < 15`를 감별자로 쓰므로, 이것까지 부재로 바꿨으면 **감별자가
> 발화해야 할 때 침묵하는 정반대 결함**을 새로 만들었을 것이다. 같은 모양의 0이라도
> 하나는 아티팩트고 하나는 측정값이다 — 구분이 수리의 핵심이었다.

폭발 반경은 `must_rule_out`에 이 신호를 쓰는 **live 14종**이다(F03-H·F03-P·F04-H·
F06-P·F10-H·F14-P·F15-H·F15-T2·F16-H·F17-P·F18-P·F19-P·F19-S·F23-R).
success·escalate 쪽은 streak 리셋일 뿐 실격 경로가 없다.

**F16-H는 빈 창이 실제로 도달한 확인된 사례다** — k6 checkout 여정이 로그인 실패 시
요청을 한 건도 안 내보내 `entry_status`가 런 내내 null이었고 4런 전부 abort했다.
이번 변경으로 그 창이 "0.0=정상"에서 unusable로 바뀐다.

### 2b. banking transfer flapping (수리 `dec83d4`)

`testbed-transfer`의 SIGKILL(137) 반복은 자원 부족이 아니라 구조 결함이었다.
체인은 릴레이에서 시작해 헬스 프로브에서 끝난다:

```
@Transactional relay()가 루프에서 최대 100건을 kafkaTemplate.send(...).get()으로
순차 대기 → producer 타임아웃 미설정이라 건당 최대 delivery.timeout 120s
→ 그 시간 내내 Hikari 커넥션 점유 → transfer 풀(15) 고갈
   (실측: total=15 active=15 waiting=1, 획득 6105ms 타임아웃)
→ DataSourceHealthIndicator가 같은 풀을 타서 /actuator/health가 probe timeout 3s 초과
→ livenessProbe 실패 누적 → SIGKILL
```

수리: 발행을 트랜잭션 밖으로(짧은 읽기 → 트랜잭션 밖 발행 → 성공분만 짧은 배치
UPDATE), Kafka producer 타임아웃 명시(request 5s / delivery 15s / max.block 5s),
liveness를 DB에서 분리(`/actuator/health/liveness`), transfer 힙 `-Xmx512m` 명시.
readiness는 `/actuator/health`를 그대로 본다 — F17-R의 승인된 스냅샷이 그 블록이다.

### 9. F06-P — 감별자가 무관한 도메인 노이즈를 세고 있었다 (`fb9ce09`)

run 4957e483 트레이스 직독. must_rule_out `promoted-to-5xx`
(`order_create_5xx_rate >= 0.1`)는 "429가 5xx로 승격됐는가"를 재려 했으나,
그 지표가 세는 order의 5xx는 payment가 아니라 **dispatch**에서 온다.

```
POST /api/orders : 200=358 · 429=33 · 400=5 · 503=43   → 43/439 ≈ 0.098
POST /api/payments: 429=33 · 200=2 · 5xx 0건            → pass-through 정상
```

그 503은 dispatch-service 자체 SERVER 500(capacity 3·상세 2·목록 2)과 order의
CLIENT 500=3에 대응한다. `OrderService`가 `checkCapacity`·`dispatchCourier` 실패를
무조건 503으로 바꾸고 CB fallback도 503이라(OrderService.java:94-112,
DispatchClient.java:66-79) dispatch 노이즈만으로 임계 0.1에 붙는다.

게다가 payment 호출은 capacity 검증(96)과 dispatch fan-out(145)을 통과해야
도달한다(154). **dispatch 503은 정의상 payment 이전에 끝난 요청**이므로 429
pass-through의 실격 사유가 될 수 없다.

감별자를 `payment_error_rate >= 5`로 교체. F19-P·F20-Q·F20-R이 이미 쓰는 같은
이름의 감별자이고, 관측은 F06-P에 **이미 선언돼 있었으나 어느 게이트에도 물려
있지 않았다** — 배선만 이어주면 되는 상태였다.

### 10. F05-R — OOM이 구조적으로 불가능한 단을 뺐다 (`d628ba9`)

## 13. F15-P — 복합 압박의 CPU 절반만 주입되고 있었다 (`e526dbd`)

결과**다. 임계 재조정은 ①②가 적용된 재실행 실측을 보고 판단한다.

## 14. F20-R — 주입이 자기 감별자를 위반하고 있었다 (`d1df8a5`)

run fa6749a8은 `evaluation_level_timeout`으로 실패했는데, 실패한 건 판정만이 아니라
주입 자체였다. target_rps 30에서 order-service는 "느려진" 게 아니라 무너졌다:

```

/stats/daily  : 54×500(30025ms) + 45×200(p95 47121ms, max 49493ms)
/checkout     : 22×500, 17×200(30529ms), 2×400
/actuator/health: 10×200 p95 26129ms, 1×503
```

주입 직전 baseline은 완전히 건강했다(checkout 40건 전부 200에 p95 203.7ms,
health p95 1.6ms). 정답지 must_rule_out은 "증상이 타임아웃 5xx가 아니라 지연이다.
5xx면 F19-P 계열"이라고 못박는데, rps 30의 F20-R은 그 조건을 **주입 자신이 위반**
하며 F19-P를 연기하고 있었다.

그대로 유지한다 — 사다리의 목적이 그 조건을 만족하는 단을 찾는 것이다. 하단 1 rps는
추측이 아니라 실측이다(k6 ramp-up이 저부하 구간을 훑어준 곡선: 첫 15초 버킷 ≈1 rps에서
500 0건·min 1826.8ms, 다음 버킷 ≈2~3 rps에서 4건 중 3건이 500).

공유 PG 중간 고리는 **관측만** 배선했다(`database.pg_slow_active_query_count`).
값의 정상 범위를 모르는 채 임계를 붙이면 그게 곧 추측 수리다.

**주의**: 이 사다리는 #1의 러너 수리가 배포된 뒤에 돌려야 한다.

## 16. 미해결 — 설계 결정이 필요한 것들

이 절의 F03-P는 이 문서를 쓴 뒤 실측으로 뒤집혀 **미해결에서 빠졌다**. 원래 판정과
정정 근거를 함께 남긴다 — 판정이 바뀐 과정 자체가 다음 사람에게 필요한 정보다.

### F09-R — 클린 베이스라인 미확보

노드를 100% 태워도 동거 서비스가 멀쩡하다는 08-04 #6의 판정이 아직 뒤집히지도
확정되지도 않았다. 컨테이너 `cpu_throttled` 계열의 깨끗한 평시 분포를 못 잡아
"압박이 전이되지 않았다"와 "전이됐는데 지표가 못 잡는다"를 가르지 못한다.
F09-R 관측에는 현재 throttle 계열이 없다.

### F03-P — 미해결에서 **재배치 확인 가설로 강등** (2026-08-07 재평가)

> 이 항목은 이 문서 안에서 한 번 뒤집혔다. 처음 적은 판정은 "레버가 없어 구조적으로
> 불가"였고, 근거는 **이론 계산**이었다 — "풀을 2로 줄여도 이론 처리량이 ~400rps인데
> 부하는 60rps라 풀이 물리적으로 포화될 수 없다". 그 계산이 틀렸다.

**풀은 실제로 막힌다(run 4a1cbd57 실측).** 평가 틱 42개 중 `payment_p95>=500`이
14틱이고 **최장 11틱 연속**이다(요구 3틱). 최대 1552.51ms까지 올라간다.

이론 논거가 틀린 이유는 유효 서비스 시간을 DB 작업 시간으로 잡았기 때문이다. payment는
`@Transactional` 안에서 커넥션을 쥔 채 외부 HTTP(PG mock·banking transfer, read-timeout
각 10s)를 호출한다. 커넥션 점유 시간은 DB 작업 5ms가 아니라 **그 왕복 전체**이므로
60rps로도 풀 2는 충분히 마른다.

**막힌 쪽은 p95가 아니라 다른 축이다.** 성공은 AND 2항이고
(`payment_p95>=500` **AND** `checkout_5xx_rate>=0.05`, 3연속),
`checkout_5xx_rate`는 **42틱 전부 0.00**이었다(min=max=0.0).

그리고 그 0.00은 **F05-R(#10)을 막은 것과 같은 기전으로 보인다.** 재고가 마르면
checkout이 `reserveStock`에서 409로 조기 종료돼 payment에 **도달하지 못한다**
(`OrderService.checkout`은 reserveStock을 payment보다 먼저 호출한다). payment가 아무리
느려도 checkout은 5xx를 내지 않는다. 재고 재설계(#2a `52f23b6`)가 그 409 지배를 없앤다.

**따라서 F03-P는 `db.workload` 없이도 재배치에서 풀릴 수 있다.** 등급을 "미해결(구조적
불가)"에서 **"재배치에서 확인할 가설"**로 내린다.

다만 의존성이 **둘**이라는 점은 같이 기록해 둔다. `payment_p95`가 읽는 commerce-payment는
#1에서 측정한 8개 서비스 중 **표본 결손이 유일하게 있는 서비스**다(APM 원시 샘플 57/60,
최대 간극 120s로 freshness 계약 경계, 0.0 아티팩트 52회). 실제로 이 run의 `payment_p95`도
0.0을 포함하며 98→1552→1201→25→32→3ms로 크게 요동친다. 즉 F03-P의 성립은
(a) 재고 수리가 `checkout_5xx_rate`를 풀어주는가 **와** (b) 러너 관측 수리 후
`payment_p95`가 어떻게 달라지는가에 **둘 다** 걸려 있다.

`db.workload`는 그 사이 `4a2f465`로 라이브가 됐고 `allowed_scenarios`는 **F02-H 하나**다.
즉 이 레버의 정당화는 F03-P가 아니라 F02-H(캐시 무력화 광역 스캔)로 좁혀졌다.

> **교훈: 이론적 논거로 시나리오를 불가 판정하지 말 것.** 이 레포가 이미 여러 번
> 배운 "기록된 원인을 믿지 말고 재라"와 같은 계열이다. 계산은 모델이고 모델은 항상
> 무언가를 뺀다 — 여기서는 커넥션을 쥔 채 나가는 외부 호출이 빠졌다. 불가 판정은
> 실측으로만 내린다.

### F02-H — 캐시 무력화 재설계, 설계 초안만

## 17. 거짓 양성 — 주입 없이 성립 가능한 성공 조건 (`147363d`)

**이 항목은 통과 이력과 무관하게 데이터셋 신뢰성 문제다.** 별도로 세운다.

F19-P·F19-S의 success는 `order_create_5xx_rate >= 0.1`이었다. 그런데 #9에서 확인한
dispatch 노이즈 상한이 **0.098**이다. 즉 임계가 노이즈 바로 위에 있었고, 주입이
전혀 없어도 dispatch가 평소보다 조금만 나빠지면 성공이 설 수 있었다.

이건 "아깝게 못 넘는 실패"가 아니라 **구조적 거짓 양성**이다. 이 조건으로 통과한
런이 있었다면 그 런이 진짜 주입 인과를 증명했다는 보장이 없다 — 데이터셋으로는
신뢰할 수 없었다.

임계를 정할 근거는 실측 주입 피해다. 노이즈와 자릿수가 다르다:

| 시나리오 | run | 평가 틱 실측 |
|---|---|---|
| F19-P | d68b4fb3 | 0.73 → 0.99로 올라 **0.93~0.98** 유지 |
| F19-S | b7d83934 | 평가 틱 **41개 전부 0.913~1.0** (최솟값도 노이즈의 9배) |

**0.5**로 올렸다 — 노이즈의 5배이면서 주입 정상구간의 절반이라 양쪽에서 안전하고,
F10-H(#5)와 같은 값이다.

AND를 하나 더 붙이는 방식은 쓰지 않았다. `c887e20`이 두 시나리오의 두 번째 AND를
내린 판단이 실측으로 재확인된다 — F19-S의 `payment_error_rate`는 b7d83934에서
**초반 3틱만 66.67이고 이후 내내 0.0**이다. 서킷이 열리면 payment가 PG를 부르지
않고 즉시 반려하므로 자기 오류율이 사라진다. 감별자로 must_rule_out에 두는 것은
맞지만(F19-P는 이미 그렇게 쓴다) 성공 조건으로는 지속되지 않는다.

**판정 기준으로 삼을 질문**: "주입 없이 이 조건이 설 수 있는가." 답이 "설 수 있다"면
그 조건은 틀린 것이다.

### ⚠ 위 수리는 실패했다 — 임계 상향으로는 안 닫힌다 (2026-08-07 후속, `7c90e08`)

**바로 위 문단의 결론("두 시나리오 모두 이제 답이 '없다'")이 실측으로 반증됐다.**
답은 여전히 "있다"였다. 0.1→0.5 상향은 거짓 양성을 못 막았다.

`order_create_5xx_rate_baseline`은 **무주입 대조 팔**이다(같은 질의를
`domain=food-delivery`로 읽어 baseline loadgen 문서를 본다). 두 팔을 나란히 놓으면
수리가 왜 실패했는지가 한눈에 보인다 — F19-P run cae8c16c(succeeded):

```
        주입 팔   대조 팔
el= 79   0.911    1.000   ← 대조가 더 높다
el=143   0.973    1.000
el=473   0.978    0.892
전 구간  payment_error_rate = 0.000 · order_hikari_pending = 0.000
```

**주입이 만든 차이가 없다.** 그런데 성공이 확정됐다. 게다가 이 시나리오가 주장하는
기전(order 커넥션 풀 고갈)의 신호도 전 구간 0이다 — 피해도 기전도 없이 통과했다.

**한 런의 사고가 아니다.** 기록된 F19 런 6개 전부 대조 팔 중앙값이 0.93~1.00이다:

| run | 주입 팔 | 대조 팔(중앙) |
|---|---|---|
| F19-P aa75203a | 0.533~0.993 | 0.933 |
| F19-P cae8c16c | 0.795~0.978 | 0.938 |
| F19-P d68b4fb3 | 0.267~0.994 | 0.931 |
| F19-S 01df886f | 0.881~0.982 | 1.000 |
| F19-S 377a2aad | 0.897~0.981 | 0.967 |
| F19-S b7d83934 | 0.913~1.000 | 0.967 |

원인은 **`dispatches`에 `status` 인덱스가 없는 것**이다(`fd9b7e8`에서 확정).
`DispatchService.countByStatus("ASSIGNED")`가 주문 생성마다 **두 번** 도는데 그 질의를
탈 인덱스가 없어 처음부터 풀스캔이었고, 표가 137만 행에 이르자 임계를 넘었다.
라이브 옵티마이저 실측: `type=ALL · key=NULL · rows=1,012,216` — 1,408행을 돌려주려고
100만 행을 훑는다. 그 결과 `/api/deliveries/capacity`가 500을 내고 dispatch 헬스가
503이 되며, `OrderService`가 그것을 `catch (Exception) → 503 "Dispatch service
unreachable"`로 바꾼다. **그 지점이 payment 호출보다 앞이라 하류 주입이 통째로 가려진다.**

결정적 증거: 두 통과 창(F19-P cae8c16c / F19-S 377a2aad)에서 order `POST /api/orders`가
503을 각각 221·258건 냈는데, **그 503 트레이스 482건 안의 payment 스팬이 0건**이다.
주입은 mock `/pay` 지연이므로 그 5xx를 만들었을 가능성이 0이다.

> **처음 적었던 원인(courier 풀 고갈)은 틀렸다.** `ASSIGNED`는 F19-P 시작 1406 →
> 성공 시점 975 → F19-S 성공 시점 532로 **오히려 줄고 있었고** 상한 2000 근처에도 가지
> 않았다. 즉 "No courier available" 분기가 아니라 "Dispatch service unreachable"
> 분기였다. 나는 전달받은 설명을 그대로 옮겨 적었고, 더 깊이 판 조사가 그것을 뒤집었다 —
> **전달받은 인과도 실측 전까지는 가설이다**(§16b에서 배운 것과 같은 교훈).

즉 위 표에서 "주입 피해 0.93~0.98"이라고 읽었던 값은 사실 대부분 이 dispatch 503이었다.

> **교훈(§17의 진짜 결론): 임계 상향은 거짓 양성을 막지 못한다.** 환경이 신호를
> 포화시키면 **어떤 절대 임계도 넘어간다** — 1.0에 붙은 신호 앞에서 0.5든 0.9든
> 의미가 없다. 노이즈가 "작다"고 가정하고 그 위에 선을 긋는 방식 자체가 틀렸다.
> **대조군이 있으면 대조군을 써라.** 환경 노이즈는 양쪽 팔에 똑같이 실리므로
> 차이로 판정하면 상쇄된다.
>
> 그리고 "주입 없이 이 조건이 설 수 있는가"는 **머리로 답하면 안 된다.** 나는 노이즈
> 상한(0.098)을 근거로 "없다"고 답했지만, 실제 대조 팔은 그 10배였다. 답은 **대조 팔을
> 재서** 내야 한다.

### 지금 할 수 있는 것과 러너가 필요한 것

**러너는 두 관측의 비교를 지원하지 않는다.** `adaptive.py`의 `Condition`은
`id/signal/operator/value: Scalar`이고 `StrictModel`이라 필드 추가도 거부한다 —
`_condition_result`는 `signal`을 **리터럴**과만 비교한다. 따라서 '주입 팔 − 대조 팔'
게이트는 **러너 변경 건**이다(별도 이관).

그때까지 표현 가능한 것은 "대조군이 이미 깨졌으면 실격"이다. `must_rule_out`에
`baseline-arm-also-failing`(대조 팔 ≥ 0.2)을 걸어 **fail-closed**로 만들었다. 차이를
증명하지는 못하지만 **대조군이 오염된 런에 성공을 주지 않는다.** F19-P·F19-S와,
같은 노출을 가진 F10-H에 적용했다(F10-H는 대조 관측이 아예 없어 신설).

**이 감별자와 인덱스 수리(`fd9b7e8`)는 서로를 대체하지 않는다.** 인덱스가 배포되면
dispatch 503이 멎어 대조 팔이 정상(≈0)으로 돌아오고, 그러면 이 감별자는 **조용해진다**
— 막으려던 상황이 사라졌으니 그것이 맞는 동작이다. 감별자는 그 뒤로도 **다음 번
환경 오염을 잡는 그물**로 남는다. 원인이 무엇이든(인덱스든 다른 것이든) 대조군이
깨진 채로는 성공을 주지 않는다는 계약 자체가 이 사건의 교훈이기 때문이다.

### 이번 배치 F19-P·F19-S 통과는 무효다

**데이터셋 사용 불가로 기록한다.** 통과했으나 위 근거로 거짓 양성이 확정됐다 —
주입 피해가 관측되지 않았고 대조 팔이 주입 팔과 구분되지 않는다. 이번 배치의 통과
개수는 **21이 아니라 19로 읽어야 한다.**

### 전수 확인 — 같은 구조가 더 있다

`success`가 loadgen 실패율을 **절대 임계**로 쓰는 ready 시나리오는 **29건**이다.
그중 대조 관측을 **갖고도 성공 귀속에 안 쓰는** 것이 8건이다:

**fail-closed는 차분의 대용이지 대체가 아니다.** 지금 걸어둔 감별자는 "대조군이
깨졌으면 실격"까지만 한다. **"주입이 대조군보다 얼마나 더 나쁜가"는 여전히 못 묻는다** —

## 18. F12-H — "관측 불가능한 감별자"로 의심했으나 실측이 반증했다 (수리 불요)

`must_rule_out`의 `cross-service-overload`(`pricing_p95 >= 300`)가 **부하를 받지 않는
서비스를 읽는 것 아니냐**는 의심에서 시작했다. 러너 수리로 APM p95가 표본 없는 창에서
에러를 내게 되면, `must_rule_out`은 `any` 매칭이라 조건 **하나만** 불가용이어도
레벨 타임아웃 시 `ABORTED / safety_observation_unavailable`로 실격된다
(`adaptive.py:277`). 그래서 새 abort 위험 후보로 지목됐다.

**실측은 정반대였다.**

| 측정 | commerce-pricing |
|---|---|
| ClickHouse SERVER 스팬(60분) | 4399건, **61/61분 존재, 빈 분 0** |
| APM 원시 샘플(60분) | 60/60, median·max 간극 **모두 60s** |
| freshness 120s 계약 위반 | **0회** |
| 0.0 아티팩트 | **0회** — 잰 8개 서비스 중 유일하게 gateway·product와 함께 0 |
| 실제 F12-H 런 (1918e0d6 / 9252ae2f) | `pricing_p95` 불가용 **0/18 · 0/58**, 값 1.05~7.48ms, 0.0 없음 |

**구조가 이 결과를 설명한다.** `OrderService.checkout`은 cart → **pricing(155)** →
inventory 예약(product 경유, 160) → payment 순이다. pricing은 주입 대상인 product보다
**상류**라, product를 조여도 pricing 호출은 줄지 않는다. 굶을 수가 없는 배치다.

### 두 측정이 갈린 이유 — 창이 다르다

같은 신호를 두고 상반된 수치가 나왔다. 7일 창에서는 공백이 **376건**이고, 60분 창과
실제 런에서는 **0건**이다. 둘 다 맞다.

7일치에는 **loadgen이 돌지 않는 유휴 구간**이 섞인다. 부하가 없으면 저트래픽 서비스는
당연히 발행이 끊긴다. 그러나 판정은 유휴 구간에 돌지 않는다 — 게이트가 신호를 읽는
시간은 런 중이고, 런 중에는 baseline loadgen이 항상 살아 있다(preflight
`baseline-traffic`이 그것을 강제한다).

> **교훈: 판정 창 밖의 공백은 감별자 재설계의 근거가 아니다.** 저트래픽 서비스의
> 지표 연속성을 볼 때 유휴 구간을 섞으면 "이 신호는 자주 끊긴다"는 잘못된 결론이
> 난다. 재야 할 창은 **런 창**이고, 가장 좋은 것은 그 시나리오의 실제 run 아티팩트에서
> `usable=false` 틱을 세는 것이다(위 0/18·0/58처럼).

수리하지 않았다. 지웠다면 정답지가 명시한 **범위 축**을 잃었을 것이다 — "느려지는
것은 product와 그 상류뿐이고, product를 거치지 않는 경로(pricing 등)는 정상이다.
노드 전역이 느려지면 F09-R이다." 이 감별자는 F09-R과의 변별을 혼자 지고 있다.

원칙("관측 불가능한 감별자는 감별자가 아니다")은 옳다. **F12-H가 그 사례가 아니었을
뿐이다.** 전수 확인 결과 ready 41종에서 `must_rule_out`이 표본기아 질의를 읽는 조건은
5개뿐이고, **abort 게이트는 하나도 없다.** 나머지 4개는 전부 위 clickhouse 쌍둥이(#1)에
걸린 `payment-also-erroring`이며, 그쪽은 abort가 아니라 거짓 음성으로 샌다.

## 19. 정답지 산문 드리프트 — 데이터셋 품질 결함의 한 범주 (`bd10144`·`f833e50`)

**구조적 사각지대다.** 구조화된 `injected_fault.levels`는 컨트롤러와 기계 대조되는데
(`test_stated_injection_matches_the_live_controller`) **산문 필드는 아무도 대조하지
않는다.** 그런데 채점자가 실제로 읽는 것은 산문 쪽이다. 즉 사다리를 고칠 때마다
정답지의 사람이 읽는 면이 조용히 낡고, 아무 테스트도 붉어지지 않는다.

ready 41종 + parked 승격 후보 3종의 정답지를 계약과 대조해 **10건**을 찾았다 — 산문 8건과
구조화 필드 2건이다.

### 유형 1 — 실행기·대상이 틀렸다 (`bd10144`)

| 시나리오 | 필드 | 산문 | 실제 |

| F15-R | injection_summary | `timeline.flap` | `timeline.compose` (레지스트리에 없는 이름) |

**F18-P가 가장 심각했다.** `e1f17b6`이 **폐기한** 설계를 정답으로 가리키고 있었다.
폐기 이유가 maxSurge=0에서 롤아웃이 유일한 파드를 먼저 내려 자기 감별자를 켜기

### 유형 3 — 구조화 필드가 어긋났다 (`59c484c`)

**산문만 대조하면 구조화 필드가 남는다.** 위 두 유형을 고친 뒤 별도 감사에서 같은
계열이 `injected_fault.companions`에서 나왔다. `levels`는 컨트롤러와 대조되는데
(`test_stated_injection_matches_the_live_controller`) **companions는 아무도 대조하지
않았다.**

| 시나리오 | 정답지 companions | 실제 companion_refs | 성격 |
|---|---|---|---|
| F05-R | `[load.north_south]` | `[k8s.env, load.north_south]` | **주입의 절반을 감춤** |
| F14-P | `[load.north_south]` | `[]` | **주입하지 않는 것을 주장** |

F05-R이 특히 나쁘다. 빠진 `k8s.env`가 **힙을 `-Xms384m -Xmx384m -XX:+AlwaysPreTouch`로
고정하는 두 번째 레버**이고, 그것 없이는 OOM이 나지 않는다 — #10의 바닥 계산(~544MiB)이
바로 그 레버 위에 서 있다. 정답지만 읽으면 "메모리 한도만 내렸다"로 읽힌다.

**두 건 다 자기 산문과 모순이었다.** F05-R의 `injection_summary`는 k8s.env companion을
정확히 설명하고, F14-P는 "부하는 baseline loadgen이 공급한다"고 쓴다. 산문·컨트롤러·
카탈로그 셋이 일치하고 구조화 필드 하나만 어긋나 있어 정본은 명확했다.

배포 블로커는 아니다 — 디스패치는 이 필드를 읽지 않는다(러너는 plan의
`companion_profile_ids`를 쓴다). 그러나 캡처 케이스에 실려 sha256으로 봉인되므로
**채점자가 읽는 면**이다.

**같은 뿌리의 부수 건**: `load.north_south`의 `tag_pattern`이 `14-P`를 받아주는데
`allowed_scenarios`에는 없었다(차집합이 정확히 이것 하나, 51 vs 50). 2026-08-03에
정규식으로 들어갔다가 그 뒤 companion이 빠지면서 allowlist에서만 사라진 것이다.
fail-closed라 실행은 막히지만 계약 안에 거짓 흔적이 남는다. 기존 가드가 **한 방향만**
(allowlist → 정규식) 보고 있어서 반대 방향이 살아남았다 — 양방향으로 넓혔다.

> **교훈: 대조 면을 하나 고치면 나머지 면이 드러난다.** 산문 감사(유형 1·2)를 통과한
> 뒤에도 구조화 필드가 남아 있었고, 그 구조화 필드를 고치자 같은 계약 안의 정규식이
> 남아 있었다. "무엇이 무엇과 대조되는가"를 목록으로 관리하지 않으면 매번 한 겹씩만
> 벗겨진다.
>
> **네 번째 면이 그 뒤에 또 나왔다 — 이번엔 레포 경계를 넘어서다(§1c `4e07550`).**
> 러너 어댑터를 전수 점검해 "빈 창을 0으로 만드는" 병을 두 곳에서 잡았는데, 세 번째
> 인스턴스는 러너가 아니라 **testbed-services의 loadgen 생산자**에 있었다. 점검 범위를
> "러너 안"으로 그은 순간 그 밖은 안 보였던 것이다.
>
> 즉 대조 면 목록은 **한 레포 안에서만 세면 반드시 빠진다.** 신호는
> 생산자(loadgen) → 저장소(VM·ClickHouse) → 소비자(러너 어댑터) → 판정(게이트) →
> 정답지(산문·구조화 필드)로 흐르고, **드리프트는 그 사슬 어디에서든 난다.**
>
> **그래서 그 사슬을 목록으로 만들었다 →
> [대조 쌍 레지스트리](correspondence-pairs-0807.md).** 각 마디에서 무엇이 무엇과
> 일치해야 하는지, 가드가 있는지, 없으면 기계화 가능한지, 불가능하면 사람이 무엇을
> 봐야 하는지를 적었다. 레포 경계를 넘는 쌍(러너 allowlist·109 배포 사본)도 포함한다.

### E5의 실제 사례 — F20-R "orders(5만 행)" (2026-08-07)

E5(**비나열형 산문 수치**)는 가드가 원리적으로 못 잡는다고 분류했는데, 그 분류가
맞았다는 사례가 바로 나왔다.

F20-R 정답지가 `orders(5만 행)`이라 적고 있었다. **실측 1,185,713행 — 20배가 넘는다.**
그리고 그 수치는 장식이 아니라 **"풀스캔이라 CPU를 크게 쓴다"는 인과 설명의 근거**로
쓰이고 있었다. 나열형이 아니라 서술 속 단일 수치라 `test_prose_ladders…`는 못 본다.

고치면서 **숫자만 바꾸면 안 된다**는 게 드러났다. 세 가지가 얽혀 있었다:

1. **행수**(5만 → 1,185,713). 인과는 오히려 **강해진다** — 20배를 훑으니 부담이 크다.
2. **"orders에는 user_id 인덱스 하나뿐"** — 오늘 프로브 수리로 `idx_orders_paid_created`를
   추가하면서 **이 문장이 거짓이 된다.**
3. 그래서 **전제 자체를 다시 썼다.** 원래 서술은 "인덱스가 없어서 풀스캔"이었는데,
   정확한 전제는 **"질의가 인덱스를 탈 수 없는 모양"**이다 — `dailyStats`는
   `FUNCTION('DATE', createdAt) GROUP BY`라 **createdAt 인덱스가 있어도** 못 타고,
   `search`는 OR-null이라 조건이 비면 전 행을 훑는다. 둘 다 sargable하지 않으므로
   **인덱스를 무엇을 얹든 풀스캔이다.** 새 인덱스가 preflight 프로브 전용이고 이 두
   질의는 여전히 못 탄다는 것도 앵커 주석에 남겼다.

> **E5에 대한 답 — 사람이 언제 봐야 하는가:** 정답지가 **실측 수치를 인과의 근거로
> 인용하면 그 수치는 시간이 지나면 반드시 낡는다.** 표는 자라고 인덱스는 추가된다.
> 그러니 (a) 자라는 데이터의 수치를 인용할 때와 (b) **인과의 전제가 되는 사실을 바꾸는
> 커밋**(오늘의 인덱스 추가 같은)을 낼 때, 그 사실을 인용한 정답지를 함께 열어야 한다.
> 이번에는 **인덱스를 추가하는 쪽이 그 사실을 인용한 산문을 찾아가서** 고쳤다 — 그것이
> 이 쌍에서 사람이 해야 하는 일의 형태다.

### 어디까지 기계화했는가

**기계화됨(가드 5종)**: ① 나열형 사다리 수치 ↔ 계약(`f833e50`) ② `injection_summary`의
실행기 이름 ↔ 바인딩(`bd10144`) ③ `code_anchor` 줄번호·심볼(기존) ④ `companions` 3면
합의(`59c484c`) ⑤ `tag_pattern` ↔ `allowed_scenarios` 양방향(`59c484c`). ③은 지금 green이라
오늘 앱 코드 변경(ReconciliationBatch·OutboxRelay·ResponseDelayFilter)으로 밀린 앵커는
없다.

수치 가드의 범위는 **의도적으로 좁다** — "A→B→C"처럼 **나열로** 쓴 것만 본다. 서술 속
단일 값("한도 1Gi")이나 측정 서술("anon 413MiB")은 계약 밖 사실을 정당하게 인용할 수
있기 때문이다. 단위 동치 넷(Gi↔Mi, 바이트 임계, 정수 파라미터, JVM 힙 플래그)을 넣어
오탐 0·진탐 5를 만들었다.

**사람 눈에 남는 것**: 인과 서술의 논리, 감별 근거의 타당성, 그리고 **폐기된 설계를
가리키는 서술**(F18-P 류 — 값이 아니라 접근이 낡은 경우라 수치 대조로 잡히지 않는다).

### 고치지 않고 남긴 것 (판단 필요)

- **F20-R**: 산문이 사다리 강등(#14)을 반영하지 않는다. 다만 rps를 **틀리게 적은 게
  아니라 언급하지 않는다** — 오류가 아니라 불완전이라 손대지 않았다.
- **F15-P**: `--vm-keep`과 새로 붙은 `load.north_south` companion(#13)이 산문에 없다.
  같은 이유로 불완전이지 오류는 아니다.
- **F21-Q(parked)**: 산문이 `host.stress`/`db.workload` 선택지를 말하는데 parked
  컨트롤러도 `host.stress`라 **현재는 일치**한다. 그러나 `a709606`의 app.control
  재설계가 승격되면 그 순간 F18-P와 같은 상태가 된다 — 승격 시 함께 고쳐야 한다.
- **F11-R**: 산문이 primary(`load.north_south`) 대신 companion(`cache.control`)을 먼저
  소개하지만 내용은 정확하다. 그래서 가드도 "primary인가"가 아니라 "바인딩된 것 중
  하나인가"로 설계했다.

## 20. 관측 행위가 대상을 교란한다 — 네 번째 결함 범주

지금까지 이 문서의 결함을 셋으로 나눠 왔다: **측정이 거짓말한다**(§1 계열),
**환경이 판정을 뒤집는다**(§2), **대조군을 안 본다**(§17). 이건 넷째다 —
**관측하는 행위 자체가 관측 대상을 바꾼다.**

### F23-R 프로브가 commerce postgres의 버퍼 캐시를 밀어낸다

F23-R의 `restock_movement_count` 프로브는 `movement_type='RESTOCK' AND created_at >=
now() - 5분`을 **15초마다**(tick_interval) 실행한다. 그런데 그 질의를 탈 인덱스가 없다.

카탈로그 직독으로 확인했다(**표를 스캔하지 않고** — 이 결함을 조사하면서 같은 질의를
또 돌리면 그 자체가 교란이다):

```
inventory_schema.inventory_movements
  인덱스: inventory_movements_pkey (id)
          idx_inventory_movements_product (product_id, created_at DESC)   ← 선두 컬럼 불일치
  행수  : 2,465,557
  크기  : 353 MB
  shared_buffers: 128 MB
```

선두 컬럼이 `product_id`라 `movement_type` 필터에 쓸 수 없다. 다른 에이전트의 실측
플랜은 `Parallel Seq Scan`, `Rows Removed by Filter 829,131 × 3 workers = 2.49M`,
`Buffers: read=20672(=161MB)`, `Execution Time 701ms`다.

**한 번 실행에 161MB를 읽는데 shared_buffers가 128MB다.** 즉 F23-R이 도는 동안
**15초마다 commerce postgres의 버퍼 캐시가 통째로 밀려난다.**

그리고 F23-R 자신의 성공 게이트는 `checkout_409_rate`로 **같은 인스턴스의 checkout
거동**을 본다. 상주 baseline 부하도 같은 인스턴스를 친다. 즉 **프로브가 자기가
측정하려는 것을 느리게 만든다.**

> **오늘 찾은 것 중 성격이 가장 나쁘다.** dispatches 인덱스 부재(§17)는 *앱*이 문제
> 질의를 돌린 것이라 "환경 결함"이었다. 이건 **러너 자신**이다 — 판정 장치가 판정
> 대상을 오염시킨다. 어떤 게이트를 고쳐도 이 교란은 남는다.

### ⚠ F23-R 결과에는 별표가 붙는다 — 이번 배치만이 아니다

**통과든 실패든 자기 프로브가 자기 측정을 교란한 상태의 값이다.** 그리고 인덱스가
애초에 없었으므로 **지금까지의 모든 배치가 같은 조건이었다** — F23-R 이력 전체가
그렇다. §12에서 "F23-R을 운에서 결정론으로 바꿨다"고 적었는데, 그 판단의 근거가 된
과거 런들도 이 교란 위에 있었다는 뜻이다.

수리(부분 인덱스 `(created_at) WHERE movement_type='RESTOCK'`)는 **다음 배포 묶음**이다.
지금 만들면 353MB 표의 인덱스 빌드 I/O가 **도는 배치를 흔든다** — 고치는 행위가 또
교란이 되는 자리다.

### 대비 사례 — 같은 설계 실수를 banking은 피했다

F14-P의 프로브도 성격이 같다(15초마다 도는 러너 DB 질의). 그런데 인덱스가 있다:

```
TRANSFERS.IDX_TRANSFERS_CREATED       : CREATED_AT          ← 창구 필터
TRANSFERS.SYS_C008659                 : TRANSFER_REF        ← 안티조인
LEDGER_ENTRIES.IDX_LEDGER_REF         : TRANSFER_REF        ← 안티조인 반대편
OUTBOX_EVENTS.IDX_OUTBOX_UNPUBLISHED  : (PUBLISHED_AT, CREATED_AT)  ← 선두가 필터 컬럼
```

**표 크기가 문제가 아니다.** TRANSFERS 882,053행 · LEDGER_ENTRIES 1,285,548행으로
inventory_movements(2,465,557)와 **같은 자릿수**다. 그런데 한쪽은 cost 6이고 한쪽은
701ms다. 차이는 규모가 아니라 **누군가 인덱스를 맞춰 뒀는가**뿐이다.

특히 `IDX_OUTBOX_UNPUBLISHED`는 **선두 컬럼이 필터 술어**라 정확히 F23-R이 못 가진
형태다. 같은 설계 실수를 한쪽만 피한 것이고, **프로브 질의가 인덱스를 타는지 아무도
확인하지 않았다**는 게 공백이다.

### 전 프로브 전수 점검 (2026-08-07) — 🔴 셋, 그중 둘은 새 발견

러너의 DB·ClickHouse 프로브 **전부**를 훑었다. **`EXPLAIN`만 썼고 `ANALYZE`는 한 번도
쓰지 않았다** — 질의를 실제로 실행하면 그 자체가 교란이라, 이 점검이 지키려는 것을
점검이 깨뜨리게 된다.

| 프로브 | 대상 | 행수 / 크기 | 계획 | 주기 | 판정 |
|---|---|---|---|---|---|
| `restock_movement_rate` (F23-R) | `inventory_movements` | 2,465,557 / 353 MB | Parallel Seq Scan, 161MB read | **15s** | 🔴 |
| `order_duplicate_count_since_t1` (F15-R) | `payment_schema.payments` | 1,187,765 / 252 MB | **Parallel Seq Scan** cost 27,245 | **15s** | 🔴 **신규** |
| `baseline-business-success` (preflight) | `order_schema.orders` | 1,185,713 / 149 MB | **Parallel Seq Scan** cost 24,297 | 런당 1회 × **41종** | 🔴 **신규** |
| `outbox_unpublished_count` (F04-H·F18-P) | `order_schema.outbox_events` | 1,123,649 / 279 MB | **Index Only Scan cost 4.31** | 15s | 🟢 |
| `inventory_stock_level` (F23-R) | `inventory_schema.inventory` | 16 / 1000 kB | Seq Scan cost 117 | 15s | 🟢 |
| `ledger_unmatched_transfer_count` (F14-P) | Oracle `transfers`⋈`ledger_entries` | 882K / 1.29M | 인덱스 서브 | 15s | 🟢 |
| `service_error_rate` (CH) | `otel_traces_local` | — | 정렬키 `service_name, timestamp` 접두 일치 + 일 파티션 | 60s | 🟢 |
| `pg_stat_activity`·`pg_locks`·`pg_indexes` 계열 | 시스템 뷰 | — | 힙 스캔 없음 | 15s | 🟢 |

**`outbox_events`가 결정적 대조다.** 1,123,649행 · 279MB로 `inventory_movements`와 같은
자릿수인데 **cost 4.31**이다. 부분 인덱스 `(created_at) WHERE published_at IS NULL`의
술어가 질의 술어와 정확히 일치해 Index Only Scan을 탄다. **같은 인스턴스·같은 규모에서
cost 4와 cost 27,245가 갈리는 이유는 인덱스 설계뿐이다.**

### 🔴 셋의 수리안 (DDL은 배포 묶음 — 여기서는 제안만)

```sql
-- 1) F23-R (기존에 확인된 것)
CREATE INDEX CONCURRENTLY idx_inventory_movements_restock
  ON inventory_schema.inventory_movements (created_at)
  WHERE movement_type = 'RESTOCK';

-- 2) F15-R (신규) — 질의는 created_at 창구 뒤 order_id 로 묶는다
CREATE INDEX CONCURRENTLY idx_payments_created_order
  ON payment_schema.payments (created_at, order_id);

-- 3) preflight (신규) — status='PAID' 고정 술어이므로 부분 인덱스가 가장 좁다
CREATE INDEX CONCURRENTLY idx_orders_paid_created
  ON order_schema.orders (created_at) WHERE status = 'PAID';
```

셋 다 `CONCURRENTLY`를 붙였다 — 353MB·252MB·149MB 표라 배타 잠금으로 만들면 그
자체가 교란이다(§20의 교훈이 수리에도 적용된다).

**우선순위**: F15-R(2번)이 F23-R과 같은 15초 주기에 252MB라 교란 크기가 비슷하다.
3번은 주기가 낮지만(런당 1회) **41종 전부의 preflight**라 배치 전체에 얇게 깔린다.

### 곁가지로 나온 것 둘

- **`outbox_events`에 동일한 부분 인덱스가 둘 있다** —
  `idx_order_outbox_unpublished`와 `idx_outbox_events_unpublished`가 정의까지 같다.
  읽기에는 무해하나 쓰기마다 두 번 갱신된다. 정리 대상(배포 묶음).
- **F20-R 정답지가 "orders(5만 행)"이라고 적었는데 실측 1,185,713행이다** — §19의
  E5(비나열형 산문 수치) 부류라 가드가 못 잡는다. 스무 배 넘게 벌어졌고, 그 산문이
  "인덱스 없이 풀스캔한다"는 인과 설명의 근거로 쓰이므로 갱신이 필요하다.

> **규칙: 새 프로브를 붙일 때 "이 질의가 대상 시스템에 무엇을 하는가"를 물어라.**
> 지금까지 프로브를 볼 때 물어온 것은 "값이 정확한가 / 표본이 있는가"였다. 그것만으로는
> 부족하다. 프로브도 **워크로드**다 — 실행 계획과 버퍼 영향을 보고 붙여야 한다.
> [대조 쌍 레지스트리](correspondence-pairs-0807.md)에 **프로브 질의 ↔ 인덱스** 쌍으로
> 넣었다.

| 시나리오 | 보정 시점 | 현재 | 배율 | 상태 |
|---|---|---|---|---|
| F20-Q | 590,913 | 1,369,819 | **2.32×** | 별표 |

> **대표성 없는 상태에서 보정했을 가능성**이 크다. 승격 전에 재보정이 선행돼야 한다.

> **검증 상태 — F20-Q 배율은 확정됐다(2026-08-07 후속).** 내가 처음에 대조에 실패해
> 가설로 뒀는데, 원인이 **내가 쓴 측정 방식** 쪽이었다.
>
> ```
> 상태별 실측 합계 : PENDING 1,349,303 + DELIVERED 19,041 + CANCELLED 959 = 1,369,303
> 표의 총 행수     : 1,369,819   (차이 516 = 그 사이 증가분)
> 내가 쓴 추정치   : 1,009,508   → 실측의 73.7%
> ```
>
> 즉 1,369,819는 **COUNT 계열 실측**이고 내가 대조에 쓴 MySQL
> `information_schema.table_rows`가 **26% 낮게** 나온 것이다. InnoDB 추정치의 알려진
> 오차 범위 안이라 **반증이 아니라 내 대조 방식의 문제**였다. F20-R은 원래 맞았다
> (내 카탈로그 측정 1,185,713 ↔ 표의 1,195,109).

> **이 대조 실패가 설계 제약의 첫 실증 사례다.**
> [드리프트 가드 설계](injection-scale-drift-guard-0807.md) §3.x에 이미
> **"밴드 판정은 같은 방식으로 잰 값끼리 비교해야 한다"**는 제약이 적혀 있고, 그 근거로
> `orders`의 추정치 1,020,625 대 실측 1,369,819(**34% 낮음**)이 붙어 있다. 내가 잰
> 1,009,508이 그 1,020,625와 사실상 같은 값이다 — **방식이 다른 두 값을 비교하면
> 26~34% 어긋난다**는 것을 우연히 실연한 셈이다. 가드를 구현할 때 이 제약을 어기면
> 배율이 그만큼 왜곡된다.

> **⚠ 아직 확인되지 않은 것 — 보정 시점 수치의 측정 방식.**
> 위 표의 보정 시점 값(590,913 / 566,279 / 19,102)이 **어떤 방식으로 측정된 것인지
> 레포 어디에도 기록이 없다.** 그 숫자들은 `ee0c909`(오늘 작성된 설계 문서)에 처음
> 등장하고, 07-24 승격 무렵 커밋 어디에도 나오지 않는다 — 즉 **당시 기록이 아니라
> 사후 재구성**이다. 따라서 배율에 오차 범위를 붙인다:
>
> - 양 끝이 **같은 방식**(둘 다 실측 또는 둘 다 추정)이면 → **2.32× 그대로.**
> - 보정 시점이 **추정치**이고 현재가 실측이면 → 배율이 최대 34% 부풀려진 것이므로
>   참값은 약 **1.73×~2.32×** 구간이다.
>
> **결론은 어느 쪽이든 바뀌지 않는다** — 하한 1.73×도 불량 구간(§21-b에서 게이트를
> 실제로 낮춰야 했다)에 들어간다. 다만 **밴드 값을 정할 때는 이 오차가 들어간다.**
> 가드를 구현하기 전에 보정 시점 값을 **추정치 방식으로 다시 기록**하는 것이 가장 깨끗하다.

### 21-b. 우리가 오늘 만든 오진 — F20-Q 게이트 완화 (`5178218`)

**이 사이클의 수리 중 하나가 드리프트 증상을 정체성 속성으로 읽었다.**

§4에서 F20-Q의 `consecutive_ticks`를 2→1로 내리며 근거를 **"이 정체성에서 구조적으로
채울 수 없다"**로 적었다. 실측상 정확한 문장은 **"지금 표 크기에서 못 채운다"**이다.
보정 시점(590,913행)에는 힙이 2.32배 천천히 차서 파드가 더 오래 버텼고 2연속이
채워졌을 것이다.

그리고 **낮춘 결과가 나쁘다** — 드리프트가 더 진행돼도 게이트가 안 보이게 됐다.
투영: 약 **2.10M행(≈08-19)에 평가 틱이 0개**가 된다. 그때는 1연속조차 못 채운다.

**되돌리지 않는다** — 지금 크기에서는 실제로 2연속이 안 채워지므로 원복하면 그냥
실패한다. **정리·재보정 후 원복 여부를 재검토**한다.

> **규칙: 게이트를 낮추기 전에 드리프트를 의심하라.** "구조적으로 불가능하다"와
> "지금 조건에서 불가능하다"는 다른 문장이고, 후자를 전자로 적으면 **완화가 영구화**된다.
> 게이트를 낮추는 근거가 "물리적으로 창이 좁다"류일 때, 그 창이 **원래 그랬는지 아니면
> 최근에 좁아졌는지**를 먼저 물어야 한다. §16b(F03-P "이론상 불가"가 틀렸다)와 방향만
> 반대인 같은 병이다 — 그때는 이론으로 불가라 했고, 이번엔 관측으로 불가라 했는데
> 둘 다 **조건부였다.**

## 22. 검증 전 판단이 전달을 통과한다 — 메타 교훈

오늘 **검증 전 가설이 전달 단계를 그대로 통과해 사용자 보고까지 간 일이 두 번** 있었다.

| 가설 | 전파 경로 | 반증 |
|---|---|---|
| food **courier 풀 포화**가 F19 5xx의 원인 | 조사 → team-lead → 나 → 결함 문서(§17) | ASSIGNED가 1406→975→532로 **줄고 있었다**. 실제 원인은 dispatches 인덱스 부재(`fd9b7e8`) |
| 앞 런 **잔해가 다음 런을 오염**시킨다 | 조사 → team-lead → 사용자 보고 | 종료 후 checkout이 **1분 내 회복**. 그 판단의 근거였던 "직전 10분 87% 실패" 창이 **앞 시나리오의 주입 구간을 통째로 포함**하고 있었다 |

둘 다 **낸 쪽이 스스로 반증**했다는 게 그나마 다행이지만, 그 사이에 문서와 보고가
한 번씩 잘못 나갔다.

> **규칙 1: 실측 전 판단에는 "가설" 라벨을 붙이고, 전달하는 쪽은 그 라벨을 유지한다.**
> 라벨이 한 홉만 떨어져도 다음 사람은 그것을 사실로 받는다. 오늘 내가 §17에 courier
> 가설을 사실로 적은 것이 정확히 그 사고다.
>
> **규칙 2: 산술로 도출한 예측은 예외 없이 가설이다.** "임계까지 몇 초", "몇 배",
> "언제 0이 된다" — 전부 모델이고 모델은 항상 무언가를 뺀다(§16b에서 커넥션을 쥔 채
> 나가는 외부 호출이 빠졌던 것처럼). **§21의 2.32×와 §21-b의 08-19 투영도 이 규칙의
> 적용 대상이다** — 그래서 위에 검증 상태를 명시했다.
>
> **규칙 3: 창을 인용할 때 그 창이 다른 주입 구간을 포함하지 않는지 먼저 확인한다.**
> 위 오독이 정확히 이것이었다. 배치는 시나리오를 연달아 돌리므로 "직전 N분"은
> 거의 항상 앞 시나리오의 주입을 포함한다.

### 22-b. 오늘 규칙이 실제로 작동한 사례 두 건

**하나 — 조사자가 자기 전제를 먼저 정정했다.** F11-R 규명(§23)을 맡은 에이전트가
"제 수리는 아직 배포 안 됐습니다"로 보고를 시작하려다 확인했더니 **이미 배포돼
있었다**(커밋 `e723d9b` 13:17:45Z → 러너 재기동 13:21:41Z). 그 확인을 건너뛰었다면
"배포 전 데이터"라는 틀린 전제 위에 규명 전체가 얹혔을 것이다. 규칙 1을 **보고
전에** 자기 문장에 적용한 첫 사례다.

**둘 — 수리 커밋 자신의 폭발 반경 예측이 빗나갔다.** `e723d9b`의 커밋 메시지는
영향 목록에서 F11-R을 이렇게 적었다: *"이미 성공한 F09-H·F11-R은 판정이 바뀌진
않지만 더 낮은 단에서 성공했을 수 있다."* 실제로는 **F11-R의 판정이 바뀌었다**
(성공 → abort). 산술(`escalate 시점 elapsed − min_hold` 여유)로 도출한 분류였고,
그 모델에는 **"레벨에 더 오래 머물면 새로운 것을 만난다"**가 빠져 있었다.

> **규칙 2의 실증이다** — 산술로 도출한 예측은 그 예측을 적은 사람의 것이라도
> 가설이다. 특히 **"영향 없음"이라는 예측이 가장 검증되지 않는다**: 영향 있는
> 쪽은 재실행으로 확인하지만 없는 쪽은 아무도 안 본다.

## 23. 수리가 결함을 만든 게 아니라 드러냈다 — F11-R (`live-41-58c5b3e5`, `e723d9b` 배포 후 첫 회귀)

**오늘 만든 수리가 배포된 뒤 처음 드러난 것이라 기록 가치가 크다.** escalate streak을
min_hold에서 리셋하는 수리(`e723d9b`)가 배포된 뒤, **이전 배치에서 통과했던 F11-R이
abort**했다. 첫 가설은 "수리의 부작용"이었고 **3/5만 맞았다.**

### 23-a. 【실측】 수리는 의도대로 작동했다

| | run | level0 체류 | 결과 |
|---|---|---|---|
| pre-fix | `1429f4dc` | **127초** (min_hold 120s) | 성공 |
| post-fix | `68ca5a2e` | **302초** | abort |

수리 전에는 min_hold가 끝나자마자 승급했다 — 선충전된 streak이 정확히 그만큼
앞당긴 것이다. 이제는 제대로 머문다. **수리 자체는 검증됐다.**

### 23-b. 【실측】 그런데 성공을 막은 건 rps 붕괴가 아니었다

F11-R 성공 = `checkout_5xx_rate >= 0.05 AND business_ok == false`, **3연속**.

```
el=238  5xx 0.97  bizok False  succ 2
el=254  5xx 1.00  bizok False  succ 2
el=270  5xx 1.00  bizok True   succ 0   ← 리셋
el=334  5xx 1.00  bizok False  succ 2
el=350  5xx 0.99  bizok True   succ 0   ← 리셋
```

**5xx가 1.00인데 `business_ok`가 True로 튄다.** 그 플랩이 성공 streak을 두 번
리셋했다. rps 붕괴는 el=429 이후로 **맨 끝**이고, 그때는 이미 4분 넘게 성공을 못
굳힌 뒤였다. **rps 붕괴는 종착점이지 성공을 막은 기전이 아니다.**

### 23-c. 【실측·소스】 플랩의 기전 — 창 비율과 점 표본을 AND로 묶었다

두 신호가 **같은 문서에서 오는데 분모가 다르다.** `loadgen_monitor.py`:

```python
elif metric == "http_reqs" and tags.get("step") == self.business_step:
    self.entry_status = int(raw) if raw and str(raw).isdigit() else 0   # 마지막 한 건

"business_ok": self.entry_status in {200, 400, 409},                    # 점 표본
"checkout_5xx_rate": business_5xx_rate,                                 # 30초 창 비율
```

- `checkout_5xx_rate`는 **30초 창의 비율**이다.
- `business_ok`는 **창의 마지막 business step 한 건**의 상태코드다. 창이 바뀌어도
  리셋되지 않고 다음 값이 올 때까지 남는다.

그래서 창의 97~100%가 5xx여도 **마지막 한 건**이 200·400·409이면 `business_ok`가
True가 된다. 성공 조건은 이 둘을 AND로 묶으므로, **분모가 수백인 신호와 분모가
1인 신호가 같은 무게로 streak을 굴린다.**

`{200, 400, 409}`가 ok인 것도 같이 봐야 한다 — **409(재고 소진)가 "비즈니스 정상"에
들어 있다.** §2a의 재고 고갈이 살아 있는 동안에는 409가 흔하므로, 마지막 한 건이
409이기만 하면 플랩이 난다. 정확한 표집 비율은 실측 안 했다(**가설**), 다만
"5xx 1.00과 bizok True가 동시에 성립하는 구조"는 위 소스로 확정이다.

**노출은 2종이고 형태가 같다.** `business.checkout_invariant`를 읽는 컨트롤러는
`F08-H`·`F11-R` 둘뿐이며, **둘 다 `business_ok == false AND checkout_5xx_rate >= 임계`**
형태다(F08-H는 2연속, F11-R은 3연속).

> **【가설】 F08-H도 같은 방식으로 막힐 수 있다.** F08-H는 이번 배치의 오스킵
> 재실행 3종에 들어 있다. 구조가 동일하므로 같은 플랩을 만나면 같은 결과가 난다 —
> 다만 F08-H가 실제로 그 구간을 지나는지는 **결과가 나와야 안다.**

### 23-d. 【가설】 수리는 결함을 만든 게 아니라 드러냈다

pre-fix는 레벨 노출이 3.3분이라 플랩을 만날 기회가 적었고, post-fix는 8분이라 두 번
만났다. 즉 **pre-fix의 통과는 부분적으로 운**이었을 수 있다.

**단정할 수 없다** — pre-fix 창이 짧아 플랩을 표집 못 한 것이라, 그때도 플랩이
있었는지는 직접 못 봤다.

> **§21-b와 짝이 되는 사례다.** 그때는 드리프트 증상을 정체성으로 오독해 **게이트를
> 낮췄고**, 이번엔 **수리가 짧은 창에 가려져 있던 불안정성을 드러냈다.** 방향은
> 반대지만 뿌리는 같다 — **창의 길이가 판정을 만든다.** 창이 짧으면 결함이 안
> 보이고, 창이 길어지면 없던 결함이 생긴 것처럼 보인다. 둘 다 결함은 내내 거기
> 있었다.

### 23-e. 【실측】 rps 붕괴는 부하 생성기 고장이 아니라 주입 결과다

```
15:00:00  checkout 38건  p95 30,309ms   ← 30초 타임아웃 벽
15:00:15  checkout  1건  p95 22,988ms
15:01:00  checkout  0건
```

요청은 **도달했고 30초 벽에 걸렸다.** k6는 `ramping-arrival-rate`로 돌지만 VU가
고갈되면 도착률을 유지하지 못한다 — 요청당 30초씩 묶이니 처리량이 무너지는 게
당연하다. **부하 생성기 고장이 아니다.**

(30초 벽 자체가 어디서 오는지는 미확인이다 — k6 스크립트에는 per-request timeout
설정이 없으므로 서버·프록시 쪽 값이다. 확인 항목으로 남긴다.)

## 24. 감별자가 "부하가 안 온다"와 "너무 망가져 처리량이 무너졌다"를 못 가른다 — 다섯 번째 범주

§23-e가 개별 사건이 아니다. **`achieved_rps`를 하한으로 걸어 "부하 미도달"을
배제하려는 감별자는, 주입이 성공해서 생긴 처리량 붕괴도 같은 값으로 본다.**

### 24-a. 노출 전수 (레지스트리 실측, 라이브 13종)

`must_rule_out`에 `achieved_rps < N`을 쓰는 컨트롤러 전부. 여유는
**(해당 시나리오 사다리 최저 단의 target_rps − 임계) / target_rps**다.

| 임계 | 시나리오 | 사다리 최저 target_rps | 여유 |
|---|---|---|---|
| `lt 30` | **F11-R** | 35 | **14%** |
| `lt 30` | **F05-R** | 35 | **14%** |
| `lt 15` | F05-H · F08-P | 20 | 25% |
| `lt 100` | **F07-H** (`surge-not-achieved`) | 120 | 17% |
| `lt 15` | F03-H · F06-H · F15-R · F17-R | 30~35 | 50~57% |
| `lt 15` | F15-T2 | 40 | 62% |
| `lt 15` | F03-P | 60 | 75% |
| `lt 15` | **F06-P · F15-H** | **5** | **−200%** (아래 24-c) |

> **전달받은 목록에 대한 정정 2건.**
> 1. **12종이 아니라 13종이다.** `F07-H`가 빠져 있었다 — 게이트 id가
>    `surge-not-achieved`라 이름으로 거르면 안 잡히지만 형태는 같은
>    `achieved_rps lt`이고, **임계 100은 전체에서 가장 높다.**
> 2. **여유는 임계의 절대값이 아니라 target 대비 비율로 봐야 한다.** `lt 30`이
>    가장 취약한 건 임계가 높아서가 아니라 **그 시나리오의 최저 단이 35라서**다.
>    F07-H는 임계 100이지만 최저 단이 120이라 여유가 17%로 비슷한 위험대에 있다.

F11-R은 **위쪽도 좁다** — 같은 `must_rule_out`의 `general-overload`가
`achieved_rps > 70`인데 최상단이 65다(여유 7.7%). 사다리가 밴드 `[30, 70]`
안에서 35→50→65를 밟는다.

### 24-b. 왜 특히 나쁜가 — 성공하면 실격되는 구조

성공 신호가 **실패율 계열**인 9종(`F03-H`·`F03-P`·`F05-H`·`F05-R`·`F06-H`·
`F08-P`·`F11-R`·`F15-R`·`F17-R` — 레지스트리 대조로 목록 확인)에서는
**완전 실패 → 타임아웃 → 처리량 붕괴가 성공 직후에 따라오는 정상 경로**다.

즉 **성공하면 실격된다.** 감별자가 배제하려던 것("부하가 안 왔다")과 시나리오가
증명하려던 것("너무 망가져 부하를 못 받는다")이 같은 관측값을 낸다.

> **§20·§17과 나란히 놓는 새 범주다.**
> - §17: 감별자가 **주입 없이도** 참이 될 수 있다(거짓 양성).
> - §20: **관측 행위가** 대상을 교란한다.
> - §24: 감별자가 **성공의 부수 효과를** 실격 사유로 읽는다.
>
> 셋 다 "감별자를 실측 없이 기대로 썼다"에서 나온다.

### 24-c. 【실측】 F06-P·F15-H는 이미 상시 발화 상태다 — 새로 찾은 결함

두 시나리오의 설계 부하는 **5 rps**인데 감별자는 **`achieved_rps < 15`**다.
즉 **주입과 무관하게 매 틱 참**이며, 붕괴가 아니라 **정상 동작에서** 발화한다.

경위는 `765e99f`(08-04)다. F06-P·F15-H의 성공 조건이 429 비율인데 부하를 올리면
앱이 429를 5xx로 바꿔 자기 신호를 지운다는 실측에 따라 **target_rps를 40 → 5로**
내렸다. 그 커밋은 이렇게 적었다:

> *"target_rps를 40 → 5로 내렸다. **감별자는 그대로 둔다 — 정당한 감별자다.**"*

**임계 15는 target 40에서는 정당했다**(여유 62%). 부하만 내리고 감별자를 안 옮기니
임계가 설계 부하 위로 올라섰다. §21(보정 드리프트)의 **거울상**이다 — 그때는
대상이 자라 주입이 세졌고, 여기서는 부하가 작아져 감별자가 못 넘는 벽이 됐다.

**우리의 08-07 F06-P 수리(`fb9ce09`)로는 안 열린다.** 그 수리는 같은 `any` 묶음의
**다른** 감별자(`promoted-to-5xx` → `payment-also-erroring`)만 교체했다.
`load-not-delivered`가 상시 참인 한 F06-P는 여전히 실격된다.

> **【검증 상태】** 소스·레지스트리로 확정된 것은 "설계 부하 5 < 임계 15"까지다.
> 두 시나리오가 실제로 매 런 abort하는지는 **런 아티팩트로 확인 안 했다**(배치 중).
> 08-04 배치의 F06-P는 `achieved_rps 5.28`로 이 감별자에 걸려 스킵됐는데,
> **그때는 붕괴값이었고 지금은 설계값이다** — 관측값이 같아 구분되지 않는다는
> 이 범주의 성질을 그대로 보여준다.

### 24-d. 완주 후 수리 대상 2건 (서로 독립)

1. **`business_ok` 플랩** (§23-c) — 지금 F11-R을 막는 유일한 이유. **"측정이
   거짓말한다" 계열이므로 §1과 같은 뿌리다.** 방향: 점 표본을 창 집계로 바꾸거나
   (예: 창 안 business step의 non-ok 비율), 성공 조건에서 빼고 `checkout_5xx_rate`
   하나로 판정한다. **생산자 쪽 수리이므로 러너 문법 변경이 필요 없다.**
   409를 ok로 셀지도 함께 결정해야 한다.
2. **`user-load-not-flowing` 감별자** (§24-a) — 13종 노출. 방향: **분모(요청 시도
   수)를 함께 보거나**, 5xx가 높을 때 면제한다(`achieved_rps < N AND
   checkout_5xx_rate < M`). `checkout_count`는 `4e07550`으로 이미 문서에 실리므로
   분모 쪽 재료는 있다. **다만 두 신호를 한 조건에서 묶으려면 러너 문법이 필요하다**
   — §17의 `compare_to`와 같은 대기 항목이다. 러너 변경 없이 지금 할 수 있는 것은
   **F06-P·F15-H의 임계를 설계 부하에 맞춰 내리는 것**(24-c)뿐이다.

**러너 관측 수리(#1)가 배포되면 이전 배치와 단순 비교하면 안 된다.** 0.0을 값으로

**success·escalate의 판정 결과는 바뀐다.**

0.0을 만들어내던 서비스(60분 창 실측, 0.0 발생 횟수):

## 이번 배치 격리에 대한 판단 — 오염 가설은 반증됐다

앞서 "앞 런의 잔해가 다음 런을 오염시킨다"는 우려가 전달됐으나 **실측으로 반증됐다**
(§22). 채택하는 문장은 이것이다:

> 이번 배치는 smoke 모드라 `clean-window`·`scenario_overlap` 격리 게이트가 꺼져 있다.
> 다만 실측상 시나리오 종료 후 commerce checkout은 **1분 안에 회복**되고 5분 간격 동안
> 청정하게 유지되므로, **앞 런의 잔해가 다음 런을 오염시킨 증거는 이 배치에 없다.**
> 남은 한계는 `baseline-business-success`가 절대 건수 임계라 매우 심하게 망가진
> 테스트베드는 통과시킬 수 있다는 것이고, 이는 **잠재 위험이지 이번 배치에서 관측된
> 오염은 아니다.**

### `baseline-business-success` 임계의 약점 (잠재 위험, 관측된 피해 없음)

임계가 **절대 건수**(5분에 5건)라 **정상의 1.6%까지 통과한다.** 그리고 러너 코드
주석의 "96% 감소" 산술은 **24 PAID/min 기준인데 실측이 61/min이라 낡았다** — 같은
임계가 실제로는 훨씬 더 망가진 상태까지 통과시킨다는 뜻이다.

이번 배치에서 **관측된 피해는 없다.** 재배치 완주 후 **상대 임계**(평시 대비 비율)로
바꾼다. 이것도 §21의 보정 드리프트와 같은 계열이다 — 절대 수치로 박은 기준은
테스트베드가 자라면 조용히 의미를 잃는다.

## ⚠ 지금 도는 배치(`live-41-f0758c44`) 데이터의 해석 한계

**이 절을 읽지 않고 이번 배치 데이터로 대조군 판단을 내리면 안 된다.**

생산자 접기 수리(`4e07550`)는 **레포에만 있고 109에 안 나갔다**(배치 중이라 배포
금지). 109 사본을 직접 확인했다 — `checkout_count else 0.0` 접기가 **5곳에 그대로**
있고, 분모(`checkout_count`)는 **한 번도 발행하지 않으며**, 파일 mtime이
**2026-07-29**다. 즉 지금 도는 배치는 접힌 데이터를 만들고 있다.

따라서 이 배치 데이터에는 다음 제약이 있다.

1. **대조 팔의 0.0은 두 가지 뜻이 섞여 있다** — "요청이 있었고 오류가 없었다"와
   "요청이 0건이라 0으로 접혔다". **이 배치 데이터로는 둘을 구분할 수 없다.**
2. 따라서 **"대조군이 깨끗해졌다"는 결론을 이 배치로 내리면 안 된다.**
   0.0은 깨끗함의 증거가 아니다.
3. **표본 수를 알 수 없다** — 0.33이 1/3인지 100/300인지 모른다. 오늘 차분 게이트가
   성립하지 않은 이유가 정확히 이것이었다(창당 요청 2~15건, 표준오차 ~0.20).
4. **주입 팔도 같은 모호성을 갖는다** — F25-H·F03-H의 `checkout_5xx_rate`가 상시
   0.000인 것이 409 지배 때문인지 빈 창 때문인지 **이번 배치에서도 구분되지 않는다.**
   §11c에서 F03-H·F03-P의 대조 팔을 "228/98 표본 전부 0.000"이라 적었는데, 그
   0.000 중 일부가 빈 창일 수 있다는 뜻이다 — **임계 0.02 자체는 안전한 방향(보수적)
   이지만, "대조 팔이 주입 무관함이 증명됐다"는 문장은 다음 배포 후에 재확인해야 한다.**
5. **다음 배포 후부터** 분모가 실리므로 이 모호성이 사라진다. **그때까지 대조군 관련
   판단은 보류가 안전하다.**

> **교훈: 없는 측정을 0으로 만들면, 그 0을 쓴 모든 판단이 소급해서 의심스러워진다.**
> 오늘 이 병을 세 곳에서 찾았고(러너 APM · 러너 clickhouse · loadgen 생산자),
> 셋 다 "값이 없음"과 "값이 0임"을 같은 것으로 취급하고 있었다. 마지막 것이 특히
> 나쁜 이유는 **대조군을 만드는 쪽**이라 대조 기반 판정 전체의 토대를 흔들기 때문이다.

## 재배치 후 확인할 가설 — 수리했다고 단정하지 말 것

아래는 **수리가 들어갔을 뿐 라이브로 확인되지 않았다.** 재배치 후 런으로
검증하기 전까지 해결로 기록하지 않는다.

**⚠ 대조군이 걸린 항목(1·2·6)은 위 해석 한계 때문에 이번 배치로는 답이 나오지
않는다** — 생산자 수리가 배포된 **다음** 배치에서 봐야 한다.

1. **F05-R·F03-P의 `checkout_5xx_rate`가 드디어 움직이는가** — 두 시나리오는
   **한 원인을 공유한다.** 재고가 마르면 checkout이 `reserveStock`에서 409로 끝나
   payment에 도달하지 못하고, 그래서 payment가 OOM으로 죽든(F05-R) 커넥션 풀이
   막히든(F03-P) 사용자 피해 신호가 0.00에 붙박인다. **같은 기전·같은 수리
   (#2a `52f23b6`)·같은 확인 항목**이므로 한 줄로 묶어 본다. 둘 다 나머지 성공
   조건은 이미 실증돼 있다 — F05-R은 OOMKilled 3회, F03-P는 `payment_p95>=500`
   11틱 연속. 이것이 안 움직이면 재고가 아니라 피해 경로 자체를 다시 의심해야 한다.
2. **F25-H의 409 dirty가 풀렸는가** — #2a의 부수 효과로 기대하지만 가설이다.
   위 1번과 세 번째 형제다(같은 409 지배가 원인).
3. **F23-R이 결정론적으로 성립하는가** — 배치 정지 후 ~8.7분 고갈이 min_hold 12m
   이전에 들어오는지, 그리고 `restock-still-running`이 오발화하지 않는지(#12).
4. **transfer flapping이 재발하지 않는가** — `restartCount` 5분 관찰(#2b).
5. **톱니형 p95가 사라졌는가** — 러너 관측 계약 수리(#1) 이후 F10-H·F20-R에서
   0.0 아티팩트가 없어졌는지.
6-b. **F08-H가 `business_ok` 플랩에 걸리는가** (§23-c) — F11-R과 성공 조건 구조가
   같고 이번 배치 오스킵 재실행에 들어 있다. 걸린다면 노출 2종이 모두 실증되고,
   안 걸린다면 플랩의 빈도가 창 길이·409 비율에 달렸다는 뜻이다.
6-c. **F06-P·F15-H가 `load-not-delivered`로 실격되는가** (§24-c) — 소스상 상시 참이
   므로 abort가 예측된다. **예측이 빗나가면 `achieved_rps`가 설계 부하와 다르게
   측정되고 있다는 뜻**이므로 그쪽을 먼저 봐야 한다.
7. **대조 팔이 실제로 어떤 값을 내는가** ⚠ — §11c/§11d의 판단과 남은 25종 분류가
   전부 여기 달려 있다. **분모가 실리는 다음 배치에서만 답할 수 있다**(위 해석 한계
   4·5번). 그때 대조 팔이 여전히 오염된 것만 추리면 다음 라운드 범위가 정해진다.
